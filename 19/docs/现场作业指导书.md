# 现场作业指导书（P5 现场部署）

> **这一份文件的目的**：把「拿到一台空服务器」到「EMS 在跑并接上真实位号」
> 写成**可复现的书面步骤**，让换人不靠口头交接。
>
> **它替谁**：`docs/交接/下一步工作交接说明.md` §2.4 里那句
> 「没有部署产物：没有服务化 / 守护进程 / 开机自启 / 日志轮转 / 配置落盘位置约定」。
>
> **配套模块**：`19/`。本文件只用 `19/` 的脚本 + `11/ P1/ P2/ 13/` 的**已编好产物**，
> 不要求现场有编译器（见 §1.2 的两条路）。

---

## 0. 怎么用这份文件

| 你是 | 从哪一节开始 |
| --- | --- |
| 第一次部署，照着做 | §1 → §3 逐节（每节都有「命令 / 期望输出 / 排查方向」） |
| 已经在跑，要核对点表 | §4 |
| 要验收 | §6 |
| 出了事要处置 | §7 |
| 要接手 | §8 |

**三条贯穿全文的纪律**（都是踩出来的，不是规定）：

1. **不许跳过"期望输出"那一行。** 现场最贵的事故都是"命令成功了、东西没生效"——
   `.bat` 的编码坑、`--capture` 的策略参数不导出、段被 `reset` 清掉，
   **退出码全是 0**。没有"期望输出"就没有判据。
2. **不算"装好了"直到 §6 的每一条都过。** 尤其 §6.4（不自动带载）——
   那条不过说明安全链是断的。
3. **任何"改了配置"的动作之后必须 `--check` + `snapshot`。** 见 §5。

## 1. 前置条件

### 1.1 安装根（本指导书的路径基准）

约定 **安装根 = 一个不含空格、不含中文的目录**，例如 `D:\EMS`。
下文所有 `<root>` 都指它。（**必须不含空格**：`schtasks /TR` 的嵌套引号对空格很敏感，
`install_task.bat` 会在检测到空格时直接拒绝安装并把原因报出来。）

安装根的**内部布局与仓库一致** —— 这样 `19/src/ems_supervisor.py` 的内置进程清单
（相对路径 `11/build/xxx.exe`）不用改就能用：

```
<root>\
├── 11\build\rtdb_initializer.exe         进程 0：建段 + 常驻保活
├── 11\build\device_side.exe              进程 1：设备侧（写 MEAS/STA/CFG）
├── 11\build\ems_side.exe                 进程 2：EMS 侧（写 CMD）
├── P1\build\ems_config.exe               配置模板 / 校验 / 导出实际生效值
├── P2\build\ems_observe.exe              可观测性演示 / 导出 SOE 与指标
├── 13\build\modbus_probe.exe             现场点表核对工具
├── 19\src\ems_supervisor.py              进程守护器（P5 新增）
├── 19\src\config_store.py                配置版本与回滚（P5 新增）
├── 19\src\log_rotator.py                 日志落盘与轮转（P5 新增）
├── 19\scripts\*.bat                      安装 / 卸载 / 跑测试
├── conf\                                   ← 运行期生成
│   ├── ems_config.json                    当前生效配置
│   ├── supervisor.json                    进程清单（按站点改这个）
│   └── history\vNNNN_*.json               配置版本快照
└── log\                                    ← 运行期生成
    ├── supervisor.log  rtdb_initializer.out.log  device_side.out.log  ems_side.out.log
    ├── soe\    soe_current.csv  soe_0001.csv …
    └── metrics\ metrics_current.prom …
```

### 1.2 前置清单

| 项 | 要求 | 怎么确认 |
| --- | --- | --- |
| OS | Windows 10 / Server 2016 及以上（64 位） | `ver` |
| 编译器 | **不需要**（用构建机编好的产物，见下） | 现场若要自编：MinGW-w64 `g++ 8.1.0`，`-std=c++17`。**避开 `<filesystem>` / `<charconv>`** |
| 产物 | `11\build\` `P1\build\` `P2\build\` `13\build\` 四组 `.exe` | `19\scripts\install_task.bat --check` 会逐个检查 |
| Python | **3.8+**，标准库即可（零第三方依赖） | `python -V` |
| 共享内存 | 无特殊端口；RT_DB 走**页面文件映射对象**（不是 socket） | `11\build\rtdb_initializer.exe --seconds 5` 能跑通 |
| 南向端口 | Modbus 现场默认 `502`（需管理员绑定）；联调替身用 `15020` | 见 §3.7 |
| 北向端口 | IEC104 默认 `2404` | `P3` 侧配置 |
| 权限 | 安装阶段需**管理员**（`/RU SYSTEM` 注册计划任务） | `net session` 返回 0 |
| 磁盘 | 建议 ≥ 20 GB 空闲（日志轮转保留 N 份，见 §3.8） | `dir <root>` |
| 时钟 | **上现场之前先对时**（见 §1.3） | `w32tm /query /status` |

**产物怎么来（两条路，选一条）**

- **路 A（推荐）——构建机编好再拷**：在开发机跑 `scripts\build_all.bat`，
  然后把 `11\build\*.exe`、`P1\build\ems_config.exe`、`P2\build\ems_observe.exe`、
  `13\build\modbus_probe.exe` 与整个 `19\` 目录按 §1.1 的布局拷到 `<root>`。
  现场不需要编译器。
- **路 B —— 现场自编**：现场装 MinGW-w64 g++ 8.1.0，跑
  `11\scripts\build.bat` / `P1\scripts\build.bat` / `P2\scripts\build.bat` / `13\scripts\build.bat`。
  **注意**：`scripts\build_all.bat` 是 33 步全量（含 P3 / vendor），现场不需要；
  按模块单独编更快。

### 1.3 上现场之前先对时（否则 SOE 时间戳不可信）

```
:: 期望输出：显示当前时区与时间源
w32tm /query /status
:: 手动指定内网 NTP
w32tm /config /manualpeerlist:"ntp.example.local" /syncfromflags:manual /update
w32tm /resync
```

**失败排查**：`w32tm` 报"服务未启动"→ `net start w32time`；
域内机器时间由域控下发，不要手工改。

> **为什么这件事排在第一步**：P2 的 SOE、`06/` 的 `fsm().history()`、经济性核算
> **全部以时间戳为轴**。时间错了两小时，事故复盘时你会在日志里找不到那条故障。
> 交接说明 §3.5 把 SNTP 列为"不做就上不了现场"的欠项之一，就是这个原因。

## 2. 部署形态：选了 **计划任务**，理由与"何时该换"

### 2.1 决定

**落地形态 = Windows 计划任务（Task Scheduler）+ 自带进程守护器。**

- 安装 / 卸载：`19\scripts\install_task.bat` / `uninstall_task.bat`
- 守护器：`19\src\ems_supervisor.py`（Python 标准库）
- 开机自启：`/SC ONSTART`，账号 `SYSTEM`，`/RL HIGHEST`
- 失败恢复：**不用**任务计划自己的"失败重启"（它只能对"任务退出"生效），
  而是守护器**一直活着**、在内部做单进程级的重启与退避。

### 2.2 为什么不选 Windows 服务

| # | 理由 |
| --- | --- |
| 1 | **真·服务不是"注册一下"就能成**。`sc.exe create` 把一个**控制台程序**注册为服务后，SCM 会等它调用 `StartServiceCtrlDispatcher` 并报 `SERVICE_RUNNING`；不报，**约 30 秒后 SCM 直接杀掉进程**，而 `sc query` 显示 `STOPPED` / 反复重启 —— 现场看到的现象是"服务自己崩了"，实际是**根本没握手**。要用 Python 握手就得引 `pywin32`，破坏"零第三方依赖"（开发约定 §1）。 |
| 2 | **服务化真正值钱的那部分，计划任务同样有**：开机自启（`/SC ONSTART`）、指定账号（`/RU SYSTEM`）、无窗口、可查询（`schtasks /Query /V`）。 |
| 3 | **守护逻辑必须自己写，外面包什么都要写。** 难的不是"起进程"，是**按正确顺序起**（§3.9 的三条约束）**+ 谁挂了要连带重启谁**。这部分在 `ems_supervisor.py` 里，与外壳无关。 |
| 4 | **跨平台**。同一份守护器在 Linux 上换一个 systemd unit 就行（`docs/README.md` 给了模板）；`sc.exe` 只能管 Windows。 |

`19\scripts\install_service.bat` **故意拒绝**在缺少 SCM 包装器时安装
（退出码 2 并把上面的原因和两条可行路径打出来）——
**不做"看起来装上了、30 秒后被 SCM 杀掉"的假成功。**

### 2.3 什么时候该换（满足任一条就换）

| 条件 | 换法 |
| --- | --- |
| 客户运维规范强制要求服务出现在 `services.msc`、可用 `net start/stop` 管理 | (a) **写一个 C++ 真服务壳**：`StartServiceCtrlDispatcher` + `CreateProcess` 拉起 `ems_supervisor.py`；壳本身零依赖，符合约定 §1。 |
| 需要系统级"服务失败自动恢复"策略与 Windows 事件日志集成 | 同上 |
| 需要以特定服务账号（而非 SYSTEM）运行并纳入服务权限审计 | 同上 |
| 需要与现网其他服务用同一套启停编排（如 SCOM / SCOM-like） | 同上 |
| (b) 用一个已实现 SCM 握手的包装器 | **不推荐**：第三方，破坏零依赖；只在客户已有统一包装器时用 |

换的时候**守护器一行都不用改** —— 壳只管"把 `python ems_supervisor.py --root <root> run`
拉起来并保持"，顺序/退避/级联仍在守护器里。

## 3. 分步操作：从空服务器到 EMS 在跑

> 每一步给三样：**命令原文** / **期望输出** / **失败的排查方向**。
> 命令里的 `<root>` 换成你的安装根（下文示例用 `D:\EMS`）。
> 所有 `python` 都可以用 `set EMS_PYTHON=<你的python.exe>` 指定。

### S1 一次性核对前置

```bat
cd /d D:\EMS
python -V
python 19\src\ems_supervisor.py --root D:\EMS check
```

**期望输出**（末行）：

```
[CHECK OK] 进程清单可用（可执行文件齐、依赖不成环）
```

并且能看到三进程的启动计划：

```
  启动顺序（依赖必须先就绪）：
   1. rtdb_initializer     deps=-                 ready_timeout=15s
        exe = D:\EMS\11\build\rtdb_initializer.exe
   2. device_side          deps=rtdb_initializer  ready_timeout=20s
   3. ems_side             deps=device_side       ready_timeout=30s
```

**失败排查**

| 现象 | 方向 |
| --- | --- |
| `可执行文件不存在 …11\build\xxx.exe` | 产物没拷全 → 按 §1.2 路 A/路 B 补齐；`dir D:\EMS\11\build` |
| `no usable python` / `[FAIL] no usable python` | 装 Python 或 `set EMS_PYTHON=...` |
| `依赖成环` | `conf\supervisor.json` 被改坏了 → 删掉它，脚本会重新生成默认清单 |
| 输出是乱码 | 控制台代码页问题，先 `chcp 65001`；**这不影响判定**（判定看 ASCII 的 `[CHECK …]` 行） |

### S2 生成进程清单并按站点改

```bat
python 19\src\ems_supervisor.py --root D:\EMS --write-config
type D:\EMS\conf\supervisor.json
```

**期望输出**：`[OK] 已写出 D:\EMS\conf\supervisor.json`，文件里三个进程的
`name / exe / args / depends_on / ready_pattern / ready_timeout_s` 齐全。

**必须改的两处**（照抄默认清单在现场是错的）：

1. `11/build/*.exe` → 换成现场的**真实设备进程**（见 S10）。
2. `args` 里的 `--steps`/`--dt`/`--speed`：默认是联调用的加速参数。
   现场要**实时**跑：`--dt 0.1 --speed 1`，`--steps` 给一个足够大的数
   （它只是"跑多少拍就正常退出"，现场应给 10 年量级，例如 `864000000`）。

**失败排查**：`--write-config` 报错 → 目录权限；`conf\` 手工 `mkdir` 后再试。

### S3 生成配置模板 → 填参数 → 上电前校验

```bat
cd /d D:\EMS
P1\build\ems_config.exe --dump-template > conf\site.json
```

**期望输出**：`conf\site.json` 是**带注释**的 JSON 模板（`//` 注释可用），
含 `loop / plant / limits / safety / coordinator / state_machine / strategies` 六节。

填参数时**只写"这个站和默认有什么不同"**（缺省即沿用各层默认值，见 `P1/docs/README.md` §3）。
填完**先校验再谈别的**：

```bat
P1\build\ems_config.exe --check conf\site.json
```

**期望输出**（末行）：

```
[OK] 配置可装配
```

退出码 **0**。

**失败排查**

| 现象 | 方向 |
| --- | --- |
| 报错带 `行:列` | 直接定位到那一行；常见是中文逗号、缺引号、`//` 注释写成了 `#`（`#` 也支持，注意别混用） |
| `error`：`soc_min >= soc_max`、`eta ∉ (0,1]`、`transformer_capacity_kw <= 0` | 这是"一定会跑坏"的错，必须改；`P1/docs/README.md` §6 有 error 全表 |
| `warning`：`d_target > transformer_capacity`、`enable_safety_engine=false` | **警告不拦启动**，但要在交接单上写明"为什么允许" |
| `装配期 error`：策略 id 不存在 | 策略 id 抄错了；`P1/docs/README.md` §4 说明为什么 id 打错必须报错 |
| 退出码 1 | 配置错误；退出码 2 是行为验证失败（`--apply` 才有） |

### S4 离线跑 24h 验证（**上电前必做**）

```bat
P1\build\ems_config.exe --apply conf\site.json --quiet
```

再跑一遍可观测性，确认**硬不变量全过 + 事件成对**：

```bat
P2\build\ems_observe.exe --demo 24 --quiet
P2\build\ems_observe.exe --fault 12
```

**期望输出**：`--apply` 打印 24h 关口峰值 / 购电量 / 充放电量 / SOC 区间，
末行无 `[FAIL]`，退出码 0；`--fault` 打印的每条故障都是 **SET/CLEAR 成对**
（例如 `PCS_FAULT_SET` 后必有 `PCS_FAULT_CLEAR`），迁移链带 `reason`。

**失败排查**

| 现象 | 方向 |
| --- | --- |
| 硬不变量被破坏（退出码 2） | **不许上电**。把 `conf\site.json` 与 `P1\build\ems_config.exe --capture` 的产物一起带回去分析 |
| SOC 打到 `soc_min` 就再也充不进 | 典型"配置过紧"（变压器容量不够同时带负荷和充电）→ 复核 `limits.transformer_capacity_kw` / `limits.d_target_kw`，`P1/docs/README.md` §5 有实测对照 |
| 关口功率抖动、跟踪误差大 | 契约需量 `d_target` 落在负荷带内会触发 L2 需量纠偏的 1 拍极限环（`11/docs/README.md` §7.1 已记录，未修）→ 把 `d_target` 抬到负荷峰值之上 |
| 事件不成对 | 记下来，这是 P2 的缺陷方向；不要用"大概没事"糊过去 |

### S5 落盘生效值（**这一步产出回滚点**）

`conf\site.json` 是**纸面配置**（写注释、写"与默认的差异"），
`conf\ems_config.json` 是**活文件** —— 真正生效的那一份。两者要分开落：

```bat
:: ① 把"实际生效值"落到活文件
P1\build\ems_config.exe --capture conf\ems_config.json

:: ② 再把它存成一个带时间戳的版本（这就是回滚点）
python 19\src\config_store.py --root D:\EMS snapshot --note "上电前离线验证通过"
python 19\src\config_store.py --root D:\EMS list
```

**期望输出**

```
[SNAPSHOT OK] v0001_20260926-101500 → conf\history\v0001_20260926-101500.json
  版本                            字段      字节  激活   备注
  v0001_20260926-101500        104    3135  *    上电前离线验证通过
  共 1 版；`*` = 与当前 conf/ems_config.json 内容一致
```

**为什么是两步，而不是只跑 `snapshot`**

- `snapshot` 自己会调 `ems_config.exe --capture` 取生效值，但**只写 `conf\history\`**，
  **不写活文件**。活文件是"系统现在正在用的那一份"，必须显式落下来。
  不落它：`list` 的激活列是空的，`rollback` 会打印
  `回滚前自动备份为 None` —— 因为**没有"当前"可备份**，§6.2 的判据④就验不到。
- `--capture` 导出的是**运行中实际生效的值**，含"被显式设置过的策略参数"——
  那是纸面配置里看不到的东西
  （`P1/docs/README.md` §8 说明了为什么未设置的参数不出现在导出里）。
- **没有这一份，现场调参一旦出错就没有可退回去的点。**

**失败排查**

| 现象 | 方向 |
| --- | --- |
| `找不到 ems_config.exe` | 设 `set EMS_CONFIG_EXE=D:\EMS\P1\build\ems_config.exe`，或先跑 `P1\scripts\build.bat`；也可以 `snapshot --from <captured.json>` 直接用已有导出 |
| `--capture 失败` | `ems_config.exe` 自己装配不起来 → 先解决 S3 的 `--check` |
| `list` 的**激活**列是空的 | 活文件没落 / 与本版内容不一致 → 回到 ① 重跑 `--capture conf\ems_config.json` |
| `rollback` 打印 `回滚前自动备份为 None` | 同上：没有活文件就没有"当前"可备份 |

### S6 版本对比与回滚演练（**上电前先演练一次，别等出事再试**）

```bat
:: 改一个参数后对比
python 19\src\config_store.py --root D:\EMS diff v0001 v0002

:: 回滚演练（注意：回滚前会自动再存一版）
python 19\src\config_store.py --root D:\EMS rollback v0001
python 19\src\config_store.py --root D:\EMS list
```

**期望输出**

```
diff v0001_20260926-101500 → v0002_20260926-113000：2 处差异
  ~ safety.soc_min: 0.1 → 0.12
  ~ limits.d_target_kw: 320 → 360
```

```
[ROLLBACK OK] 已回滚到 v0001_20260926-101500（回滚前自动备份为 v0003_20260926-114500）
```

**回滚后版本数是 `+1` 而不是 `-1`** —— 因为回滚**自己**也要可回滚。
如果看到版本数减少，说明有人在代码里把"回滚前自动备份"删了，**停下来查**。

（`--root` 后面也可以跟 `latest` / `active` / `7`；`active` 表示"当前生效的那一版"。）

### S7 点表核对（**逐点**，见 §4 的清单）

先用联调替身自检点表，再对真设备逐点读：

```bat
cd /d D:\EMS
:: ① 替身自检：打印 32 点对照表（人眼核对用）
python 13\sim\modbus_slave.py --self-check
:: ② 只打印分块读计划（不发报文，先确认"3 次请求读全 32 点"）
13\build\modbus_probe.exe --plan
:: ③ 读真设备一遍
13\build\modbus_probe.exe --host 192.168.1.10 --port 502 --unit 3
```

**期望输出**（`--self-check` 末行）：

```
  共 32 点（C++ 侧 EMS_POINT_COUNT = 32）
```

（`--plan`）**期望输出**：`3` 次请求（量测 7 点 + 空位 1 + 配置 14 点 → IR 两段；指令 → HR 一段；
状态 → DI 一段）。**这个数字是契约**：变成 32 说明点表散了，现场会表现为"采一帧要 3 秒"。

（`--port 502` 读一遍）**期望输出**：一张 32 行的表，每行有 `ok` 列。

**失败排查（`ok` 列是最重要的一列）**

| 现象 | 方向 |
| --- | --- |
| `ok=--`（该点本拍不可信）而值是 0 | **这就是最典型的静默失败**：0 kW 的负荷与"读失败"在协议上完全一样，只有这一列能分开。查 `block_fails`（通信/地址）vs `decode_fails`（映射表，尤其 32 位字序） |
| 数值离谱或 NaN | **32 位字序写反**。`MEAS.P_BAT` 刻意是低字在前（`BA`），其余 f32 是高字在前（`AB`）——这是**故意的区分度**（`13/docs/README.md` §2.3） |
| `block_fails` 一直涨 | 线 / 网关 / 从站地址 / 超时；先用 `--plan` 确认没发报文，再 `ping`、`telnet <ip> 502` |
| `decode_fails` 涨 | 映射表配错（字序 / NaN / 越界），**不是**通信问题 |
| 全部读到 0 且 `ok=--` | UnitId 不符（`--unit`）或表地址段不同 |

### S8 日志落盘与轮转（含"导出周期"的算式）

**先设定导出周期**，用算式算，不要拍脑袋：

```bat
python 19\src\log_rotator.py --root D:\EMS advise --rate 100 --capacity 4096
```

**期望输出**

```
== 不丢事件算式：导出周期 × 最大事件速率 < SoeLog::capacity ==
  事件速率        : 100 条/s
  SoeLog capacity : 4096 条
  不丢事件最大周期: 40.96 s
  建议周期(2倍余量): 20.48 s
```

**为什么需要这个算式**：P2 的 `SoeLog` 是**有界**的（默认 4096 条 ≈ 600 KB），
超出就**淘汰最旧**并累加 `dropped()`。导出周期太长 → 两次导出之间生成的事件数 > 4096
→ 最旧的事件**永久消失**，而且现象极具欺骗性：段里"有事件"、条数"正常"、程序"没报错"。

```
不丢事件条件：  T × r < C
  T = 导出周期（秒）
  r = 事件最大生成速率（条/秒，取**风暴峰值**不是均值）
  C = SoeLog::capacity（默认 4096）
现场留 2 倍余量：T ≤ C / (2r)
```

| 最大事件速率 r | 最大周期 T | 建议 |
| --- | --- | --- |
| 1 条/s（常态） | 4096 s ≈ 68 min | 30 min |
| 10 条/s | 409.6 s | 200 s |
| 100 条/s（风暴） | 40.96 s | 20 s |

> **`r` 的量级远小于"拍率"**：P2 的核心机制是边沿检测 + 时间窗抑制，
> 一次持续 838 拍的安全限幅只产出 **2 条**事件（`SAFETY_CLIP_START/END`）。
> 所以 `r` 由**事件跳变次数**决定，不由 10 Hz 控制周期决定。
> 现场第一次上电建议先用 **60 s**，跑一天后看 `dropped` 再收紧或放宽。

**现场侧的导出代码要这么做**（`ems_side` 已在进程内持有 `RuntimeObserver`，
接真实位号后按这个顺序加即可；**`reset()` 会清掉 `dropped` 计数，所以必须先读后清**）：

```cpp
// 每 T 秒执行一次（T 由上面的算式给出）
if (!write_file(batch_csv, obs.soe().to_csv())) { /* 报错，别静默 */ }
if (!write_file(batch_json, obs.soe().to_json())) { /* 报错 */ }
const size_t dropped = obs.soe().dropped();   // ★ 必须在 reset() 之前读
if (dropped) { /* 大声记一笔：这一批之前已经掉过事件 */ }
obs.soe().reset();                             // 清空已落盘的条目
```

落盘：

```bat
:: 把一批导出接进存储（csv 是事件，json 用来读 dropped）
python 19\src\log_rotator.py --root D:\EMS ingest --csv D:\EMS\log\soe_batch.csv --json D:\EMS\log\soe_batch.json --interval 60
```

**期望输出（正常）**

```
[INGEST OK] 追加 37 条（当前段 412 条 / 63401 字节）
  本批抑制合并 5 次（P2 时间窗机制，不是丢失）
```

**期望输出（掉过事件 —— 必须处理）**

```
  [LOST] ★ 本批导出时 SoeLog 已淘汰 128 条 —— 导出周期过长，事件已永久丢失
         按算式 T × r < capacity 收紧周期（见 log_rotator.py --help）
```

并且 CLI **退出码 2** —— 这样告警脚本能自动发现，不需要人去看中文。

**轮转与检索**：

```bat
python 19\src\log_rotator.py --root D:\EMS status
python 19\src\log_rotator.py --root D:\EMS query --from 1000 --to 2000 --level ERROR
python 19\src\log_rotator.py --root D:\EMS query --from 1000 --to 2000 --json > D:\EMS\log\q.json
```

**期望输出**（`status`）：

```
== soe 存储状态 ==
  目录            : D:\EMS\log\soe
  封存段 / keep   : 3 / 5
  当前段          : 412 条 / 63401 字节（阈值 2000 条 / 524288 字节）
  保留窗口        : t ∈ [0.0, 86399.9]

  最近导出间隔    : 60.0 s
```

**轮转规则**：**大小 512 KiB 或 条数 2000 条**（任一超出即封段），
保留 **5** 份封存段，多出来的**删最旧**。
`keep × 阈值` 就是保留窗口 —— **窗口外的历史会被删，这是设计意图**。
要留更久，把段在封段后归档到别处（`log\soe\soe_0001.csv` 是标准 CSV，直接搬）。

**失败排查**

| 现象 | 方向 |
| --- | --- |
| `保留窗口` 比预期窄 | `keep` 太小或阈值太小 → `--keep` / `--max-bytes` / `--max-entries` 调大；先看磁盘余量 |
| 查不到某条事件 | ① 先 `status` 看是否已超出保留窗口；② 确认查询区间的**端点写成十进制**（工具对浮点边界有 1 µs 容差，但如果区间本身写错就真的查不到） |
| `[LOST]` 出现 | 立刻把导出周期减半，并把这一批的 `dropped` 数记进运行日志 —— 那份"丢过事件"的记录是事故复盘的证据 |

### S10 接真实位号

**先接"位号"，再接"控制"。** 顺序反了会在还没有可信量测的时候下发控制量。

1. **量测先通（只读）**：把真实设备的量测接进点表，用 §4 的清单逐点核对。
   两条路选一条：
   - **RT_DB 路**（本指导书的默认形态）：设备侧进程（现在是 `device_side.exe` 的替身）
     换成"读真实 BMS/PCS/电表 → 写 `MEAS/STA/CFG`"的进程。**角色边界不能破**：
     设备侧只写 MEAS/STA/CFG、只读 CMD（`11/docs/README.md` §1）。
   - **Modbus 路**：用 `13/` 的 `ModbusDeviceIO` 直连设备；核对仍用 `modbus_probe.exe`。

2. **确认 EMS 读到的是**设备给的**值，不是点表默认值**：
   ```bat
   :: 看 EMS 侧日志：连上之后不该再有"设备侧未发布"之类的告警
   findstr /C:"FAIL" D:\EMS\log\ems_side.out.log
   ```
   **期望输出**：没有任何匹配行。
   > 这条不是走过场：EMS 在 `attach_device()` 时会立刻读一次 `CFG.*`；设备还没发布就读到
   > **点表默认值**（变压器 250 kVA），现场表现是"EMS 拿错误的一次侧参数算安全边界"。
   > 这正是 §3.10 的顺序约束 ③。2026-09-19 之前还只刷装配期那一次 —— 那等于把
   > BMS 动态降功率、禁充放位、PCS 额定全当常量用（`11/docs/README.md` §5.4）。

3. **再放控制**：确认量测可信后，把 EMS 的 `CMD.*` 接到 PCS。
   **调度侧的任何设定都不得绕过 `05/` 安全约束引擎**（`13/docs/README.md` §9 的共同纪律）。

4. **断链演练**（必做，见 §6.4）：拔网线 → 采集不可信 → FAULT → 指令归零；
   恢复 → 停 READY，**不自动带载**。

### S11 三条部署顺序约束（守护器已经替你处理，但你要知道它在处理什么）

| # | 约束 | 违反了会怎样 | 守护器怎么保证 |
| --- | --- | --- | --- |
| ① | **初始化器（`reset=true`）必须在所有连接之前** | `reset` 把整个段 memset（段级连接计数一起清零）→ "连接数与真实进程数脱节" | `rtdb_initializer` 最先启动，且**就绪**之后才启动下游 |
| ② | **初始化器不能"跑完就退"** | Windows 下段是页面文件支撑的文件映射对象，最后一个句柄关闭即销毁 → 段没了，下游继续跑只会读到死段（**进程活着但数据是错的**） | 把它当**常驻保活进程**；它一旦退出，**级联作废**全部下游并重起（`cascade_dirty`） |
| ③ | **EMS 侧要等设备侧先发布 `CFG.*`** | EMS 读到点表默认值（变压器 250 kVA）→ 拿错误的一次侧参数算安全边界 | `depends_on: ["device_side"]` + **就绪探测**（匹配 `device_side` 自己打印的 `[DEVICE] connected`），不用 `timeout /t 2` 猜时间 |

**就绪探测为什么不能退化成 `sleep`**：慢盘 / 冷启动 / 杀软扫描下"1 秒后设备就绪"不成立；
一旦不成立，EMS 读到错的一次侧参数，而**进程活着、日志干净、数据是错的**。
所以每个进程带一条 `ready_pattern`，命中**进程自己打印的横幅**才算就绪
（`[INITIALIZER] segment` / `[DEVICE] connected` / `[EMS] connected`）；
超时 → 判定**启动失败** → 按退避重启，**不"就当它好了"**。

### 4.1 核对方法

1. 读真设备一遍：`13\build\modbus_probe.exe --host <ip> --port <port> --unit <id>`

```
        ↓
④ 离线 24h    P1\build\ems_config.exe --apply conf\site.json --quiet
              P2\build\ems_observe.exe --fault 12                        → 事件成对
        ↓
⑤ 现场调参    （改了参数就回到 ③）
        ↓
⑥ 导出生效值  P1\build\ems_config.exe --capture conf\ems_config.json   ← 落"活文件"
              python 19\src\config_store.py --root <root> snapshot --note "…"

```

### 7.1 配置回滚（改坏了参数）

```bat
cd /d D:\EMS
python 19\src\config_store.py --root D:\EMS list          :: 找到要退回去的那版
python 19\src\config_store.py --root D:\EMS rollback v0007
python 19\src\config_store.py --root D:\EMS diff v0007 latest   :: 看清差了什么
```

**回滚之后必须重启 EMS 才生效**（`conf\ems_config.json` 是进程启动时读的）：

```bat
schtasks /End /TN EMS_Site_P5
schtasks /Run /TN EMS_Site_P5
```

**注意**：回滚只改 `conf\ems_config.json`。**点表 / 字序 / 设备侧参数不在里面**
（那是一次侧属性，EMS 只能读，见 `11/docs/README.md` §6）——
所以"改配置能修的问题"与"必须到设备上去改的问题"是两件事，别把回滚当成万灵药。

### 7.2 整机停止 / 重启

```bat
:: 正常停
schtasks /End /TN EMS_Site_P5
:: 正常起
schtasks /Run /TN EMS_Site_P5
:: 完全卸载（保留 conf/log）
cd /d D:\EMS\19\scripts

```

### 7.3 应急处置卡（**贴在机柜上**）

| 现象 | 先做什么 | 再看什么 |
| --- | --- | --- |
| EMS 完全没在跑 | `schtasks /Run /TN EMS_Site_P5` | `log\supervisor.log` 末尾 20 行 |
| 守护器在，worker 反复起 | `type log\device_side.out.log` | `ready_timeout` 行 → 设备侧起不来 |
| 出现 `cascade_dirty` | **当作事故处理** | 初始化器挂过，段被销毁过；查 `rtdb_initializer.out.log` |
| 指令下不去 / 功率不动 | 看是否停在 READY（`EMERGENCY`/`FAULT` 后需人工确认） | `ems_side.out.log` 的状态迁移链 |
| 通信中断告警 | **不要急着复位** | `COMM_LOST_*` / `HOLD_LAST_*` 是否成对；链路恢复后仍停 READY 是**预期** |
| 日志里 `[LOST]` | 把导出周期减半并重启 EMS | `status` 的 `dropped_seen`；把丢事件记录进运行日志 |
| 时钟跳变 | `w32tm /resync` | SOE 时间戳会跟着跳，先记下跳变时刻 |

**断链之后怎么办**（按顺序）：

1. **不手动复位** —— 先确认现场：开关位、设备面板、有没有人作业。
2. 看 SOE 是不是成对（`COMM_LOST_PCS` 有没有配对的 `COMM_RESTORED`）。
3. 链路恢复 → EMS 停在 READY（**不会自动带载**）→ 由运行人员确认后
   下发 `start_command`。
4. 把这次中断的 SOP 记录进运行日志（含起止时间、原因、处置人）。

### 7.4 "停机保命"（需要立刻让储能不带载）

1. `schtasks /End /TN EMS_Site_P5`（停守护器 = 三个 worker 一起收掉）
2. 用 PCS 本体的急停 / 就地控制把设备置到安全态
3. 记录：谁、什么时候、为什么、停之前的状态

> **顺序很重要**：先停 EMS（它就不下发新指令了），再用设备侧手段置安全态。
> 反过来做的话，EMS 可能在设备已置安全态之后**又下发一次指令**。

## 附：不丢事件算式的推导

`SoeLog` 的语义（`P2/src/soe.h`）：`push()` 时若 `entries_.size() > capacity`，
**从头部淘汰最旧**并 `++dropped_`。

设：
- `T` = 导出周期（s），两次导出之间不清空
- `r` = 该周期内事件的最大生成速率（条/s）
- `C` = `capacity`（默认 4096）

两次导出之间新增的事件数 `N = T × r`。

- 若 `N < C`：最旧的 `C` 条里仍包含窗口内的全部事件 → **一条不丢**
- 若 `N == C`：淘汰发生在"刚超出"的那一刻。第 `C+1` 条一进来，第 1 条立刻被淘汰 ——
  而这第 1 条**正是本窗口最早的那条**，它还没被导出 → **丢**
- 若 `N > C`：丢 `N - C` 条

所以判据是**严格小于**：`T × r < C`。现场取 2 倍余量：`T ≤ C / (2r)`。

**为什么 `r` 要用风暴峰值**：常态下 `r` 可能只有 0.01 条/s（几分钟一条事件），
而一次故障可能在 1 秒内产生十几条（置位 / 清除 / 迁移链）。
按均值设周期 → 平时没事，**一出故障就丢事件** —— 而故障时刻的日志恰恰是最贵的。

**怎么拿到 `r`**：`SoeLog::total()` 是累计 `push` 次数。
跑一天后 `r ≈ Δtotal / Δt`，取**最大**的那个小时。

> ★ **一个必须知道的细节**：`reset()` 会把 `dropped_` 一起清零。
> 所以现场侧必须 **先读 `dropped()` 再 `reset()`**，否则"上一批丢过事件"这件事
> 会**不留痕迹地消失** —— 而它恰恰是最需要留痕的东西。
> `19/src/log_rotator.py` 的 `ingest --json` 就是按这个顺序消费 `to_json()` 里的
> `summary.dropped`，非 0 时打印 `[LOST]` 并以**退出码 2** 收尾。
