# 12/docs/design.md — 验收设计说明

> 配套阅读：[`README.md`](./README.md)（怎么跑、报告怎么看）与
> [`ACCEPTANCE-REPORT.md`](./ACCEPTANCE-REPORT.md)（验收结论）。
> 本文只回答一个问题：**为什么验收要这样设计。**

---

## 1. 验收与测试的区别

同一个断言，放在 `tests/` 里叫测试，放在验收器里叫**判据**。区别不在代码，在**谁有权解释结论**。

| | 开发期断言（`01/`~`11/`） | 验收断言（`12/`） |
|---|---|---|
| 提问 | "我的实现符合我的意图吗？" | "交付物符合设计方案的字面要求吗？" |
| 判据来源 | 实现细节（内部变量、私有状态） | 公开出口（`StepRecord` / 点表 / 文件 / 墙钟） |
| 复核成本 | 需读源码才能核对 | 报告自带判据 + 实测，第三方可独立复核 |
| 阈值 | 无，或形如 `> 0` | **可量化**，且可被现场标定覆盖 |
| 失败含义 | 实现有 bug | 交付物不达标 |

因此 `12/` **不复用**上游的断言，只复用上游的**能力**。这是"验收通过"这句话
有意义的前提 —— **被验收的代码就是提交的那份代码**。

## 2. 三条设计原则

### 2.1 判据与实测必须同时输出

只输出 `PASS` / `FAIL` 的报告是**不可复核**的：读者无法判断这是"真通过"
还是"断言写错了"。所以每个检查项都是三元组：

```
编号    A3-07
判据    ramp_rate 约束 active=true 但 binds_interval=false 且 counts_as_derate=false
实测    binds=false, derate=false, margin=180.00 kW
```

判据是**人话**（不是表达式字符串），实测是**可独立验证的数值**。任何一项不通过，
都能被单独定位；任何一项通过，都能被质疑。

### 2.2 阈值集中在一处

所有可标定阈值都在 `AcceptanceRunner::Options`：

```cpp
double perf_mean_us_max  = 1000.0;   // 单拍均值上限
double perf_max_us_max   = 20000.0;  // 单拍峰值上限
double perf_duty_pct_max = 20.0;     // 单拍时间占用率上限（%）
double perf_speedup_min  = 2000.0;   // 24h 仿真墙钟加速比下限
// 以及 A5 的迁移次数 / 指令抖动上限
```

现场标定只改这一处，不改判据逻辑。**阈值散落在检查项内部是验收制度的头号敌人** ——
一旦散落，就会出现"为了让它过而调那个数"的暗改。

### 2.3 每条正向断言都要有反向守卫

只断言 `X 成立` 的验收是最容易假通过的：只要 `X` 恒真（例如两路都是 0），断言就永远绿。

以 **A1-05（三适配器等价）** 为例：

```
正向：SimDeviceIO 与 RtDbDeviceIO 的 P_bat / SOC 逐拍偏差 ≤ 1e-9
反向：峰值指令 > 50 kW（否则"两边都恒 0"也能满足正向）
反向：SOC 确实变化（否则"两边都卡死"也能满足正向）
反向：stale_reads() == 0（否则"读到的是陈旧缓存"也能满足正向）
```

**A4-04（资源无泄漏）** 同理：不只断言"句柄数没涨"，还断言"跑之前句柄数 > 0"
（否则计数器本身失效也会让它通过）。

## 3. 七个维度是**正交**的

维度不是按模块切的（那样会重复测同一个东西），而是按**问题类别**切的。
同一条能力可能被多个维度从不同角度测量 —— 这是刻意的：

| 能力 | 功能维度怎么看 | 其他维度怎么看 |
|---|---|---|
| 实时闭环 | A1-03：能跑 2000 拍，状态机走完七态 | A4-01/02/03 看耗时，A5-01 看硬不变量，A5-03 看抖动 |
| 安全引擎 | A3-01：9 条约束都被评估到 | A3-02~09 逐条注入，A3-09 单独盯"矛盾→DERATED" |
| RT_DB | A1-05：能读写、与另外两个适配器等价 | A5-04 看跨进程长稳 + stale 零 |
| 24h 仿真 | A1-08：能装载日计划 | A4-05 看加速比 + 经济净收益，A5-01/02/03 看长稳 |

如果某个能力只被一个维度测到，那它就是**验收盲区**。

---

## 4. 为什么落盘三件套（md / json / html）

- **md**：给人读。维度总览 + 逐项表格，能直接贴进交付邮件。
- **json**：给机器读。CI 抓 `summary.passed` / `summary.total` / `summary.result` 判门禁，
  不需要解析表格。**它是真的 JSON** —— T58 用 `P1/src/json_lite.h`
  这个**独立解析器**反解验证，不是自证。
- **html**：给汇报用。自带样式，双击即开，绿 / 红标色，不需要装任何东西。

三种渲染器共用同一个 `AcceptanceReport` 数据模型，因此**不可能出现三份报告口径不一致**。

---

## 5. 退出码是门禁的另一半

```bash
build/acceptance.exe --quiet --root .. || exit 1
```

- `0` = 全部通过
- `1` = 存在未通过项
- `2` = 参数错误

**报告可以给人看，但门禁必须机器可判。** 只出报告不设退出码的验收，
最终会退化成"定期跑一下、看一眼、都挺绿"。

---

## 6. 刻意的"不测"

| 不测 | 为什么 |
|---|---|
| 各模块**内部**实现细节 | 那是开发期测试的职责；验收看公开出口 |
| 文档**内容质量** | 靠评审，不靠脚本。脚本能做的只是让"忘了写文档"这件事无法悄悄发生 |
| 真实日曲线的经济性 | `09/` 的 7 个场景是抽样工况（暴露耦合缺陷），真实日曲线在 `10/` 的 24h 仿真里（A4-05 顺带跑了它并核对净收益） |
| 性能**绝对值** | 会随机器/负载变化。判据用"占控制周期的比例"，跨机可比 |

## 7. 目录结构

```
12/
├── src/
│   ├── acceptance_runner.h     7 个维度函数 + 报告模型 + 3 个渲染器（纯头文件）
│   └── main_acceptance.cpp     CLI：参数解析 → 跑 → 打印 → 落盘 → 退出码
├── tests/
│   └── test_acceptance.cpp     T51~T59：逐维度断言 + 报告自洽性 + JSON 独立反解
├── scripts/
│   ├── build.bat               编译验收器
│   ├── build_test.bat          编译 + 运行 T51~T59
│   └── run_acceptance.bat      正式验收（含落盘与门禁退出码）
├── docs/
│   ├── README.md               怎么跑 / 报告怎么看 / 三个验收结论 / 已知限制
│   ├── design.md               本文件
│   └── ACCEPTANCE-REPORT.*     验收报告（运行后生成）
├── data/
│   ├── README.md               目录说明
│   └── _report_selftest/       A7-06 自检产物（可删，会自动重建）
└── build/                      编译产物
```
