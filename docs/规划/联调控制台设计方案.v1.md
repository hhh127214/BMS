## 0. 一页速览

### 0.1 结论

**有必要做，但只能做成「控制台（Console）」，不能做成「第二个仿真器」。**

网页 = 面板 + 显示器。物理模型、策略、安全链**一行都不重写**。

### 0.2 三张表

| 为什么必要 | 证据 |
|---|---|
| **一次侧参数根本没有注入口** —— 改工况 = 改源码重编 | `11/src/integration_runner.h` `struct DeviceSimConfig` 共 **18** 个字段全是编译期默认值；`11/src/main_device.cpp:40-52` 命令行只认 `--steps / --dt / --speed / --fault / --report` |
| **已实测的工况对比是死证据**，复现一次要重编 | `11/docs/README.md` §6 的 4 组工况（250/800/1200/1000 kVA × 250/450/500/600 kW） |
| **§7.1 的 L2 极限环是"未修、只留证在文档"的缺陷** | `11/docs/README.md` §7.1 —— 有人质疑时你得当场跑出来给他看 |
| **结果只有 txt，无曲线、无法与上一组对比** | `11/scripts/run_integration.bat:52-55` 两份 `type` 出来的报告 |

| 做什么 | 不做什么 |
|---|---|
| 网页只做：编辑工况 → 触发内核 → 呈现结果 | 不在网页里重写物理模型 / 策略 |
| 复用 `DeviceSideSim` / `EmsSideApp` 的 `step()` | 不引入新的仿真内核 |
| 结果落 CSV/JSON，一次性拉取 | 不做 WebSocket 逐拍推送 |
| 默认单进程顺序驱动（快） | 不追求毫秒级实时曲线 |
| `DeviceSimConfig` 加 JSON 加载口 | 不改任何现有语义（缺省 = 原默认值） |

| 阶段 | 交付 | 可否独立停 |
|---|---|---|
| **P0** | `console_runner.exe --config x.json --out r.csv` + 单文件 HTML 面板 | ✔ 用完即止也值 |
| **P1** | 三进程真并发开关 + 故障时间轴拖拽 + 多工况并排对比 | ✔ |
| **P2** | 点表/映射配置化（推 C5）+ 接 `13/` Modbus + 无段快速模式 | ✔ |

## 1. 定位：控制台 vs 第二个仿真器（**本文最关键的一节**）

两条路的差别不在工作量，在**结论可不可信**。

```
参数面板（浏览器）
      │
      ├─── A：在网页里重写一套 JS 物理模型 + 策略
      │        └─► 第二份真相 ─► 跨进程缺口永久测不到 ─► 与 9276 基线脱钩
      │
      └─── B：生成 scenario.json，喂给现有 C++ 内核            ★ 本方案
               └─► 复用 DeviceSideSim::step() / EmsSideApp::step()
                    └─► 与 T41~T49 同一份代码 ─► 结论可回填成断言
```

**为什么 A 会"永久测不到"**：本项目已经踩过三次同一类缺口 ——
① `CMD.P_UPPER/P_LOWER` 从未被发布（§5.1）、② seqlock 碰撞被误计为采集失败（§5.2）、
③ 设备限值运行期冻结（§5.4）。三条的共同点是：**三层测试全绿，只有跨进程/并发才暴露**。
一个跑在浏览器里的单进程 JS 模型，会把这类缺口从"难发现"变成**不可能发现**。

**为什么 B 的结论可信**：`11/docs/README.md` §2 明确作保 ——
单进程形态（T41~T49）与三进程形态跑的是**同一份** `DeviceSideSim::step()` /
`EmsSideApp::step()`，这是"单进程结论能外推到多进程部署"的根据。控制台复用它，
得到的结论与现有断言同源。

### 1.1 三条硬边界（写进代码注释，违反即视为缺陷）

1. **内核唯一**：任何物理量/策略的算式，只允许存在于 `04/`~`08/` 与 `11/`。
   `14/` 里不允许出现第二个 `p_grid` 定义、第二个 SOC 积分、第二个安全约束。
2. **点名不出现在网页层**：网页传的是 `device.transformer_kva` 这种**业务键**，
   不是 `CFG.TR_KVA`。点名只出现在适配器里（P0 纪律）。
3. **缺省即默认**：`scenario.json` 里没写的字段 = 沿用编译期默认值
   → 现有工况**逐位不变**，9276 断言不受影响。这条是"不破坏基线"的保证。

### 2.2 三种内核形态（P0 只做第一种）

| 模式 | 适配器 | 共享段 | 并发 | 墙钟 | 语义 |
|---|---|---|---|---|---|
| **`rtdb`**（P0 默认） | `RtDbDeviceIO` + `DeviceSideSim` **顺序驱动** | 需要 | 单实例 | 秒级 | 走 RT_DB 点表路径，与三进程**同一份 step()** |
| `proc`（P1） | 同上，但真三进程 + `Pacing` | 需要 | 单实例 | 15 s 起 | 最真，能照 seqlock 那类并发缺口 |
| `fast`（P2 可选） | `MemoryDeviceIO` 直连 | 不需要 | 可多会话 | 最快 | **不走点表路径**，页面须显著标注 |

> **为什么 P0 默认 `rtdb` 而不是 `fast`**：`fast` 绕开了点表，等于把 A1/A2 那类
> "写了但某条路径上不生效"的缺口（§10.4 D4）重新藏起来。控制台要的是可信结论，
> 不是最快结论。只有当 T21/T25 的适配器等价性断言持续全绿时，`fast` 才值得开。

### 2.3 `rtdb` 模式的装配顺序（**顺序错了会静默跑错**）

```
① 建段（复用 07/src/rtdb/ems_rt_db_setup.c，保留存活句柄）
② DeviceSideSim dev(&h, script)
③ dev.step(0, dt)          ← ★ 必须先发布一次 CFG.*
④ EmsSideApp app(&h, cfg)  ← 构造时 attach_device() 会读 read_limits()
⑤ 循环 N 拍：dev.step(t, dt) → app.step(dt) → 落一行 CSV
```

第 ③ 步不能省：`11/docs/README.md` §2.1-3 踩过 —— 设备还没发布 `CFG.*` 时
EMS 读到的是**点表默认值**（变压器 250 kVA），安全边界全错。
（`rtdb` 模式下**不能**调 `app.wait_for_device()`——那是等多进程发布的，单进程会死等到超时。）

## 3. 数据契约

### 3.1 输入 `scenario.json`

四组。**全部可选**，缺省即编译期默认值（`json_lite` 的 `number(default)` 正好表达这一点）。

```jsonc
{
  // ---- 标识：用于结果归档与"结论回填成断言" ----
  "id": "baseline",
  "note": "联调基准：1000 kVA / 600 kW 需量，无故障",

  // ---- ① 运行控制 ----
  "run": {
    "mode": "rtdb",      // rtdb（P0 唯一可用）| proc（P1）
    "steps": 600,
    "dt": 0.1,
    "speed": 4,          // ★ 仅 proc 模式生效；rtdb 模式忽略
    "log_every": 1
  },

  // ---- ② 一次侧参数（DeviceSimConfig，18 项）----
  "device": {
    "battery_capacity_kwh": 1000,
    "pcs_max_chg_kw": 200,
    "pcs_max_dis_kw": 200,
    "bms_chg_limit_kw": 200,
    "bms_dis_limit_kw": 200,
    "transformer_kva": 1000,     // ← §6 四组工况的变量 1
    "demand_target_kw": 600,     // ← §6 四组工况的变量 2
    "tau_s": 0.5,
    "ramp_kw_per_s": 400,
    "standby_kw": 2,
    "eta_chg": 0.95,
    "eta_dis": 0.95,
    "soc_phys_min": 0.05,
    "soc_phys_max": 0.95,
    "temp_ambient_c": 25,
    "temp_heat_coef": 0.0006,
    "temp_cool_coef": 0.002,
    "meter_bias_kw": 0           // ← 缺口 A2 的判据注入点（T49 用 +40）
  },

  // ---- ③ EMS 侧场景约束（EmsSideApp::Config）----
  "ems": {
    "grid_p_min_kw": -1e9,       // ← 防逆流 S05 的命门
    "grid_p_max_kw":  1e9,
    "ramp_kw_per_s":  1e9,
    "use_forecast": true
  },

  // ---- ④ 剧本（DevFaultWindow[]）----
  "script": [
    { "kind": 4, "t_begin_s": 20, "t_end_s": 25 },   // PCS 故障
    { "kind": 8, "t_begin_s": 30, "t_end_s": 35 }    // BMS 禁放（非故障）
  ]
}
```

`kind` 取值（`11/src/integration_runner.h`）：

| kind | 含义 | 性质 |
|---|---|---|
| 1~6 | BMS通信断 / 电表通信断 / PCS通信断 / PCS故障 / 设备离线 / 品质位劣化 | **故障**（计 `comm_fault_ticks`） |
| 7 / 8 | BMS 禁充 / BMS 禁放 | **正常上报的运行限值**，不是故障（`11/docs/README.md` §4.1） |

> ★ 面板上必须把 1~6 与 7/8 **分成两组显示**，否则用户会以为"置了故障"。
> 这两类走的是不同链路（7/8 → `read_limits()` → S01 → `05/` 收区间），语义完全不同。

### 3.2 加载期校验（**fail fast，禁止静默截断**）

手填参数必然出现非物理值。加载时校验，**不通过就退出并给出 `文件:字段:原因`**：

| 校验 | 原因 |
|---|---|
| `soc_phys_min < soc_phys_max`，且都在 [0,1] | 反了会让 SOC 区间为空 |
| 容量 / 额定 / 需量 > 0 | 负值会让安全约束算出荒谬区间 |
| `eta_*` ∈ (0,1] | 效率 >1 会造能量 |
| `script` 窗不重叠同 kind、`t_end > t_begin`、窗不超出 `steps*dt` | 窗超出 = 剧本根本没发生（**静默**） |
| `steps*dt` 与 `speed` 算出的墙钟有上界 | 防浏览器请求挂死 |

> 这条是项目纪律的直接延伸：**静默失败是头号敌人**。宁可拒绝运行，也不给一个看起来正常的错误结果。

### 3.3 输出 `result.csv`

逐拍一行。列 = `StepRecord`（`07/src/realtime_loop.h`）19 字段 + 3 个派生列：

```
t, state, p_load, p_pv, p_grid, p_cmd, p_actual, soc, temp,
p_lower, p_upper, plan_target, correction,
clamped, safety_clip, state_gated, hold_last, fault_bits, reason,
bms_chg_forbid, bms_dis_forbid, ext_active
```

| 派生列 | 来源 | 为什么必须逐拍 |
|---|---|---|
| `bms_chg_forbid` / `bms_dis_forbid` | `rt().device_limits()` | 这两位是**事件型**通路，只看末态无法区分"通路断了"与"窗口过去了"（§4.1 的教训） |
| `ext_active` | `rt().last_verdict().ext_active` | A3.2 外部设定是否生效 |

- `state` 用 `fsm().state_str()` 的字符串，不存枚举值（可读性 + 前端直接上色）。
- `reason` 含逗号 → **必须加引号转义**，放在最后一列。
- 86400 拍 × 22 列 ≈ 6 MB，可接受；前端画图**降采样**（>2000 点时按拍抽稀，但状态跳变点与故障窗边界**不得被抽掉**）。

### 3.4 输出 `checks.json`

```jsonc
{
  "id": "baseline", "mode": "rtdb", "wall_s": 1.24, "steps": 600,
  "scenario": { /* 原样回灌，保证结果可复现 */ },
  "checks": [
    { "phase": "通信建立", "name": "一次侧参数来自设备侧 CFG（非点表默认）",
      "pass": true, "evidence": "tr=1000 kVA" }
  ],
  "summary": { "pass": 9, "total": 9 },
  "device_stats": { "steps": 600, "cmd_peak_kw": 187.3,
                    "out_of_interval": 0, "failsafe": 0,
                    "fault_ticks": 50, "bms_forbid_ticks": 50 },
  "soe": [ { "t": 20.1, "code": "PCS_FAULT_SET" }, { "t": 25.0, "code": "PCS_FAULT_CLEAR" } ]
}
```

检查项直接沿用 `11/src/integration_runner.h::IntegrationCheck`
（`phase / name / pass / evidence`），与 `11/` 联调检查单**同一套口径**，不另起炉灶。

## 4. 内核改动清单（逐文件）

**原则：只加不改。** 现有文件里唯一需要动的是 `DeviceSimConfig`——
给它加一个"从 JSON 覆盖默认值"的函数，而不是改默认值本身。

| # | 文件 | 改动 | 为什么 |
|---|---|---|---|
| 1 | `11/src/integration_runner.h` | 新增 `inline bool load_device_sim_config(const json::Value&, DeviceSimConfig&, std::string* err)` | 18 个字段逐个 `number(默认值)`；**缺省即默认** |
| 2 | 同上 | 新增 `load_ems_side_config(...)`（4 字段） | `grid_p_min_kw` 是防逆流命门，同样没有注入口 |
| 3 | 同上 | 新增 `load_fault_script(...)`（数组） | 命令行 `--fault` 只能由 bat 传，网页传不了 |
| 4 | `14/src/main_console.cpp` | **新文件**：§2.3 的装配顺序 + 逐拍落 CSV + 输出 checks.json | 新外壳，零模型 |
| 5 | `14/scripts/build.bat` | **新文件**：照抄 `11/scripts/build.bat` 的 `INC` / `RTDBOBJS`，追加 `-I ..\P1\src` | 复用既有编译配置 |
| 6 | `14/scripts/build_test.bat` | **新文件**（P0 可留空壳，但**必须存在并挂进 build_all**） | D2 纪律 |
| 7 | `scripts/build_all.bat` | 追加第 **32** 步，并把 1/31…31/31 的分母同步改成 32 | D2：不挂进去就是下一个 `lvrt_agent` |

编译命令（照 `11/scripts/build.bat:33-46`，仅追加 `-I ..\P1\src`）：

```bat
set INC=-I src -I ..\04\src -I ..\05\src -I ..\06\src -I ..\07\src -I ..\08\src ^
        -I ..\P2\src -I ..\07\src\rtdb -I ..\07\vendor\rt_db -I ..\P1\src
set RTDBOBJS=build\rt_db_api.o build\ems_point_table.o build\ems_rt_db_setup.o
g++ -std=c++17 -Wall -O2 %INC% src\main_console.cpp %RTDBOBJS% -o build\console_runner.exe
```

> `-I ..\P1\src` 是为了 `#include "json_lite.h"` —— **项目自带**的最小 JSON 解析器
> （`P1/src/json_lite.h`，纯头文件、支持 `//` `#` `/* */` 注释、尾逗号、裸键、
> 出错带行:列）。**不引入 nlohmann/json**，保持零第三方依赖。

### 5.2 预设工况（**本方案最有价值的部分**）

把 `11/docs/README.md` 里的死证据做成一键可复现：

| 预设 id | 关键参数 | 预期（页面直接显示判据） | 来源 |
|---|---|---|---|
| `baseline` | 1000 kVA / 600 kW | 末段平均跟踪误差 ≈ 0，指令跳变 0/200 | §6 基准工况 |
| `limit_cycle` | **800 kVA / 450 kW** | 跳变 **163/200**、平均误差 **40.7 kW** | §6 + §7.1（**未修缺陷**复现） |
| `small_transformer` | 250 kVA / 250 kW | 变压器过载常驻 → NORMAL/DERATED 抖动 | §6 |
| `meter_bias` | `meter_bias_kw = 40` | `p_grid` = 三路平衡值 **+40**，逐拍成立 | T49 口径 |
| `bms_forbid_dis` | script kind 8 @ [30,35) s | 窗内 **0 拍放电**、`p_upper ≤ 0` | T48 口径 |
| `pcs_fault` | script kind 4 @ [20,25) s | FAULT + 设备侧 `failsafe > 0` | T44 口径 |

`limit_cycle` 这类"故意设成非物理/不合理工况"的预设，页面标注
**「这是缺陷复现工况，不是设计工况」** —— 否则它会反过来被人当成"EMS 会振荡"的证据。

## 6. 分阶段（每阶段可独立停）

## 7. 验收口径（怎么证明它没骗人）

### 7.1 逐位回归（最硬的一条）

**空 `scenario.json`（全缺省）跑出的 `result.csv`，必须与现有 `11/` 单进程形态
同参数结果逐位一致** —— 判据：`max|Δp_cmd| = max|Δp_actual| = max|Δsoc| = 0`。

不成立就说明 `load_*` 偷偷改了默认值，或有字段漏了默认值分支。

### 7.2 预设工况判据必须全绿

§5.2 六个预设的"预期"列全部成立。这不是"跑通了"，是"跑出了该有的结果"——
区别在 A2 的教训：**先造出能区分对错的可观测差异，再谈修好**。

### 7.3 反向守卫（证明检查单有区分度）

故意把 `transformer_kva` 设成 **250**（点表默认值），
检查项「一次侧参数来自设备侧 CFG（非点表默认）」必须 **FAIL**。

> 没有这条，检查单可能在"参数压根没生效"时也 vacuously 通过 ——
> 与 §10.1 A1 的"恒 false 也能全绿"是同一个陷阱。

### 7.4 结论可回填（**防止它沦为演示玩具**）

至少 1 个预设工况落成 `14/tests/` 的断言用例（建议 `limit_cycle` 与 `meter_bias`，
两者都有明确数值判据）。

**这条不做，整个控制台就与 9276 基线脱钩** —— 那比不做更糟：
脱钩的演示会给人"这个工况没问题"的错觉，而 §7.1 的极限环现在正是这个状态。

每条给证据与归属。**最严重的是 G2，它要求改架构，不只是补字段。**

### 9.1 G2 展开：这是架构问题，不是补字段

```
现状（割裂）：
   P1/data/ems_config.json ──► config_loader ──► EmsRuntime     ← 算法参数这条路
   11/ EmsSideApp::Config（硬编码 6 字段）──► EmsRuntime        ← 联调这条路
                    ↑
              两者互不相通：联调里 P1 的 safety/coordinator/loop/strategies
              一律用**结构体默认值**，改 ems_config.json 对联调毫无影响。
```

本文原方案的 `scenario.json` 是**第三套 schema** —— 这正是要避免的。修正方向：

```jsonc
{
  "id": "...", "note": "...",
  "run":   { /* 运行控制，14/ 自有 */ },
  "device":{ /* DeviceSimConfig 18 项 —— 11/ 特有，保留 */ },
  "ext":   { /* G4：外部设定注入 */ },
  "ems_config": { /* ★ 直接嵌 P1 的完整 schema，不另起一套 */
     "loop": {...}, "plant": {...}, "limits": {...}, "safety": {...},
     "coordinator": {...}, "state_machine": {...}, "strategies": {...}
  }
}
```

**为什么必须嵌而不是自己定义**：P1 已经定义了 9 大组、60+ 个键，且带校验与
`--dump-doc` / `--dump-schema`。重新定义一遍 = 第二份真相（§1 的纪律），
而且两套 schema 会立刻开始漂移。

> ⚠️ **G2 引出一个必须核实的问题**：`11/` 联调与 `P1` 两路的**默认参数是否已经一致**？
> 目前未验证。若不一致，则"P1 里跑通的结论"与"11/ 联调跑出的结论"不可互相外推 ——
> 这本身就是一条待查缺口，与 §10.4 D4（"写了但某条路径上不生效"）同型。

### 9.2 G3 的一个修正：死区**已经默认启用**，但压不住极限环

原以为 §7.1 的极限环是因为"死区没启用"。核实后**不是**：

| 项 | 默认值 | 证据 |
|---|---|---|
| `LoopConfig::output_deadband_kw` | **2.0**（已启用） | `07/src/realtime_loop.h:142` |
| `LoopConfig::output_switch_delay` | **3**（已启用） | `07/src/realtime_loop.h:143` |

`11/` 的 `EmsSideApp::Config` 不含这两项 → 沿用默认 → **死区是开着的**。
所以 §7.1 那 163/200 次跳变是**在死区生效的情况下**发生的。

**这反而加固了"§7.1 是真缺陷"的判断**：根因在 `DemandMgmtStrategy` 的 `p_pred_avg`
含本拍指令自身反馈（正反馈 + 1 拍延迟），幅值 40.7 kW 远超死区能压住的小信号范围。
控制台要覆盖它，必须能开**对照实验**：

| 实验组 | 调整 | 目的 |
|---|---|---|
| A（现状） | 默认 | 163/200 跳变、40.7 kW（基线） |
| B | `coordinator.enable_correction = false` | 验证根因确在 L2 纠偏 |
| C | `loop.output_deadband_kw` 调大 | 验证死区能压到什么程度 |
| D | `strategies.S04_DEMAND_MGMT.enabled = false` | 隔离策略，确认归因 |

> ★ 这才是控制台真正的价值：**不是"能跑"，是能做受控对照实验。**
> 而 A/B/C/D 四组实验现在一组都做不了（都要改源码重编）。

### 9.3 G9 为什么不做单步/暂停/回退

会诱导出一个假的交互语义：EMS 是**硬实时闭环**（100 ms 节拍），暂停后再继续
不等于"中间什么都没发生" —— 设备侧的物理积分、SOC、热模型都在继续，而控制台
把它们冻住了。那是一个**在真实系统里不存在的状态**，结论不可外推。

要"看清楚某一拍"，正确做法是**跑完再定位**（曲线 + 状态带 + SOE 表），
或者**缩短窗口重跑**（改 `run.steps`），而不是暂停。
