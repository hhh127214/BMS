## 3. 上行：数据怎么放到 RT_DB

### 3.1 一次写入包含 4 个要素

RT_DB 的一个 `DataPoint` 是 `{value, quality, sequence, timestamp, point_id, units}`。
所以"放数据"从来不只是放一个数：

| 要素 | 谁提供 | 说明 |
|---|---|---|
| **值** | 设备侧 | 物理量本身 |
| **品质位** | 设备侧 | `QUALITY_BAD/GOOD/UNCERTAIN`。**EMS 侧会因为品质位异常判定数据不可信**，所以模拟器必须会发坏品质（11/ 的 `kind=6` 剧本就是干这个） |
| **时标** | 段自动打 | 写入时刻，`rt_db_get_value` 可带出 |
| **点名 / 单位** | 建段时一次性写 | 元数据，`rt_db_get_point_info()` 读 |

### 3.2 写入 API（`07/vendor/rt_db/rt_db_api.h`）

```c
bool   rt_db_set_value(rt_db_handle_t* h, size_t index, double value, long quality);
bool   rt_db_set_multiple_values(rt_db_handle_t* h, const size_t* idx, size_t n,
                                 const double* vals, const long* quals);   // ← 未被使用
size_t rt_db_find_index_by_id(const rt_db_handle_t* h, const char* point_id); // 字符串→索引
```

工程纪律：**热路径按索引写，不按点名写**。点名查找是字符串比较，
`RtDbPointWriter::write(index, ...)` 与 `write_by_name()` 两个重载同时存在，就是给这两种场合分家的。

### 3.3 点表谁建 —— 这是 RT_DB 的一个硬约束

RT_DB 自己**没有"注册点表"的公开 API**（`build_index_map()` 里把 `config_path` 直接丢弃了）。
所以点表必须由调用方在装配阶段写进段：

```
07/src/rtdb/ems_point_table.h      点表真相源（40 点：点名 + 单位 + 默认值）
        │
        ├─► ems_rt_db_setup.c      建段 + 逐点注册 + 保留只读存活句柄
        │                          （11/src/main_initializer.cpp 调用，进程常驻）
        │
        └─► 07/src/memory_device_io.h :: mem_point
                                   进程内等价物，点名**逐字相同**
                                   → 两个适配器可以互相做对照测试
```

### 3.4 全点表会带来三个新问题（**目前未解决**）

现在的 40 点表每拍**全量重发**没问题（约 40 次写），但"BMS 全点表"可能是几百到几千点：

| 问题 | 为什么出现 | 可选做法 | RT_DB 是否已支持 |
|---|---|---|---|
| **批量写** | 逐点写要 2000 次函数调用 + 2000 次 seqlock | `rt_db_set_multiple_values()` 一次写一批 | ✅ API 已存在，**项目未用** |
| **变化上传（死区）** | 大多数点每拍几乎不变，全量上传是纯浪费 | 设备侧维护影子副本，只在 `\|Δ\|>死区` 时写 | ❌ 需自己实现 |
| **采集节拍分级** | 单体电压不需要 100 ms，SOC 需要 | 快慢两档：安全相关 100 ms，诊断类 1 s / 10 s | ❌ 需自己实现 |

> RT_DB 的 `MAX_DATA_POINTS = 20000`，注释里写着"覆盖储能 7300、光伏 10000、风电 11000 系列指令输出"
> —— 容量上完全放得下全点表，问题只在**刷新策略**。

### 3.5 段的生命周期（Windows 独有的坑，已踩过）

- 段是**页面文件映射对象**，最后一个句柄关闭 → 段销毁。所以初始化器**不能做成"跑完就退"的短命进程**。
  这就是 `rtdb_initializer.exe --seconds 60` 的意义（Linux 上用 `shmget` 无此约束，极易漏）。
- `rt_db_init()` 里若走了 `reset` 分支会 `memset` 整段（连接计数被清零）→ **初始化器必须在所有连接之前跑**。
- **一个进程一条连接**（create/open 共用进程级全局句柄）→ 适配器一律**借用** `rt_db_handle_t*`。

## 4. 下行：指令怎么发给被控对象

### 4.1 ★ 这里有一个"现成但从未启用"的机制

RT_DB 其实提供了**两条**下行路径。项目只用了第一条。

| | **路径 ① 点表写值**（当前唯一在用） | **路径 ② 指令环形队列**（RT_DB 自带，**零调用**） |
|---|---|---|
| API | `rt_db_set_value(h, CMD_P_BAT, ...)` | `rt_db_push_command(h, &ControlCommand{...})`<br>`rt_db_pop_command(h, &cmd)` |
| 载体 | 段里的 3 个 `DataPoint` | `CommandRingBuffer`，**256 槽**（`COMMAND_QUEUE_SIZE`） |
| 目标寻址 | ❌ 无。靠点位语义约定"`CMD.P_BAT` 就是那台电池" | ✅ `device_id[64]` 显式指定目标 |
| 指令类型 | ❌ 无。一个 double 的含义靠点名区分 | ✅ `command_type` 显式区分（有功/无功/启停/模式…） |
| 优先级 | ❌ 无 | ✅ `priority` |
| 下发时刻 | 段自动打的写入时刻 | ✅ `issue_time` 由发送方给（可表达排队延迟） |
| 队列语义 | ❌ 值被覆盖，只保留最后一拍 | ✅ 环形缓冲，**指令不会因为"没被及时读走"而丢失** |
| 多设备 | 每个目标要单独加点（10 台 PCS 就要 10×3 点） | 一条队列服务所有设备，按 `device_id` 分发 |
| 何时必须用 | 单机单 PCS — 够用 | 多 PCS / BMS 也要接收指令 / 指令不能丢 / 要审计"谁在什么时候发了什么" |
| 本项目状态 | ✅ 已用（`RtDbDeviceIO::write_command()`） | ❌ **`grep` 全仓只有 vendor 里的声明，零调用** |

**建议**：不必现在就切到路径 ②。但要知道它存在，并明确一条边界 ——
**"稳态有功调度走路径 ①（快、幂等、值语义正好），需要目标/类型/优先级/不丢的指令走路径 ②"**。

### 4.2 指令下行的三层确认链

```
第 1 层  EMS 发布            write_command(cmd)  →  段里 CMD.P_BAT / P_UPPER / P_LOWER
         （为什么 P_UPPER/P_LOWER 也要发：设备侧要按 EMS **自己声明的**区间做交叉校核）

第 2 层  设备侧接收         读 CMD.*（或从队列 pop）
        ＋交叉校核           if (cmd < lo || cmd > hi) ++cmd_out_of_interval;
                            ★ 这个"设备侧检查 EMS 有没有自相矛盾"的设计，接真机时同样要保留

第 3 层  执行机构            物理积分（仿真）／写寄存器 + 回读（真机）
                            execute() 返回值**不可信**，闭环走下一拍 read_snapshot()
```

> 路径 ① 的"不可信返回值"这条纪律（`04/src/device_io.h` 契约 ③）是从真机上抽象出来的，
> 所以在模拟器里也必须保持 —— 否则仿真跑得很顺，接真机就崩。

### 4.3 从设备侧到真实 PCS（🟡 **机制已通**，缺真实设备）

```
device_side.exe  ──►  Modbus TCP/RTU 主站  ──►  PCS 寄存器
                     ├─ 写：有功设定 / 无功设定 / 启停 / 模式
                     ├─ 写后回读校验（写不进去要能发现）
                     └─ 读：功率反馈 / 状态字 / 故障码
```

这是 P0 文档里明确标注的"**当前唯一真正的功能缺口**"（`docs/产品化/P0-架构分层.md` §3.3）。

## 5. 点位清单：EMS ↔ BMS / PCS / 电表

### 5.1 下行：EMS 该发什么

| 目标 | 现在发的（40 点表） | 全点表通常还需要的 |
|---|---|---|
| **PCS** | `CMD.P_BAT`（有功设定）<br>`CMD.P_UPPER` / `CMD.P_LOWER`（EMS 自声明的允许区间） | **无功指令**、运行模式（并网/离网/待机）、启停命令、变化率设定、限功率使能 |
| **BMS** | ❌ **一个都没发** | 一般 EMS **不直接控制 BMS**；只需要**接收** BMS 的"允许充放/禁充禁放"。若要做远端均衡/维护，才需要下行通道 |
| **电表 / 光伏 / 变压器** | ❌ 无 | 光伏逆变器：限功率（防逆流场景）；变压器：无（只读） |

### 5.2 上行：EMS 该取什么

**BMS**

| 类别 | 现在（40 点表） | 全点表通常包含 |
|---|---|---|
| 能量状态 | `MEAS.SOC`、`MEAS.SOH` | SOC / SOH、剩余可充/可放电量、循环次数 |
| 簇 / 单体 | — | 簇电压电流、**单体最高/最低电压及其编号**、最高/最低温度及其编号、压差、温差 |
| **允许/禁止** | — | **允许充电 / 允许放电**、允许充放电流、允许充放功率 ← **安全链最关键的一类** |
| 接触器 | — | 主正/主负接触器、预充继电器、断路器状态 |

### 5.3 抽象表 vs 全点表 —— 建议做**两层点表**

这是本文最重要的一条架构建议：

```
第 1 层：设备全点表（RT_DB 段里，几百~几千点）
        MEAS.BMS_01.CELL_V_MAX / MEAS.PCS_01.UA / MEAS.METER_01.EP_FWD ...
        ↑ 忠于厂家/协议点表，可以由协议层自动生成
        │
        ├── 协议适配层（Modbus / IEC104 / 自有）
        │
第 2 层：EMS 抽象视图（现在的 40 点表 / 业务结构体）
        RealtimeSnapshot / DeviceLimits / DeviceStatus / PowerCommand
        ↑ 算法只认这一层；点名不许出现在算法里（P0 纪律）
```

现在只有第 2 层，第 1 层直接不存在。**"BMS（全点表格式）"要的就是第 1 层。**
两层之间必须有一个显式的映射表，否则"某个单体过温"这种信息永远进不到 EMS。

## 6. 模拟器：要开发什么

### 6.1 模拟器矩阵

| 模拟器 | 现在有什么 | 目标 | 优先级 |
|---|---|---|---|
| **BMS** | 6 点（SOC / T_C / SOH / 通信位） | 全点表（簇/单体/允许充放/接触器/绝缘/告警）+ 单体级异常注入 | **高**（安全链依赖） |
| **PCS** | 3 点（P_BAT / 通信 / 故障）+ 完整的物理积分（惯性/死区/变化率/效率/fail-safe） | 全点表（有功无功/模式/状态字/故障码/三相电量），物理模型直接复用 `MemoryDeviceIO` | **高** |
| **电表** | `integration_env()` 里两个 `sin()` 捏出来的数 | 三相全电量 + 电能累积 + 需量 | **中**（防逆流 / 需量策略的价值全在这上面） |
| **光伏逆变器** | 含在 env 里 | 独立点表 + 限功率 + 通信中断 | 中 |
| **变压器温控** | 只是一个常数 `CFG.TR_KVA` | 油温/绕组温度/负载率点表 | 低 |
| **负荷** | `integration_env()` 的 300 s 周期波形 | 可配日曲线（`10/src/day_curves.h` 已有 96 点日曲线能力，可直接搬） | 低 |

> 现成的物理模型**不要重写**：`07/src/memory_device_io.h` 已经有 PCS 的惯性/死区/变化率/效率/
> fail-safe + 热模型（`set_thermal_model()`），`11/src/integration_runner.h::DeviceSideSim`
> 已经把它包装成"会写共享内存的设备进程"。**新增全点表 = 在这套之上加一层点位映射，不是另起炉灶。**

### 6.2 Python 版模拟器 —— 一个必须先定的架构决策

你说的"python 发数据"。难点在于：**Python 不能 `#include` C 头文件**，
而 RT_DB 的段是一整块 `SharedMemorySegment` 结构体的内存镜像。三条路：

| 方案 | 怎么做 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **(a) ctypes 调 DLL** | 把 `rt_db_api.c` 编成 `rt_db.dll`，Python 用 `ctypes` 调 `rt_db_set_value` 等 | 复用官方实现，零布局风险 | 要做 DLL 导出；结构体布局仍要对（`struct` 手动对齐） | 可选 |
| **(b) Python 复刻 `mmap` 布局** | 用 `mmap` + `struct` 逐字段复刻 `SharedMemorySegment` | 纯 Python，无编译 | **最脆**：`atomic_double`、`struct timespec`、指针大小、段名/大小必须逐字节一致；任一平台差异就静默出错 | 不推荐 |
| **(c) 走 Modbus TCP**（推荐） | Python 起 `pymodbus` 从站，EMS 侧写 `ModbusDeviceIO` 主站 | **与真机走同一条路**，语言无关，`pymodbus` 成熟 | 要做点表 ↔ 寄存器地址映射；多一层可观测 | **首选** |

**为什么强烈倾向 (c)**：你要的模拟器不只是"给算法喂数"，而是**在真机之前把真机那条路走通**。
如果 Python 模拟器直写共享内存，那么等到接真 PCS 时，"Modbus 写寄存器"这条路**一次都没走过**，
所有协议层的问题（字节序、寄存器地址、写后回读、超时重试、通信中断恢复）都在现场第一次遇到。

> 而且 (c) 顺带把 §7 的"跟别人的系统对接"也铺好了 —— 同一个 `ModbusDeviceIO`，
> 对着模拟器是调试，对着真机是生产。

### 6.3 "生成的指令如何发给被控对象"

分两种情况，接口要**刻意做成同一个**：

```
情况 A：被控对象 = 模拟器
   EMS ──► ModbusDeviceIO（主站）──► Python 从站（模拟 PCS 寄存器）
                                        │
                                        └─ 从站把寄存器值当指令，跑物理模型，更新量测寄存器

情况 B：被控对象 = 真 PCS
   EMS ──► ModbusDeviceIO（主站）──► PCS ──► 电池
```

**只有把 A 和 B 做成同一条代码路径，模拟器才有意义。** 这正是 P0 的 `IDeviceIO` 抽象
（`04/src/device_io.h`）存在的理由 —— 算法一行不改，只换适配器。

### 10.1 A 类：安全相关（接真机前必须补）

#### ~~A1. BMS 禁充放位走不进 RT_DB~~ —— **已修（2026-09-19）**

原证据：`07/src/rtdb/rtdb_device_io.h:259-262`

```cpp
// 禁充/禁放位：当前点表未建模（与 MemoryDeviceIO 对齐）。
out.bms_chg_forbidden = false;
out.bms_dis_forbidden = false;
```

后果链：

```
BMS 上报"禁充/禁放"（全项目最硬的安全边界）
   └─► 04/ 的 kBmsForbid 策略（S01 · L0 · 最底层）
         └─► 05/ 安全引擎折进 (p_lower, p_upper)
               └─► 决定 EMS 到底能不能放电
```

原状是这两个位**恒 `false`**，等价于「BMS 永远允许充放」。

**为什么测试全绿也没发现**：仿真形态下 `DeviceLimits` 由 `SimDeviceIO` 直接从 `PlantConfig` 给，
`bms_chg_limit_kw` 那一路是通的，所以 `05/` 的限值逻辑照常被测到 ——
**只有 `RtDbDeviceIO` 这一条路是恒 false**。而 T26 的跨进程对照只比了 30 个**点的值**，
没比这两个 `bool`。

##### 修法（四层）

| 层 | 内容 |
| --- | --- |
| 点表 | 追加 `STA.BMS_CHG_FORBID` / `STA.BMS_DIS_FORBID`（30 → **32 点**），**追加在末尾**而不是插进 STA 段中间 —— 索引是运行时坐标，中间插入会让其后所有点整体偏移，而共享内存里已有段的索引不跟着变，现场表现为"点名对得上、值全是隔壁点的" |
| 默认值 | **0 = 允许**。刻意不设 1：默认禁充放会让"设备侧尚未上线"直接锁死 `[0,0]`；而"允许"与修复前**逐位一致**。安全性由 `05/` 的 `bms_comm_lost → [0,0]` 独立承担（那条路径不依赖本点） |
| 适配器 | `RtDbDeviceIO::read_limits()` 真读点表；`MemoryDeviceIO` 同步（逐点可互换），并加 `set_bms_forbid(chg, dis)` 注入口 |
| 断言 | `07/T25`（四方向：置位 / 不串扰 / 可恢复 / 双置）、`11/T48`（窗内 0 拍放电 + 差分守卫）、`12/A5-07`（验收口径） |

##### 连带发现：设备限值在运行期是**冻结**的（比 A1 本身更严重）

写 T48 时断言红了（`dis_ticks = 0`），追下去发现 **`EmsRuntime::step()` 从不调用
`refresh_device_limits()`** —— 限值只在装配期刷一次，运行期**冻结**。
于是 BMS 动态降功率、PCS 额定、变压器容量、契约需量**全部退化成装配期常量**，
而 `04/IDeviceIO::read_limits()` 的契约写的是"每个控制周期刷新"。

修法：`04/` 接口新增 `limits_are_live()` 能力开关（`RtDbDeviceIO → true`、
仿真适配器 `→ false`），`attach_device()` 据此**自动打开** `refresh_limits_each_step`，
`step()` 新增 ⓪ 步刷新。**现场装配不会忘，仿真行为逐位不变。**

完整复盘见 [`11/docs/README.md`](../11/docs/README.md) §5.4 与 `07/docs/README.md` §8.6。

##### A1 的现场接入硬要求（交付给 BMS 网关方）

1. **必须每拍显式写** `STA.BMS_CHG_FORBID` / `STA.BMS_DIS_FORBID`。写到 old 段
   （30 点）不影响前 30 点，但这两个点会读不到 → 值回落默认（允许）。
2. **不许把这两个位当故障位用**。它们是**正常上报的运行限值**，不是设备故障：
   置位不触发 FAULT、不计 `comm_fault_ticks`、必须可恢复。

#### ~~A2. 关口功率是推算的，不是电表报的 —— 同一路数据两个口径~~ —— **已修（2026-09-19）**

原证据：同一个文件里两个函数取了不同的源

```cpp
// read_snapshot() :224   ← 算法用的这一路
out.p_grid_kw = p_load - p_pv - p_bat;

// read_actuals()  :296   ← 记录 / 上报用的这一路
a.p_grid_kw = cached_value(EMS_P_GRID);
```

真实系统里关口电表是**唯一权威计量点**，另外三路各有误差与不同时延，
相减会把误差**叠加**而不是抵消。而防逆流策略（S05）正是拿 `p_grid` 当命门
→ 推算偏差直接变成误动作，或漏判倒送。

##### 修法与一个"差点漏掉"的前提

三个适配器统一改成**读电表这一个源**：
`RtDbDeviceIO` / `MemoryDeviceIO` 读 `MEAS.P_GRID`；`SimDeviceIO` 由
`PlantModel::meter_p_grid()`（电表模型）给；`read_actuals()` 本来就是读电表 →
两个路径同口径。同时把同一个式子从两处收敛到一处定义。

> ★ **这条缺口差点修了个寂寞**：设备侧发布的 `MEAS.P_GRID` **恰好等于**
> 那个相减式，所以"改成读电表"在**所有现有夹具下逐位恒等** ——
> 编译、`07/T21` 三适配器等价、`11/T41~T49`、`12/` 验收**全部照样绿**，
> 断言杀不死旧写法。所以先给设备侧加了**电表系统偏差**
> （`DeviceSimConfig::meter_bias_kw` / `PlantConfig::meter_bias_kw` /
> `MemoryDeviceIO::set_meter_bias_kw`，**默认 0 → 逐位不变**），
> 让"电表读数 ≠ 功率平衡"可被表达，判据才有区分度。
> 这与 A1 的教训是同一条：**先造出能区分对错的可观测差异，再谈修好。**

##### 修复过程中暴露的第二个真问题

改完后 `07/T21`（三适配器逐位等价）立刻红：`maxΔcmd=75 / maxΔgrid=75`。
根因：`MEAS.P_GRID` 原本只在 `execute()`（每拍末）更新，而负荷/光伏是在**拍首**
写入的 → 电表读数比其它量测**慢一拍**；改前 `read_snapshot()` 用本拍的 load/pv
自己重算，正好把这个偏差**掩盖**掉了 ——
**也就是说 T21 的"逐位等价"有一半是绕过点表换来的（等价性本身是那个 bug 的产物）。**
修法：`set_environment()` 里同步刷新电表读数（"一次环境发布 = 同一时刻的一致量测集"）。
恢复后 `maxΔcmd=0 / maxΔsoc=0 / maxΔgrid=0`，**而这次是真等价**。

##### 断言（三层）

| 层 | 位置 | 覆盖 |
| --- | --- | --- |
| 单进程 · 点表契约 | `07/T25` | 电表点**故意 ≠ 平衡式**（137 vs 157）→ 快照跟电表；且快照 == actuals |
| 单进程 · 适配器 | `07/T22` / `07/T29` | MemoryDeviceIO（250 vs 272）/ SimDeviceIO 电表模型；反向守卫：偏差归零后回到平衡值 |
| 跨进程 | `11/T49`（新增） | 设备侧电表带 **+40 kW** 偏差 → 算法看到的关口功率 = 三路平衡 + 40，**逐拍 200/200** 成立 |
| 验收 | `12/A1-09`（新增） | 公开出口口径；反向守卫：两源确实差 40 kW |

**判据有效性已验证**：把 `read_snapshot()` 临时退回推算式，
`11/T49` 立刻 **6 条红**（`ok_meter / ok_algo / ok_gap / min_gap / max_gap / max_err_algo`）。

##### 遗留（本次未做）

- **外部台账只到"偏差"这一层**：真机的电表误差是**慢漂移 + 时延**，
  这里只建模为**常量偏差**。要做真机对账，还需给电表模型加一阶滞后与漂移。
- `PlantModel` 的量测路径带噪声、真值路径不带 —— 两条路径的 `p_grid` 在
  `noise_kw > 0` 时**不相等**（这是"量测 vs 真值"的固有差别，不是缺陷），
  但**计量口径只有一处定义**（`meter_p_grid()`）。
