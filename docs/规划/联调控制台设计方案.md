## 0. 一页速览

### 0.1 结论

**有必要做，但只能做成「控制台（Console）」，不能做成「第二个仿真器」。**

网页 = 面板 + 显示器。物理模型、策略、安全链**一行都不重写**。
真正的价值不是"能跑"，而是**能做受控对照实验**（§5.3）。

### 0.2 v2 相对 v1 的四处修正

| # | 修正 | 性质 | 证据 |
|---|---|---|---|
| **M1** | **补策略开关**（v1 里一个开关都没有） | 补缺口 | `P1/data/ems_config.sample.json:149-179` `strategies.{id}.enabled` |
| **M2** | **`scenario.json` 改为直接嵌 P1 的完整 schema**，不另起一套 | **架构级** | `P1/src/config_loader.h:206/297/455` |
| **M3** | **补 EXT 外部设定注入**（v1 只能读不能写） | 补缺口 | 写端 `P3/src/rtdb_ext_sink.h:88` `RtDbExtWriter` |
| **M4** | **补闭环指标导出**（v1 只给逐拍 CSV，让人自己算） | 补缺口 | `07/src/realtime_loop.h:197` `LoopMetrics` |

> **M2 为什么是架构级**：v1 拟定的 `device`/`ems` 两组 schema 会成为**第三套配置**，
> 与 P1 的 `ems_config` 并列 —— 那正是 §1 纪律要禁止的"第二份真相"。
> v2 改为：`14/` 只自留 `run` / `device` / `ext` / `script` 四段，
> **算法侧参数一律走 P1 的 `ems_config` 嵌段**，不重新定义任何一个键。

### 0.3 做什么 / 不做什么

| 做什么 | 不做什么 |
|---|---|
| 网页只做：编辑工况 → 触发内核 → 呈现结果 | 不在网页里重写物理模型 / 策略 |
| 复用 `DeviceSideSim` / `EmsSideApp` 的 `step()` | 不引入新的仿真内核 |
| 结果落 CSV/JSON，一次性拉取 | 不做 WebSocket 逐拍推送 |
| 参数装配**必须走 `apply_config()`** | 不自己逐个赋值（§3.7 三个顺序陷阱） |
| 故障/限值/外部设定统一为"时间窗剧本" | 不做单步 / 暂停 / 回退（§5.5） |

## 1. 定位：控制台 vs 第二个仿真器（**最关键的一节**）

两条路的差别不在工作量，在**结论可不可信**。

```
参数面板（浏览器）
      │
      ├─── A：在网页里重写一套 JS 物理模型 + 策略
      │        └─► 第二份真相 ─► 跨进程缺口永久测不到 ─► 与 9276 基线脱钩
      │
      └─── B：生成 scenario.json，喂给现有 C++ 内核            ★ 本方案
               └─► 复用 DeviceSideSim::step() / EmsSideApp::step()
                    └─► 与 T41~T49 同一份代码 ─► 结论可回填成断言
```

**为什么 A 会"永久测不到"**：本项目已踩过三次同一类缺口 ——
① `CMD.P_UPPER/P_LOWER` 从未发布（`11/docs/README.md` §5.1）、
② seqlock 碰撞被误计为采集失败（§5.2）、③ 设备限值运行期冻结（§5.4）。
共同点是：**三层测试全绿，只有跨进程/并发才暴露**。浏览器里的单进程 JS 模型
会把这类缺口从"难发现"变成**不可能发现**。

### 1.1 四条硬边界（写进代码注释，违反即视为缺陷）

1. **内核唯一**：任何物理量/策略的算式，只允许存在于 `04/`~`08/` 与 `11/`。
   `14/` 里不允许出现第二个 `p_grid` 定义、第二个 SOC 积分、第二个安全约束。
2. **点名不出现在网页层**：网页传的是 `device.transformer_kva` 这种**业务键**，
   不是 `CFG.TR_KVA`。点名只出现在适配器里（P0 纪律）。
3. **缺省即默认**：`scenario.json` 里没写的字段 = 沿用编译期默认值
   → 现有工况**逐位不变**，9276 断言不受影响。
4. **★ 配置单一来源**：算法侧参数（`loop`/`safety`/`coordinator`/`fsm`/`strategies`）
   **只经由 P1 的 `EmsConfig` 结构进入 `EmsRuntime`**，禁止 `14/` 另立等价字段。
   一次侧参数则只经由 `DeviceSimConfig`（§2.4）。

### 2.2 三种内核形态（P0 只做第一种）

| 模式 | 适配器 | 共享段 | 并发 | 墙钟 | `inject_plant` | 语义 |
|---|---|---|---|---|---|---|
| **`rtdb`**（P0 默认） | `RtDbDeviceIO` + `DeviceSideSim` **顺序驱动** | 需要 | 单实例 | 秒级 | **false** | 走 RT_DB 点表，与三进程同一份 `step()` |
| `proc`（P1） | 同上，真三进程 + `Pacing` | 需要 | 单实例 | 15 s 起 | **false** | 最真，能照并发缺口 |
| `fast`（P2 可选） | `MemoryDeviceIO` 直连 | 不需要 | 可多会话 | 最快 | **true** | **不走点表**，页面须显著标注 |

> **为什么 P0 默认 `rtdb` 而不是 `fast`**：`fast` 绕开点表，等于把 A1/A2 那类
> "写了但某条路径上不生效"的缺口（`模拟器与设备接入梳理.md` §10.4 D4）重新藏起来。

### 2.3 `rtdb` 模式的装配顺序（**顺序错了会静默跑错**）

```
① 建段（复用 07/src/rtdb/ems_rt_db_setup.c，保留存活句柄）
② DeviceSideSim dev(&h, script)          ← device 段的参数在这里生效
③ dev.step(0, dt)                        ← ★ 必须先发布一次 CFG.*
④ EmsSideApp app(&h, cfg)                ← 构造时 attach_device() 读 read_limits()
⑤ EmsConfig ecfg = P1::from_json(嵌段)   ← ems_config 段
⑥ P1::validate(ecfg) → 有错就退出（不静默）
⑦ P1::apply_config(app.rt(), ecfg, {inject_plant=false, reset_runtime=true})
⑧ 循环 N 拍：dev.step(t,dt) → [按窗发布 ext] → app.step(dt) → 落一行 CSV
```

第 ③ 步不能省：`11/docs/README.md` §2.1-3 踩过 —— 设备还没发布 `CFG.*` 时
EMS 读到的是**点表默认值**（变压器 250 kVA），安全边界全错。
（`rtdb` 模式下**不能**调 `app.wait_for_device()`——那是等多进程发布的，单进程会死等超时。）

### 2.4 ★ 一次侧参数的**双源辨析**（v2 新增，易混淆）

同一个物理量（如变压器容量）在两个地方都能设，**但只有一个生效**：

| 来源 | 载体 | `rtdb`/`proc` 模式 | `fast` 模式 |
|---|---|---|---|
| **`device`（`DeviceSimConfig`）** | 设备侧 → `CFG.*` 点 → `read_limits()` | **真值源** ✅ 生效 | 不走点表 → 不适用 |
| **`ems_config.plant` / `.limits`** | 装配层直接注入 `rt.device_limits()` | **参考值** ❌ 不生效 | ✅ 生效 |

依据在 `P1/src/config_loader.h:446-453`：

```cpp
struct ApplyOptions {
    // 仿真装配：把配置里的 plant / limits 注入内置仿真适配器。
    // 现场部署（attach_device() 注入了 RT_DB / Modbus 适配器）应传 false ——
    // 真实设备的额定与限制由设备每拍给出，配置文件里的是**参考值**，不得覆盖。
    bool inject_plant = true;
```

**面板必须把这两组视觉分区并明确标注**，否则用户会遇到
"我在 ems_config 里改了变压器容量，怎么没反应？"——
那是一个**看起来像 bug 的正确行为**（§10.4 D4 的同型陷阱）。

> ⚠️ **由此引出一条未验证的待查缺口**：`11/` 联调与 `P1` 两条装配路的
> **默认参数是否已经一致**？`11/src/integration_runner.h:543` 只调
> `rt_.apply_configs()`（用结构体默认），全仓 `11/` 无 `ems_config` 引用。
> 若两路默认值不一致，则"P1 跑通的结论"与"11/ 联调的结论"**不可互相外推**。
> 详见 §10 T1。

### 3.4 `ext`（M3 —— 模拟调度下发）

复刻 `DevFaultWindow` 的"时间窗"抽象，与故障剧本同构：

```jsonc
"ext": {
  "windows": [
    { "t_begin_s": 10, "t_end_s": 40,
      "p_setpoint":  80,    // 6001：正 → 只收上界；负 → 只收下界；0 = 无设定
      "p_upper_set": 1e9,   // 6003（1e9 = 不限制）
      "p_lower_set": -1e9,  // 6004
      "d_target":    0,     // 6002（0 = 不覆盖）
      "pcs_onoff":   true,  // 5001
      "ems_enable":  true } // 5002
  ]
}
```

| 约束 | 原因 |
|---|---|
| 必须走 `RtDbExtWriter::begin_publish()` / `commit_publish()` | 区序号 SEQ 前后各递增一次 → 稳定态为偶数；绕过会让读者读到"半更新"快照（`07/src/rtdb/ext_setpoints.h:21-26`） |
| `EXT.TS` 必须写**墙钟**当前值 | `load_ext_setpoints` 用 `now_s - ts_s` 判陈旧，写模拟时间会算错 |
| 语义是"**单侧收紧**"，不是覆盖 | `narrow_interval_by_ext()`（`ext_setpoints.h:232`）：正设定只压上界，负设定只压下界。对称带会把反方向也锁死 → 制造假降额 |
| 停机 / 闭锁（5001/5002）**stale 也粘住** | `ext_setpoints.h:234-245`："调度最后说停"是状态意图，通信断了不该自动复机 |

> ⚠️ **单进程模式下 EXT 的 stale 语义不成立**（§9 R4）：
> 模拟 600 拍 × 0.1 s = 60 s，墙钟只过 ~1 s → `stale_s = 30` 永远不会触发。
> 所以 **"EXT 失效兜底"只能在 `proc` 模式（真实时节拍）下测**。

### 3.5 `script`（故障 / 限值剧本）

```jsonc
"script": [
  { "kind": 4, "t_begin_s": 20, "t_end_s": 25 },
  { "kind": 8, "t_begin_s": 30, "t_end_s": 35 }
]
```

| kind | 含义 | 性质 |
|---|---|---|
| 1~6 | BMS通信断 / 电表通信断 / PCS通信断 / PCS故障 / 设备离线 / 品质位劣化 | **故障**（计 `comm_fault_ticks`） |
| 7 / 8 | BMS 禁充 / BMS 禁放 | **正常上报的运行限值**，不是故障（`11/docs/README.md` §4.1） |

> ★ 面板上必须把 1~6 与 7/8 **分成两组显示**，否则用户会以为"置了故障"。
> 两类走不同链路（7/8 → `read_limits()` → S01 → `05/` 收区间）。

### 3.6 加载期校验（**fail fast，禁止静默截断**）

| 校验 | 原因 |
|---|---|
| `soc_phys_min < soc_phys_max`，均在 [0,1] | 反了会让 SOC 区间为空 |
| 容量 / 额定 / 需量 > 0 | 负值算出荒谬区间 |
| `eta_*` ∈ (0,1] | 效率 > 1 会造能量 |
| 剧本窗 `t_end > t_begin`、同 kind 不重叠、**窗不超出 `steps*dt`** | 窗超出 = 剧本**静默不发生** |
| `strategies` 的 id 必须已注册 | `apply_config` 已会报错，此处再拦一次以便给出行号 |
| `steps*dt/speed` 算出的墙钟有上界 | 防浏览器请求挂死 |
| 校验失败 → **退出并给出 `字段:原因`** | 静默失败是头号敌人 |

### 3.7 ★ 装配必须走 `apply_config()`，不许自己赋值

`P1/src/config_loader.h:455-521` 已经踩过并记录了**三个顺序陷阱**，
绕过它自己拼赋值会精确复现"配置生效了但行为没变"：

| 陷阱 | 内容 |
|---|---|
| ① | `configure_plant()` 内部会 `read_limits()` 覆盖 `dev_` → `device_limits()` 必须**后**赋值 |
| ② | `apply_configs()` 用 `dev_.pcs_rated_*` 算协同层参数 → 必须在 `device_limits` 落定**之后** |
| ③ | **`OutputShaper` 在 `init()` 里缓存了 deadband / switch_delay 的副本** → 只改 `LoopConfig` 而不重推 `shaper`，就**完全没效果** |

> 陷阱 ③ 尤其致命：它是"改了参数、界面也显示了、但行为一点没变"的典型。
> 本项目纪律是"注释声称的行为必须与代码实际行为一致"，这里正是它的正面教材 ——
> P1 已经处理了，`14/` 只要不绕过即可。

### 5.4 交互取舍

| 不做 | 为什么 |
|---|---|
| WebSocket 逐拍推送 | 600 拍 × 100 ms，引入实时性复杂度；要的是"跑完看全景" |
| 曲线缩放/刷选（P0） | P1 再加 |

### 5.5 为什么不做单步 / 暂停 / 回退

会诱导出一个**假的交互语义**：EMS 是硬实时闭环（100 ms 节拍），暂停后再继续
不等于"中间什么都没发生" —— 设备侧的物理积分、SOC、热模型都在继续，而控制台
把它们冻住了。那是**真实系统里不存在的状态**，结论不可外推。

要看清某一拍：跑完再定位（曲线 + 状态带 + SOE），或缩短 `run.steps` 重跑。

## 8. 验收口径（怎么证明它没骗人）

### 8.1 逐位回归（最硬）

**空 `scenario.json`（全缺省）跑出的 `result.csv`，必须与现有 `11/` 单进程形态
同参数结果逐位一致** —— 判据：`max|Δp_cmd| = max|Δp_actual| = max|Δsoc| = 0`。

不成立就说明 `load_*` 偷偷改了默认值，或漏了默认值分支。

### 8.2 七个预设的判据必须全绿

§5.3(a) 的"预期判据"列全部成立。这不是"跑通了"，是"跑出了该有的结果"——
区别在 A2 的教训：**先造出能区分对错的可观测差异，再谈修好**。

### 8.3 反向守卫（证明检查单有区分度）

| 反向操作 | 预期 |
|---|---|
| `transformer_kva` 设成 **250**（点表默认） | 「一次侧参数来自设备侧 CFG」必须 **FAIL** |
| 剧本窗设成 `t_begin > steps*dt` | 「剧本窗内确有其拍」必须 **FAIL**（证明窗没被静默吞掉） |
| `strategies` 里写一个不存在的 id | 加载期报错退出，不许静默忽略 |

> 没有这些，检查单可能在"参数压根没生效"时也 vacuously 通过 ——
> 与 §10.1 A1 的"恒 false 也能全绿"是同一个陷阱。

### 8.4 结论可回填（**防止沦为演示玩具**）

至少 1 个预设 + 对照实验组 B 落成 `14/tests/` 断言。

**不做这条，整个控制台就与 9276 基线脱钩** —— 那比不做更糟：
脱钩的演示会给人"这个工况没问题"的错觉，而 §7.1 的极限环现在正是这个状态。
