## 3. 为什么"静态链接"是关键

GPL-3.0 的义务按"**是否构成同一部作品**"划分，两种情形结论完全不同：

- **衍生作品（derivative work）**：GPL 代码与本项目代码编译进**同一个二进制**、
  在同一地址空间运行、互相调用 → 通常认为整部作品都要按 GPL-3.0 发布。
  **本项目现在是这一种**（静态链接进 `iec104_gateway.exe`）。
- **聚合（mere aggregation）**：两者是**各自独立的程序**，只通过通用通道
  （socket、共享内存、管道、命令行）交换数据 → 通常认为 GPL 不传染到另一方。

> 所以"要不要改代码"这件事，取决于法务对上面这条的判定，而不是取决于库有多大。

## 4. 可选路径与代价

| 路径 | 做法 | 技术代价 | 商业代价 | 适用条件 |
|---|---|---|---|---|
| **A 购买商业授权** | 向 MZ Automation 采购，现状不动 | **零**（不用改代码） | 授权费（需询价；通常按产品/装机量计价） | 要闭源分发，且预算可接受 |
| **B 进程隔离** | 把网关拆成**独立程序**，业务侧只通过 IPC（socket / 共享内存）与它通信；GPL 组件只留在那个独立程序里 | **中**：定接口、进程生命周期与联调；但 `P3/` 已有的 `IDataSource` / `ICommandSink` **就是现成的窄接口**，可直接当进程边界 | 无 | 法务认可"聚合"判定 |
| **C 换自研实现** | 用自研 APCI/ASDU 栈替换 | **大**：协议栈要重新验证（现有 **408 条**协议断言、**10 个缺陷复盘**都建立在这个实现上） | 无 | 时间与验证成本可接受 |
| **D 换成宽松许可的库** | 换 MIT / BSD / Apache 许可的 104 实现 | **中**：只改 `iec104_server.h` + `main_gateway.cpp`；**许可必须逐个核对**（同厂商的 `libiec61850` 也是同样的 GPL/商业双轨，不算解法） | 无 | 存在许可清晰且可用的替代 |
| **E 整体开源** | 接受 GPL-3.0，按 GPL 发布 | 零 | 失去闭源 | 商业上可接受时（一般不是） |

> **C 不是从零发明**：2026-09-15 已经做过一版**不依赖 lib60870 的自研
> Modbus + IEC104 双适配器**，存放在远程分支 `origin/p3-dual-adapter-0915`。
> 当时的取舍是"避开 GPLv3、换来逐字节断言能力"。也就是说，
> **这条路走通过一次**，代价是协议栈要重新攒验证。

## 5. 需要商务 / 法务回答的三个问题

1. **本产品对客户是"分发二进制"还是"仅现场部署 / 提供服务"？**
   只在内部使用、不对外分发二进制时，GPL 的义务范围与"卖软件"完全不同。
2. **能不能接受"只开网关这一个组件"？**
   （路径 B 的目标就是让需要开源的范围缩到最小 —— 一个独立程序，而不是整个平台。）
3. **是否采购商业授权？预算与流程**（供应商 MZ Automation）。
   若选这条，技术上不需要任何改动。

## 6. 技术侧已经做的（为任一选项留门）

- **物理隔离**：库在 `vendor/lib60870/`，业务在 `P3/`，两个目录；

  换任何实现都能原样带走；

  路径 B 可以直接拿它们当进程边界。

## 7. 建议顺序

1. **先回答 §5 的三个问题**，定下走 A / B / C / D 哪一支；
2. 再动代码。

**在授权未定之前，建议不要再加深对库 C API 的依赖** ——
典型如：把 lib60870 的 ASDU 结构体 / 内部头文件泄漏到业务代码里。
依赖越浅，四条路的成本都越低。
