# 核对：日仿真 d001 与 d002 的差异（2026-10-11）

## 结论

- 都是 `kind=day`、`fault=0`，即"典型日（正常）"默认场景；
- 10/ 仿真器是**确定性模型**（`10/src/` 全目录 0 处 `rand/srand/mt19937/random_device`），

- `summary.json`、`report.html` **仅差 run_id 标签与墙钟耗时**。

## 顺带发现：`sim_run.steps` 与 `scenario.steps` 同名列口径不一致

| 表.列 | d001 值 | 语义 | 来源 |
|---|---|---|---|
| `scenario.steps` | **86400** | 仿真积分步数（dt=1 s × 86400 s） | `importer.py:304` ← summary.json |
| `scenario.log_rows` | 8640 | 落盘行数（log_every=10） | `importer.py:304` |
| `sim_run.steps` | **8640** | ← 实际写的是**落盘行数** | `simrun.py:282` |
| `sim_run.log_rows` | 8640 | 落盘行数 | `simrun.py:282` |

因果链：

1. `importer.import_scenario()` 的返回值里，`"steps": len(step_rows)`（`importer.py:415`）——
   这是**插入 step_record 的行数**（8640），不是仿真步数（86400）；
2. `simrun.py:282` 把同一个 `res["steps"]` 同时写进了 `steps` 和 `log_rows` 两列：
   `(_now(), wall_s, res["steps"], res["steps"], ...)`；
3. 于是台账 `sim_run.steps` 恒等于 `log_rows`，而 `scenario.steps` 是 86400 —— **同名不同义**；
4. `14/tests/selftest.py:1295` 用 `t.eq(rr["steps"], 8640, "日仿真 8640 拍")` 把它**钉住**了，
   注释写作"8640 拍"⇒ 测试作者是把 `sim_run.steps` 当"采样拍数"理解的；
5. `get_run()` 是 `SELECT r.*, ... s.log_rows`，两表 `log_rows` 重名，后取的 `s.log_rows` 覆盖前者，
   两者恰好都等于 8640 ⇒ **掩盖**了冲突，界面上看不出来。

性质判定：

- **不是**数据错误，两列各自都有确定含义，且 `scenario.steps` 是对的；
- **是**命名/口径缺陷：同一个词 `steps` 在两张表里指两个量（积分步 86400 / 落盘行 8640），
  且现有断言把它固化为"拍数"，任何按 `sim_run.steps` 反推仿真时长（`steps × dt_s`）的代码
  都会算出 8640 s 而不是 86400 s。
- 未修，理由：一改就要动 `selftest.py:1295` 的断言值与注释，属于口径变更而非 bug 修复，
  应先确认下游是否有页面/报表依赖 `sim_run.steps` 这个 8640 口径。**留证据待定。**

## 追问："既然零差异，还需要分两个吗？"

### 判断

**数据上不需要两份；台账上必须留两条。**
但更要紧的一句是：**"零差异"不是设计正确的证明，是平台层没接输入口的症状。**

### 结构性原因：平台侧发起仿真的输入空间只有 6 个离散点

平台实际下发的命令行（`14/src/simrun.py:217-221`）：

```
sim_demo.exe --out <dir> --title <t> --duration-s <d> --log-every <n> [--fault]
```

仿真器自身支持的参数（`10/src/main.cpp:308-310` 的 usage）：

```
sim_demo [--csv <path>] [--out <dir>] [--fast] [--log-every N]
         [--duration-s SEC] [--title STR] [--fault] [--stress]
```

**8 个参数里平台只接了 5 个，且漏掉的恰是最关键的那个 —— `--csv`（日曲线输入口）**
（解析处 `main.cpp:282-284`，优先级见 `main.cpp:270-272`：内置场景 < `--fault` < `--fast` < 显式 CLI 项）。

`KINDS` 是常量表（day / week / month），`fault` 只有布尔两态 ⇒
平台可发起的运行 = **3 × 2 = 6 个离散点**，且 `--stress` 也不可达（内置 stress 场景走
`import_sim.bat` 批量导入，不走这条路径）。
「日仿真（正常）」在这 6 个点里是**唯一一个** ⇒ 点两次必然逐字节相同。

⇒ 零差异的来源是"没有变量可差"，不是"两次运行等价"。
一旦接上 `--csv`，两次运行就会合理地不同。

### 两份数据确实白占地方（实测）

| 项 | 单次 | d001 + d002 |
|---|---|---|
| `step_record` + 索引 | ≈1.35 MB | ≈2.7 MB |
| `control_command` + 索引 | ≈0.96 MB | ≈1.9 MB |
| 磁盘产物 4 件 | 1.14 MB | 2.3 MB |
| **合计** | **≈3.3 MB** | **≈6.9 MB** |

- `ems.db` 实测 **11.18 MB**，其中 `step_record`+`control_command`+索引 ≈ 11.0 MB（占 98%）；
- d001 + d002 = 17 280 / 43 252 行 = **39.9%** ⇒ 库里约 **4.4 MB 是这两份重复数据**；
- `docs/后续完善路线-2026-10-11.md` 已记一条「sim-dXXX 只增不减，无保留/归档/轮转策略」——
  **点两次 = 库里两份一样的东西**，这条在日仿真上已经发生了。

### 台账两条必须留 —— 这是唯一的证据

`audit_log` 实测（id 15 / 16）：

```
2026-10-11 21:06:54  admin  sim_run_start  engine  d001 kind=day fault=0
2026-10-11 21:07:02  admin  sim_run_start  engine  d002 kind=day fault=0
```

台账的价值不是"记一个不同的结果"，而是**记"谁在什么时候请求了什么"**。
删掉第二条不会让"有人点了两次"这件事消失，只会让它**失去证据**——
而这两条恰好是"平台没有防重"的唯一证据。

### 建议（三选一，含代价）

| 选项 | 做法 | 代价 | 遗留问题 |
|---|---|---|---|
| A 不动 | 靠人别点两次 | 0 | 不解决根因，数据继续翻倍 |
| **B 加防重提示**（推荐先做） | 发起前查同 `(kind, fault)` 的成功运行，界面弹「d001 已是相同参数的运行（21:06），仍要再跑？」 | ≈半小时：一个查询 + 一个确认 + 一条断言 | 不改数据模型、不动已有断言 |
| C 数据去重复用 | 输入指纹相同 → 不重跑，`scenario_id` 指回已有数据集，台账加行标 `reused` | ≈半天：加列 + 改 `start()` + 断言 | **前提是输入有变量**，否则指纹恒等；"复用哪一次 / 被删了怎么办"要定规则 |
| D 直接拒绝（409） | 同参数已有成功运行就拦 | 最小（1 行 `if` + 断言） | 真想重跑时被拦住；接 `--csv` / `--stress` 后会误拦 |

推荐 **B**：它把"重复"从**静默产生两份数据**变成**用户的显式选择**，
且不动 `selftest.py:1295` 那条已钉住的断言，风险最低。
若用户每次都点"仍要再跑"，则说明缺的不是防重、而是 `--csv` 输入口 —— 这正是 B 的价值。

### 顺序提醒：C 不该先做

在平台接出 `--csv` 之前，"输入指纹"就等于 `(kind, fault)` 两个值 ——
那只是把"零差异"写进代码，给一个恒定值加哈希不会带来任何收益，
还会为将来的输入口留下一个错的抽象。

**正确顺序：先接 `--csv` 输入口（`main.cpp` 已支持，平台侧只需多传一个参数 + 一处文件选择）→ 再做指纹去重。**

### 现场处置

`d002` 可用 `DELETE /api/sim/runs/d002` 删除，`audit_log` 的 `sim_run_start` 记录会保留，证据不丢。
但**删了不解决任何问题**（下次再点就是 d003）。建议**留着当证据**，等 B 做完一并清理。
