# 设备侧数据通道 —— 实证验证（2026-10-11）

> **为什么要做这件事**：2026-10-11 的体检给出一个判断 ——
> 「平台层没有设备侧数据的入库通道，即使接上真设备，设备侧那 107 个点也到不了界面」。
> 这个判断**没有实跑证据**，是从三处静态事实推出来的（表是空的 / 没有桥接进程 /
> `h_realtime` 不读那张表）。
> 本次的目标就是**把它跑一遍**，看推出来的结论和跑出来的结论是不是一回事。

**结论先行**：**原判断不准确，需要修正。** 通道是**通的** —— 设备数据能进库、能在界面上看到真值；
真正断的是**设备级那张表**，以及**107 点全点表没有产出方**。详见 §4。

## 1. 实验设计

不写新代码、不改任何源码，全程只用**项目自带的工具**，这样结论不会被"我新写的探针有 bug"污染：

| 环节 | 用什么 | 为什么用它 |
|---|---|---|
| 设备替身 | `13/sim/modbus_slave.py`（项目自带夹具） | 可控工况：`--load 380 --pv 150` 的值是**我设的**，能反查 |
| 采集核对 | `13/build/modbus_probe.exe` | 现场点表核对工具，逐点印 `ok` 列 |
| 闭环采集 | `07/build/main_field.exe --device modbus` | 现场入口，**项目自己定义的接真机方式** |

| 看界面取到没 | `api.dispatch` 调 `/api/realtime`、`/api/devices/{id}` | 界面调的就是这两个 |

口径纪律：**每一步都留可复核的输出**，不是"跑通了"三个字。

**"采得到"这一步是实证**：380 / 150 与我给从站设的工况逐字一致。

### 步骤 3 · 闭环采集并写实录

```
07/build/main_field.exe --device modbus --host 127.0.0.1 --port 15020 --unit 1 \
                        --steps 20 --dt 0.2 --control --record .dev_live.csv -v
→ 设备来源 : modbus      接入参数 : 命令行指定
  预读体检 : 读快照 成功 / 品质位 有效 / 状态 正常
  实录文件 : .dev_live.csv（20 列，与 10/ timeseries.csv 同构）
  闭环指标：samples=20 mean_err=23.160kW rmse=30.015kW max_err=44.000kW
            over_delivery=0.000%  flips=0
```

实录 CSV：**21 行（含表头）× 20 列**，首行
`t_s=1791671600.633, 2026-10-11 06:33:20, INIT, P_load=380.000, P_pv=150.000, P_grid=272.000, SOC=0.550, T_C=25.000`。

★ 顺带一条**设计事实**（help 里写明，此前没在任何文档里被强调）：
**`--record` 只在 `--control` 下有意义** —— 现场第一次接进来默认是**只读**（不下发指令），
那时**不产实录、数据不落盘**。这是对的（不下发就不该产生闭环数据），
但"默认姿势下平台看不到数据"这件事必须写进作业指导书，否则会被误判成故障。

### 步骤 4 · 入库：进了 `step_record`，没进 `realtime_data`

```
python 14/src/importer.py --live .dev_live.csv live <临时库>
→ [OK] live 入库: 场景 live (time_base=wall)  本次 20 行，累计 20 行

表行数：step_record = 20   realtime_data = 0   device = 6   device_point_map = 0
```

### 步骤 5 · 界面到底取到没

| 接口 | 结果 |
|---|---|
| `GET /api/realtime` | **items = 5 台，值是真的**：`DEV-LOAD-01 = 380.0 kW`、`DEV-PV-01 = 150.0 kW`、`DEV-METER-01 = 268.394 kW`、`DEV-PCS-01 = 3.606 kW`、`DEV-BMS-01 SOC=0.55 T=25.0` |
| `GET /api/devices/DEV-BMS-01` | **`latest_realtime = None`** |

**同一份数据，一个接口看得到、另一个看不到** —— 这就是断点最精确的画像。

## 3. 最硬的一条证据（静态，可复核）

全仓库扫描 `realtime_data` 的**写入**语句：

```
grep (INSERT|REPLACE|UPDATE|DELETE) + realtime_data   →  0 处
```

`realtime_data` 的全部出现只有 8 处，且是：建表（`schema.sql:129`）+ 索引（143/144）
+ **一处读**（`api.py:307`，即 `h_device_one` 的 `latest_realtime`）+ 表清单（`emsdb.py:182`）。

**这是一张"有读无写"的表。** 这比"表里 0 行"更硬：
0 行可以解释为"没人跑过"，**没有写入方**说明通道在设计上就不存在。

后果是一个教科书式的**静默失效**：接口返回 200、`latest_realtime` 恒为 `null`，
界面上"这台设备没有实时数据"和"这个功能坏了"长得一模一样。

## 4. ★ 修正此前的判断

| | 原判断（10-11 体检，静态推出来的） | 实测后（本次） |
|---|---|---|
| 设备侧数据能不能进平台 | **"没有通道，接了真机也到不了界面"** | **通道存在且可用**：`main_field --device modbus --control --record` → `importer --live` → `step_record` → `/api/realtime` 看得到真值 |
| 断在哪 | "平台层缺设备侧入库通道" | **断在设备级那一层**：`realtime_data` 无写入方 → `/api/devices/{id}` 恒 null |
| 107 点能不能到界面 | 笼统地说"到不了" | **40 点 EMS 口径能到**（20 列实录）；**107 点设备全点表没有产出方** —— 没有任何进程把它写出来 |

**这次修正本身就是做实验的价值**：原判断会让下一步投入跑偏 ——
照着"打通入库通道"去做，等于重造一条已经存在的路；真正要补的是**设备级那一段**。

## 5. 三个缺口的准确定位

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|
| G1 | `realtime_data` **无写入方** | 全仓库 0 处 INSERT/REPLACE | `/api/devices/{id}` 恒 null；`device_point_map` / `device_conn` 恒 0 行 |
| G2 | **107 点设备全点表没有采集产出方** | 实录只有 20 列（EMS 口径），不含空调/消防/门禁等点 | 装配视图 9 个灰部件**即使 G1 修好也仍然灰** |
| G3 | 只读模式不落盘 | `--record` 仅 `--control` 下有意义 | 现场首次接入（默认只读）时平台无数据 —— 是设计，但没写进作业指导书 |

> G1 与 G2 是**两件事**，别混为一谈：
> 修 G1 只能让"null"变成"有值"，值的**丰富度**取决于 G2。
> 灰部件的病根在 G2。

## 6. 补法建议（三选一 + 一个必做项）

| 选项 | 做什么 | 量级 | 解决什么 | 不解决什么 |
|---|---|---|---|---|
| **A 止痛** | `importer --live` 顺带把实录映射进 `realtime_data`（5 台设备，映射关系现成） | 半天 | G1：`latest_realtime` 不再是 null | **G2 不动**，灰部件照灰 |
| **B 根治** | 设备侧每拍导出**设备级**点（32 → 逐步到 107），新增 `--record-devices`，由 importer 吃进 `realtime_data` | 2~3 天 | G1 + **G2**：灰部件才有真数据 | 需要定点表与 device_id 的对应（17/ 已有 `point_mapping.h`） |
| **C 让界面诚实**（**必做**） | `h_device_one` 无数据时显式标注来源与原因，如 `latest_realtime=null, source="realtime_data 无写入方（见 G1）"`；前端照此显示"无实时源"而不是空白 | 1 小时 | 消除"200 + null"的静默失效 | 不产生数据 |

**推荐顺序**：**C 先做**（1 小时，先让界面不再假装）→ **再决策 A / B**
（A 是止痛、B 是根治，取决于现场要的是"设备页有数字"还是"装配视图全亮"）→ 才动工。

不建议：跳过 C 直接做 B。B 做完之前，界面一直处于"看起来正常、其实是空的"状态 ——
那正是本项目最忌讳的失效形态。

## 7. 复现命令（给下一个接手的人）

```bat
:: 0) 依赖：pymodbus>=3.15（仅从站夹具需要；13/ 的 C++ 侧零依赖）
python -m venv .venv && .venv\Scripts\pip install -r 13\sim\requirements.txt

:: 1) 起从站（窗口 1，保持运行）
.venv\Scripts\python.exe 13\sim\modbus_slave.py --port 15020 --load 380 --pv 150 --bias 40

:: 2) 采一遍看 ok 列（窗口 2）
13\build\modbus_probe.exe --host 127.0.0.1 --port 15020

:: 3) 闭环采集 + 写实录
07\build\main_field.exe --device modbus --host 127.0.0.1 --port 15020 --unit 1 ^
                        --steps 20 --dt 0.2 --control --record dev_live.csv -v

:: 4) 入库（用临时库，别污染 14\data\ems.db）
python 14\src\importer.py --live dev_live.csv live <tmp>.db

:: 5) 看接口：/api/realtime 有值；/api/devices/{id} 的 latest_realtime = null
```

判据：第 5 步两个接口**必须**一个看得见、一个看不见 ——
如果两个都看不见，说明通道本身坏了（那就回到原判断）；
如果两个都看得见，说明 G1 已被修掉（那就把本报告 §4 划掉）。
