## 0. 一句话结论

**10/ 的 7 类告警 source 代码早已写全，一条都不产生，是因为「默认场景里系统健康」——
这是正确行为，不是缺陷。**
唯一需要修的是 **COMM 逐拍刷屏（真缺陷，270 条未去抖）**。
B 方案的正确做法是：**新增一个「异常工况日」压力场景**，让各类告警在各自真实的物理工况下触发，
**而不是改默认场景把健康系统改成病态系统来刷数据**。

## 2. 我原先的判断错了，自我纠正

初查时我判定「TEMP 是死代码，温度模型量纲错误」。**这个判断是错的**，订正如下：

`07/src/plant_model.h:247-253` 的模型是稳态可解的：
`ΔT = heat_coef · pn² / cool_coef = 0.0006 / 0.002 = 0.3 °C`（满功率）

对照 `17/src/bms_sim.h:78-84` 那份**注释可自复核**的高保真标定：
`heat_coef=5.6e-7 · I² / cool_coef=0.005`，注释称「0.95C / 267 A 下稳态温升 ≈ 8 °C」，
实测 `5.6e-7 × 267² / 0.005 = 7.98 °C` —— **注释与代码一致，标定可信**。

10/ 这台机器：1000 kWh / 250 kW = **0.25C**，5 簇并联每簇 ≈ 70 A
→ 按 17/ 的物理标定推算 `5.6e-7 × 70² / 0.005 ≈ 0.55 °C`

**07/ 实测 0.3 °C 与 17/ 推算 0.55 °C 同量级 → 系数没错，是这台机器在 0.25C 下物理上就不该发烫。**

> 我一度打算「调大 `heat_coef` 让 TEMP 触发」—— 那正好犯了本项目明令禁止的纪律：
> **「别为了掩盖不确定性去调大魔数，那是把假红推远，问题在原地」**（SOUL.md）。
> 正确结论：**TEMP 不是死代码，是需要真实异常工况（散热失效）才触发的健康指标。**

## 3. B 方案做法：新增「异常工况日」压力场景

### 3.1 设计约束（不可突破）

| 约束 | 说明 |
|---|---|
| **默认场景零变化** | `scenario_normal()` / `scenario_fault()` 的行为与断言数**一个字节都不能动**，基线不动 |
| **硬不变量必须为 0** | `out_of_interval` / `over_limit` / `gated_nonzero` —— 架构级，破了就是架构问题 |
| **安全不变量允许非零** | `grid_breach` / `tr_breach` / `soc_violation` —— `sim_24h.h:181-182` 注释明写「越限本身是有效结论而非缺陷」 |
| **复用现有接口，不改物理模型** | 优先用 `set_temp_ambient()` 这类已有 setter，不动 `07/` 的系数 |

### 3.2 每类的触发设计（定量）

| source | 造法 | 关键数字 | 物理语义 |
|---|---|---|---|
| **SOC** | `soc_init = 0.90` | ≥ 0.895 触发告警；≤ 0.902（`soc_max+soc_tol`）**不算越界** | 前一日满充未放，开局贴上限 |
| **SAFETY** | `soc_init = 0.11` + 峰段放电 | 触 `soc_min` → 安全层限幅 → `safety_clip` 置位 | 能量预算耗尽，策略与安全边界冲突 |
| **TRANSFORMER** | `tr_check_cap_kw: 500 → 420` | 阈值 `0.95×420×1.05 = 418.95`；实测峰值 445 > 419 ✓ | 现场实际变压器偏小 / 负荷增长 |
| **TEMP** | 新增故障窗 kind 7「散热失效」→ `set_temp_ambient(50.0)` | `T → 50 + 0.3 = 50.3 > 45` ✓ | 精密空调 / 液冷 CDU 停运 → 柜内环境温升 |
| **GRID** | `soc_init = 0.90`（电池满无法吸收）+ 光伏峰 300 > 负荷谷 250 | 富余 50 kW 无处去 → `p_grid ≈ −50 < −6` ✓ | 现场真实的「午间倒送」风险工况 |
| **COMM** | **修缺陷**（见 §3.3），非造数据 | 270 → 6 条 | — |

> ⚠️ **GRID 一条标注为「需实测验证」**：控制侧是否真的存在防倒送约束，决定它是「真倒送 → GRID 告警」
> 还是「被限住 → SAFETY 告警」。两种结果都可接受，但不能猜，跑出来才算数。

### 3.3 COMM 去抖缺陷（必修，独立于分类需求）

**现状**：`sim_24h.h:280-283` 是唯一没有去抖的分支 —— 其余 5 类都用 `in_xxx` 沿检测，
COMM 直接 `if (fault_bits != 0)` 逐拍记，故障窗 30 分钟 × 10 s 日志 = 180 条/窗。
**症状**：故障日 270 条 FAULT 全是同一句话 `故障位 bits=8`，告警中心被刷屏淹没。

**修法**：按位变化沿去抖
```cpp
if (s.fault_bits != prev_bits) {
    if (s.fault_bits != 0) out.push_back({t, "FAULT", "COMM", "故障位置位 bits=..."});
    else                   out.push_back({t, "INFO",  "COMM", "故障位全部恢复"});
    prev_bits = s.fault_bits;
}
```
预期 **270 → 6 条**（3 窗 × 发生/恢复）。**需先查 `10/tests/` 与 `12/` 是否断言了 COMM 条数，有则同步改。**

## 4. 映射层：source → 部位 → 链路/协议（对齐链路协议清单）

链路清单的「部位」是**物理位置**维度，10/ 的 source 是**系统功能**维度 —— 两者正交，映射层不可省。

| 10/ source | 链路清单部位 | 具体链路 | 协议 |
|---|---|---|---|
| SOC | 柜内·电池舱 | BMS 三层 → BAMS 出口 | 层内 CAN，层间 RS485；BAMS 出口 Modbus TCP |
| TEMP | 柜内·电池舱 **+ 柜内·辅助（散热）** | BMS 电芯采样 + 精密空调/液冷 CDU | CAN + Modbus RTU（RS485） |
| SAFETY | EMS 内部 | 控制 ↔ 设备 | 共享内存 RT_DB |
| GRID | 站内·一次 | 关口电表 → EMS | Modbus TCP（老表 DL/T 645） |
| TRANSFORMER | 站内·一次 | 变压器温控器 → EMS | Modbus RTU（RS485） |
| COMM | 跨全部位（按故障位判定） | 各链路 | 各协议 |
| FSM | EMS 内部 | 控制 ↔ 设备 | 共享内存 RT_DB |

**14/ 侧改动比预想小**：`14/src/importer.py:435-448` 的 `_source_to_device()` **已有 5 路映射骨架**
（FSM→BMS、SAFETY/TRANSFORMER→TR、PCS→PCS、METER/GRID→METER、PV→PV）。
只需：① 给 COMM 加按故障位判定部位的分支；② source 造全后 device_id 自动脱假。

## 6. ⚠️ 能力边界（汇报时必须如实说）

**14/ 告警中心目前只有 290 行数据，全部来自 10/ 的两个 24 h 离线仿真场景。**

B 方案能做到：让告警中心的**分类维度在数据结构上完备、可演示、有断言守着**。
B 方案做不到：让它变成「现场告警中心」—— 数据仍是仿真造的，不是现场真的。
而链路协议清单是**现场真实链路**的清单。两者之间缺的一层是**现场设备侧数据通道**（已挂账，不在本方案内）。

**汇报口径**：「告警分类已按链路协议清单的部位 × 链路 × 协议建模完成，当前数据来自离线仿真压力工况；
接入现场设备通道后，同一套分类无需改造即可承载真实告警。」

## 8. 实施结果（2026-10-11 回填）

### 8.1 拍板结论

D1 = 新增 `--stress` 独立场景；D2 = 允许安全不变量非零；D3 = COMM 去抖现在修。

### 8.2 与设计稿的偏差（**设计与实测差在哪**）

| 设计稿的预期 | 实测结果 | 偏差原因 |
|---|---|---|
| TEMP 用「散热失效」造，环境温度 50 ℃ | ✅ 成功，最高温 50.08 ℃ | — |
| SOC 用 `soc_init=0.90` 造 | ✅ 成功 | 试过 0.80 / 0.88 都不行，见下 |
| SAFETY 靠「满充 + 策略仍要充」造 | ❌ **没造出来** | 策略与安全层共用 `soc_max`，策略守规矩 → 恒 0 |
| GRID 靠「满充 + 光伏大发」造 | ❌ **没造出来** | 典型日全天 `pv < load`，物理不可达 |
| COMM 去抖 270→6 | ✅ 成功 | 顺带发现 TEMP 是**同构的第二个漏网分支**（1440→2） |
| TRANSFORMER 改 `tr_check_cap_kw=420` | ✅ 成功 | 曾把 `limits.transformer_capacity_kw` 也改成 420，**结果反而丢了告警**（关口被压到 373.3，差 0.65 kW 不过线） |

### 8.3 三条反直觉的实测（值得单独记）

1. **`soc_init` 取 0.80 反而造不出 SOC 告警**：实测 `soc_max` 从 0.80 充到
   **0.8801 就停了** —— 策略会充电，但规划终点就是 0.88，离告警线 0.895
   恒差 0.015。要告警只能让**开局值本身**落在告警区。
2. **两个变压器容量必须只改一个**：`tr_check_cap_kw`（告警用）与
   `limits.transformer_capacity_kw`（安全层用）都改成 420 后，安全层收紧
   把关口从 400 压到 373.3，`tr_load = 373.3 + 0.1×450 = 418.3`
   **差 0.65 kW 反而不过线了**。这是**设计内的降级**：安全层成功防住过载，
   于是过载告警不触发 —— 区分降级与故障，靠的就是这种差一点点的数字。
3. **散热失效窗要放在晚峰而不是中午**：中午光伏大发、策略本就不出力，
   降额落空；晚峰 19:00 负荷 450 kW、尖峰电价，正常日实测 max|cmd| 到过
   满功率 250 kW，降额才会真的削到指令。

|---|---|---|---|---|
| normal | FSM 7 | 0 | 0/0/0 | 0/0/0 |

### 8.5 两类不可达（不硬凑，如实标注）

- **GRID**：典型日全天 `pv < load`（光伏峰 300 @ 12:00，当时负荷 341），
  物理上不可能倒送。验证路径：`sim_demo --stress --csv <低负荷高光伏曲线>`。
- **SAFETY**：需设备侧限值运行期突然下降（`pcs_derate_ratio`「检修/老化」
  通道），属已挂账的「设备侧数据通道」缺口。
