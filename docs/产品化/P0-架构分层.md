# 产品化 P0：架构分层（算法 ↔ 设备解耦）

> 目标：让**算法**与**设备数据来源**彻底解耦。
> 一句话验收标准：**换数据源，不改算法**。
> 交付物：`04/src/device_io.h`（接口）+ `07/src/sim_device_io.h`（仿真适配器）
> + `07/src/memory_device_io.h`（点表适配器）+ `07/tests/test_device_io.cpp`（79 断言）。
>
> 状态：✅ 已完成。全量回归 **6736 断言全绿**（04:63 / 05:66 / 06:34 / 07:6050 / 08:444 / P0-P0.5:79）。

---

## 1. 为什么必须做这一步

改造前，`EmsRuntime`（周期 5/6/7/8 的总编排）**直接持有 `PlantModel`**：

```cpp
class EmsRuntime {
    PlantModel plant_{};                 // ← 编译期绑死
    RealtimeSnapshot rt = plant_.sample(t_);       // ① 采集
    double p_actual = plant_.step(cmd.p_bat_cmd_kw, dt_s);   // ⑩ 执行
};
```

这带来三个**致命**后果：

| 后果 | 具体表现 |
| --- | --- |
| ① 无法交付 | 现场调试时只能改源码把 `PlantModel` 换成真实驱动 —— 那不是产品，是实验室 demo |
| ② 测的不是跑的 | 单元测试跑 `PlantModel`，现场跑 Modbus/RT_DB，**两套代码路径**，测过的不等于要跑的 |
| ③ 回归面不可控 | 接一次 RT_DB 要动 05/06/07/08 四个模块，6594 条断言全部面临失效风险 |

**P0 就是切这一刀。** 它不是加功能，是**改结构**：把"算法依赖具体设备"改成"算法依赖接口"。

## 2. 接口设计（`04/src/device_io.h`）

```cpp
class IDeviceIO {
public:
    virtual ~IDeviceIO() = default;

    virtual bool        read_snapshot(Timestamp now, RealtimeSnapshot& out) = 0;  // ① 读量测
    virtual bool        read_limits(DeviceLimits& out)                     = 0;  // ② 读限制
    virtual DeviceStatus read_status()                              const  = 0;  // ③ 读状态
    virtual DeviceActuals read_actuals()                            const  = 0;  // ④ 读实际值
    virtual bool        write_command(const PowerCommand& cmd)             = 0;  // ⑤ 写指令
    virtual double      execute(double p_cmd_kw, double dt_s)              = 0;  // ⑥ 推进一拍
    virtual double      battery_capacity_kwh()                      const  = 0;  // ⑦ 静态参数
    virtual const char* name()                                      const  = 0;  // ⑧ 自检
};
```

### 2.1 四条不可违反的设计纪律

**纪律一：接口参数一律是业务语义结构体，绝不出现点名。**

接口签名里只有 `RealtimeSnapshot` / `DeviceLimits` / `PowerCommand` / `DeviceStatus`。
**没有** `"BMS_01.SOC"` 这种字符串。

为什么这条最重要：点名是**基础设施细节**。一旦算法里出现 `get_point("BMS_01.SOC")`，
点表定义就成了算法的编译期依赖 —— 换一个站（点表不同）就得改算法，分层立刻破产。
点名 ↔ 结构体的映射**只允许发生在适配器内部**（见 `memory_device_io.h` 的 `mem_point::` 命名空间）。

**纪律二：接口只表达五件事。**

读量测 / 读限制 / 读状态 / 写指令 / 推进一拍。没有"设置负荷""设置光伏"——
真实系统里负荷与光伏来自电表量测，**算法不得设置**。这两个能力只存在于仿真适配器上
（`SimDeviceIO::set_environment` / `MemoryDeviceIO::set_environment`），刻意**不在**接口契约里。

**纪律三：算法不得假设 `execute()` 的返回值是可信实际功率。**

- 仿真里 `execute()` 立即返回本拍实际功率；
- 真实系统里它只是"把指令发出去"，实际值要等**下一拍** `read_snapshot()` 的 `p_bat_actual_kw`。

因此闭环回路必须以 **① 的量测**为准，`execute()` 的返回值只用于本拍记录。
这条纪律现在写进了接口注释，避免以后有人在真实适配器上误用返回值做闭环。

**纪律四：关口功率只读「电表」，不得由其它三路推算**（2026-09-19 补，缺口 A2）。

`RealtimeSnapshot::p_grid_kw` 的真实来源是**关口电表**（`MEAS.P_GRID`）。
曾经 `RtDbDeviceIO::read_snapshot()` 用 `p_load - p_pv - p_bat` **推算**，
而记录路径读电表点 —— 同一路数据两个口径。为什么必须纠正：

- 真实系统里电表是**唯一权威计量点**。负荷/光伏/电池三路各有 CT/PT 精度、
  滤波与通信周期差异，**相减是把误差叠加而不是抵消**，且偏差随工况漂。
- 两个消费者都是**安全约束**：S05 防逆流（`surplus = p_grid_min - rt.p_grid_kw`）
  与变压器过载（`|p_grid| + 0.1·p_load`）。推算偏差直接变成**误动作或漏判倒送**。
- 现场症状："报表里 100 kW、防逆流却按 137 kW 动作"。

现在口径收敛成 `PlantModel::meter_p_grid()` **一处定义**（量测路径与真值路径都从它出），
`read_snapshot()` 三个适配器**统一读电表点**。

> ★ 这条纪律还有个**测试上的教训**：设备侧发布的 `MEAS.P_GRID` 恰好等于那个相减式，
> 所以"改成读电表"在**所有既有夹具下逐位恒等** —— 断言杀不死旧写法。
> 必须先造出**可观测差异**（可注入的电表系统偏差，默认 0）再谈修好。
> 详见 `CHANGES.md` §26 与 skill `bms-ems-module` §6.5。

### 2.2 顺带修正的一个语义含糊

`read_snapshot()` 的返回值约定为：**无论返回什么，适配器都必须填充 `out`**
（失败时填最近一次有效值，无历史值时填保守零值）。返回值仅作诊断提示，
数据是否可信以 `read_status().data_valid` 为准。

这样算法层**不需要为"采集失败"写分支** —— 故障语义统一收敛到 `detect_faults()` 里。
原来的实现里"采集"和"数据有效性"是两处独立判断，容易漏。

## 3. 适配器

```
                    ┌─────────────────────────────┐
                    │        算法层 (05/06/07/08)  │
                    │   EmsRuntime / SafetyEngine  │
                    │   / StateMachine / Coordinator│
                    └──────────────┬──────────────┘
                                   │ 只认识 IDeviceIO*
                    ┌──────────────▼──────────────┐
                    │      IDeviceIO  接口         │
                    └──┬────────┬────────┬────────┘
                       │        │        │
          ┌────────────▼──┐ ┌───▼──────┐ ┌▼─────────────┐
          │ SimDeviceIO   │ │ Memory   │ │ RtDbDeviceIO │  ← P3 之后
          │ (PlantModel)  │ │ DeviceIO │ │ / Modbus...  │
          │ 仿真/回归      │ │ (点表)   │ │ (现场)        │
          └───────────────┘ └──────────┘ └──────────────┘
```

### 3.1 `SimDeviceIO`（07/src/sim_device_io.h）—— 保真通道

把周期 7 的 `PlantModel` 包装成 `IDeviceIO`，**行为与重构前逐位一致**。

刻意采用**适配器模式**而不是让 `PlantModel` 直接实现接口：`PlantModel` 天然要提供
`set_environment` / `force_soc` / `set_pcs_fault` 这类"上帝视角"注入接口，这些**不属于**
接口契约。混在一起会让接口被仿真细节污染。分开之后有个额外好处 ——
**仿真专属接口被单独放在 `SimDeviceIO` 上，算法若误用它们，编译直接失败**，
让"越界"变成编译错误而不是运行期惊喜。

### 3.2 `MemoryDeviceIO`（07/src/memory_device_io.h）—— P0.5 的可换性证明

一个**纯进程内点表**适配器，不依赖 `PlantModel`：

- 内部是 `std::unordered_map<点名, 值>` —— 这正是 **RT_DB"共享内存 + 数据点表"的进程内等价物**；
- 点名 ↔ 业务结构体的映射全部发生在本文件内部（`mem_point::kSoc = "MEAS.SOC"` 等 32 个点）；
- 带 `miss_count()` 自检：读到不存在的点名会计数，便于发现拼写错误。

它存在的唯一目的是**证明 P0 的抽象是真的**，而不是一句设计口号。

### 3.3 后续适配器（不在 P0 范围内）

| 适配器 | 何时做 | 说明 |
| --- | --- | --- |
| `RtDbDeviceIO` | **P3 之后** | 对接共享内存实时库。**P0 明确不含 RT_DB** —— RT_DB 是多进程协调控制器方案，只有确认本系统要作为"协调控制器内的一个进程"运行时才需要 |
| `ModbusDeviceIO` | P3 | 设备侧通信（PCS/BMS/电表）。这是当前**唯一真正的功能缺口** |
| `Iec104DeviceIO` | P3 | 对外通信（EMS ↔ 调度/云端），基于 lib60870（注意 GPLv3 / 商业双授权） |

## 4. 验收：可执行的等价性证明

`07/tests/test_device_io.cpp` 的 **T21** 是这个交付物的核心：

```cpp
// 同一条 300s 环境脚本，分别驱动两个适配器
EmsRuntime rta;  rta.configure_plant(ideal_plant_config());  // A 路：PlantModel
EmsRuntime rtb;  MemoryDeviceIO mem;  rtb.attach_device(&mem); // B 路：纯点表
// 两条轨迹逐位比较
EXPECT_NEAR(max|Δp_cmd|,  0.0, 1e-9);
EXPECT_NEAR(max|Δp_actual|, 0.0, 1e-9);
EXPECT_NEAR(max|Δsoc|,    0.0, 1e-9);
EXPECT_NEAR(max|Δp_grid|, 0.0, 1e-9);
EXPECT(state 序列完全一致);
```

实测输出：

```
[T21] 适配器等价性（SimDeviceIO vs MemoryDeviceIO） ...
        等价性：maxΔcmd=0 maxΔsoc=0 maxΔgrid=0
```

**3000 拍、逐位一致（差值恒为 0）。** 为了让"一致"有意义，测试还断言两条轨迹
**都不是恒 0 的假一致**（`max|p_cmd| > 10 kW`、SOC 确实演化过）。

四个测试的分工：

| 测试 | 验证什么 |
| --- | --- |
| **T21** 适配器等价性 | 换数据源不改算法（逐位一致） |
| **T22** 点名 ↔ 结构体映射 | 写指令入点表 / 从点表装配快照 / 限制点 / 执行动力学 / 故障 fail-safe |
| **T23** `attach_device()` 生效 | 换适配器后限值随之改变（PCS 200kW → 50kW，指令被卡在 50kW） |
| **T24** 点表自检 | 32 个点齐全、闭环 200 拍无缺失点读取 |

## 5. 现场怎么用

`EmsRuntime` 保留了 `plant()` / `configure_plant()` / `set_environment()`，
**仅用于兼容既有 6594 条断言**，它们是仿真专属。生产代码请用 `attach_device()`：

```cpp
EmsRuntime rt;                    // 默认挂 SimDeviceIO（仿真）

// 现场部署：
ModbusDeviceIO dev(cfg);          // 或 RtDbDeviceIO / 未来任意适配器
rt.attach_device(&dev);           // 此后算法只经 dev 读写设备
rt.apply_configs();
while (running) {
    StepRecord r = rt.step(0.1);  // 算法一行未改
}
```

`attach_device()` 会同步刷新 `dev_`（设备限制）并更新优化协同层的设备参数 ——
否则优化层仍会用旧设备的额定/容量做 96 点规划，与实时层不一致。
