二改动明细：改了什么 · 为什么这么改

2.1 新增 11/：跨进程系统级联调

改动为什么
新增 3 个可执行进程（初始化器 / 设备侧 / EMS 侧）+ 测试 T41~T49（151 → 152 断言） 此前每个模块的测试都是「自己和自己对答案」——数据是夹具造好直接喂进去的。跨进程读同一块共享内存，是夹具替不了的那一段，必须真起进程才能验
点区纪律写进测试：设备侧只写 MEAS/STA/CFG，不碰 CMD，也不碰 EXT 三个写入者（设备侧 / EMS 侧 / 网关）各写一段互不重叠的地址。这个边界一旦破了，故障现象是「数据莫名其妙被改」，根本追不到源头 —— 所以要有一条断言专门守着它
T47 并发判据：从「降级必须恒为 0」改成四层判据 见下面 2.4 与 6.2，这是本轮最有代表性的一个判据缺陷

2.2 新增 12/：最终验收（交付门禁）

七维度 55 项检查：A1 功能 9 / A2 策略 9 / A3 安全 11 / A4 性能 5 / A5 稳定性 7 / A6 多策略协同 8 / A7 文档 6。

改动为什么
验收器产出正式报告 ACCEPTANCE-REPORT.{md,json,html}，而不是只印几行日志 验收结论要能给第三方复核。报告是产物，日志是过程 —— 产物需要能被引用、被归档、被逐条追溯
检查项里凡涉及点数的，从真相源派生（EMS_POINT_COUNT），不手抄数字 点表从 32 扩到 40 时，手抄的「32 点表自检」标题没跟着变，而证据行已经是 40 —— 让它结构上不可能过期，比每次记得改更可靠

2.3 新增 13/：Modbus TCP 设备接入（09-20 新模块）

现场设备（BMS / PCS / 电表）走 Modbus TCP。这一层的关键词是「跨语言」：设备侧模拟器是 Python（pymodbus），EMS 侧是 C++。

改动为什么
测试分三层：协议层 T01~T15（223）/ 适配器契约 T21~T30（133）/ 跨语言对账 T40~T47（83，需 Python） 三层各自能独立失败，才能一眼看出「是协议写错了、还是适配器接错了、还是两边理解不一致」
必须有外部对端（真 pymodbus），不能只用自己写的 Python 模拟器 自己写两端 = 自己和自己对答案，双方同时理解错也能「对得上」。用第三方库当对端，才有独立参照
环境缺失时 SKIP 而非 FAIL，但必须显式宣布自己 SKIP 了（总是打印 SKIPPED=n） 原来只在 skip 时才打印，于是「跑了」在日志里没有正面证据，和「没跑 / grep 写错 / 日志被截断」无法区分。把「没验」写成「验过」是这一行最危险的失败方式

2.4 A3 缺口：外部设定（调度遥调）落进安全链

分两步：A3.1 通路（能落到地方）→ A3.2 语义（落到地方之后，安全引擎怎么用）。

改动为什么
A3.1：点表 32 → 40 点，纯追加，新增 EXT 点区（8 点）+ 网关落点 + 接口 IExtSetpointSink 而点表索引就是运行时坐标 → 插入点会让所有已有点的地址平移，等于全系统错位。只能追加在末尾
接口只提供六个具名 setter，没有「按索引写 / 按点名写 / 批量写」入口 把边界写进类型里：网关想写 CMD.* 不是「不允许」，而是写不出来。运行期白名单校验此前已失手两次，编译期约束更硬
一区一个 SEQ + 一个 TS，发布时序号前后各递增一次 共享内存只保证「单点不撕裂」，而「上界+下界+设定」是一组要同时生效的量。中间态可能比两端都宽（新的上界配旧的下界）—— 只递增一次挡不住「读的过程中正在变」
失效兜底做两条正交判据：网关断开时清空（快路径）+ EMS 侧看时标是否过期（兜底） 网关进程被强杀时「清空」这段代码根本不会跑 → 最后一条设定会永远生效。兜底不能只靠写者还活着
A3.2：接进安全引擎，成为第 10 条约束，位置在「9 条收敛之后、区间矛盾检查之前」 外部设定只会收紧区间，但收紧本身可能制造矛盾（调度限放 50 kW，而本地防逆流要求放电 ≥100 kW）。放在矛盾检查之后，这个矛盾就会被漏判成「正常」
A3.2：拍板「停机/闭锁 stale 后粘住，功率设定不生效」 安全不对称：丢「停机」会丢安全，粘「停机」只丢钱。调度让停机的理由本地看不到，网关失联后自动复机可能违背安全意图；而粘住只是停在 [0,0]（少赚钱、零风险）

2.5 转发表外置 CSV

改动为什么
IEC104 的 CA/IOA 映射从编译进程序改成可加载 --point-map <file>，失败自动回退内置默认表 转发表是每个现场不同的。让现场为了改一个 IOA 去重编 C++ 不可接受 —— 现场没有编译环境，改完还得过一遍测试
加载后走和内置表完全同一套自检规则；任一条不过就整体回退，绝不「加载一半就开始跑」 外置表如果不校验，它就变成了新的错误来源；「一半生效」比「整体不生效」难排查得多
随程序提供样例 CSV，与内置默认表互为镜像（测试逐字段对账） 样例文件和编译进去的兜底如果不一样，现场按样例改就会踩坑。对账让「谁改了一边」立刻露馅

2.6 顺手清扫（三遍）

  • 第一遍：点表扩容后 grep "32 点" → 抓到 2 处会印进正式报告/联调报告的过期标题。
  • 第二遍：全仓审计 30/27/29/32 点 共 115 处 / 22 文件 → 真过期只有 27 处，其余指的是别的表（13/ 的「32」是设备侧绑定数、P3/ 的「30」是映射表子集）。
  • 第三遍：全项目复核 13 张「未做/遗留」清单 → 8 处过期（含一条已交付的缺口仍挂在「未做」栏）。
关键教训：清扫前必须先分类，不能全局替换。 本项目里同一个「32 点」有两种含义 —— 无脑替换会把 A 文件改对、把 B 文件改错。 另外修法优先改结构（改成派生、或干脆去掉硬数字写成「全点表」），只改数值等于下次一定重犯。

5.3 复核时新发现：从根目录跑测试会「假红」

复核中先是在仓库根目录直接跑 P1/build/test_config.exe 和 10/build/test_sim_24h.exe，分别报 165/6 与 126/12 失败。 换到模块目录下再跑，立刻变成 171/0 与 144/0。

根因是这些用例读写相对路径的产物（配置 JSON、导出文件），工作目录变了，读写地址就变了。 值得记一笔的是它的失败形态：|读回值 − 写入值| = 5.5 > 1e-12（2 vs 7.5） —— 看起来像一个真实的产品缺陷（写入 7.5 读回 2，像是回退到了默认值）， 很容易被当成回归去查代码。「假红」和「假绿」一样危险，只是方向相反。

纪律（本轮新增）：单独跑测试可执行文件必须在对应模块目录下执行（与 build_all.bat 的行为一致）； 从仓库根目录跑出来的失败，先怀疑工作目录，再怀疑代码。

六测试抓到了什么：三类问题

6.1 产品缺陷（测试真的拦住了）

序缺陷为什么危险 / 怎么发现
1 发布协议缺「写之前也递增序号」
EXT 点区		 共享内存单点不撕裂，但一组量会读到「新的上界 + 旧的下界」，中间态可能比两端都宽。单点写入看不出问题；只有一次写 6 个点的清空操作才暴露。末次递增只挡「读完之后才变」，挡不住「读的过程中在变」

3 「一个检查项自己和自己矛盾」
正式验收报告		 标题写「32 点表自检」，证据行是按真相源派生的「点数=40」。断言不会红，因为技术上它是对的 —— 错的是文案，而文案会跟着报告交到客户手里
4 SKIP 了却仍印「三层测试全部通过」
13/ 跨语言层		 最外层结论行是假的 —— 把「没验」写成了「验过」。这是静默失败的教科书形态：不报错、退出码 0、结论行还是正面的
5 心跳行永远印 T+0s 换算单位写错。修法不是改个除数，而是把换算抽成可被断言覆盖的纯函数 —— 不可断言的计算，改多少次都可能再错
6 禁用位、禁充放位通路级失效
A1 / A2 缺口		 BMS 的禁充/禁放位没有接进安全链；关口功率口径不一致。都是「看起来在跑、实际没生效」那一类

另有 13/ 模块内 6 个、P3/ 6 个静默出错类缺陷（协议细节、点表、容量边界），详见 CHANGES.md §27 / §11。

6.2 测试自己出错：假绿与假红（这一类最值得记）

序问题教训
1 T47 断言 stale == 0
全量构建下红了一次（降级=22 / 106 万次读），同一二进制单跑恒为 0		 这条判据测的是「机器闲不闲」，不是「代码对不对」。stale 的语义是「保留上次有效值 + 品质置不可信」，属设计内降级。→ 改成四层判据（碰撞>0 / 降级<碰撞 / 量级 / 硬判据），并刻意不调大重试次数 —— 那只是把假红推远
2 并发用例「空跑」
300 次快照一次都没被对账过，看着「零违规」，实际什么都没检查		 写者「先提交再记账」，而读者能拿到稳定窗口的时刻恰好就在记账之前。「没报违规」与「查过之后没违规」是两件事 → 改成按公式预推期望值 + 覆盖率守卫（已对账数 == 可用数，本次实测 300/300）
3 断言适用范围写错
断言「±1e9 哨兵对任意区间都是恒等元」，用 ±1e30 当初始区间 → 2 条红		 真相是 1e9 确实会裁剪 ±1e30 的区间。不要为了消红去调大魔数 → 改成「对量级正常的区间是恒等元」，并把前提本身也断言下来
4 覆盖率不足的循环
T76 的遍历误把序号/时标点也算进载荷点，实际只覆盖了 6 个点		 断言数看着对，覆盖面悄悄缩水。并发/覆盖型用例必须自带守卫
