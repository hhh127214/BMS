## 1. 三个角色边界，以及为什么网关是"第五个角色"

RT_DB 共享内存段上原本有四个角色，各写各的区：

| 角色 | 写 | 读 |
| --- | --- | --- |
| 设备进程 | `MEAS.*` / `STA.*` / `CFG.*` | `CMD.*` |
| EMS 进程 | `CMD.*` | `MEAS.*` / `STA.*` / `CFG.*` |
| 初始化器 | （只建段 + 注册点表） | — |
| **P3 网关** | **什么都不写** | **全段只读** |

网关是第五个角色，而且是唯一一个**纯读者**。

**为什么网关不能写 `CMD.*`。** 最省事的做法是"调度发遥控 → 网关直接写
`CMD.P_BAT` → PCS 执行"。三行代码就能跑通，联调时看起来完全正常。
但它把 `05/` 安全约束引擎整个绕过去了：调度的设定值不再经过
SOC 上下限、PCS 限功率、变压器容量、变化率这一整套收敛，
**等于让远端能直接驱动 PCS**。设计方案 §十一「安全优先级最高」直接不允许。

所以命令的路径被拉长成：

```
调度 ASDU ──► Iec104Server::on_asdu ──► ICommandSink::on_command
                                              │  （返回值决定肯定/否定确认）
                                              ▼
                                        装配层裁决
                                              │
                                    （未来）EXT 点区 ──► 安全引擎
```

**这条纪律用类型表达**：`RtDbReadOnlySource` 只实现 `read()`，
**没有 `write()` 方法**。不是"约定不要写"，是想写也写不出来 ——
下一个改这个文件的人（可能是三个月后的自己）不会"顺手加一个写方法"。

同理，`IDataSource::read()` 被标成 `const`：读操作不该改数据源状态，
统计计数用 `mutable`。`const` 在这里不是装饰，是接口契约。

## 2. 为什么数据源要抽象成接口

```cpp
class IDataSource {
    virtual bool read(const char* point, double* out, Quality* q = nullptr) const = 0;
};
```

两个实现：`RtDbReadOnlySource`（生产，读共享内存）和 `MemorySource`（测试，读内存表）。

**收益是"协议层可以脱离共享内存单独测"**：T61~T68 全部 165 条断言
**不需要 RT_DB、不需要初始化器、不需要多进程**，两秒跑完。
反过来，RT_DB 适配器也能脱离协议层单独验证（点表自检）。

这是 `04/` 的 `IDeviceIO` 思路在网关侧的复用 ——
**同一份网关代码换个数据源就能喂不同的实时库**。

代价是多了一层虚函数调用（每点每拍一次）。在一个 5 s 周期、30 点的
场景下完全无所谓；如果哪天真到了毫秒级，再把这层拿掉。

## 3. 品质三态：一次签名变更的取舍

`read()` 的第二/三参从 `bool* quality_ok` 改成了 `Quality*`。
**这是对已有接口的破坏性变更**，改了三个文件（`iec104_server.h`、
`rtdb_source.h`、`tests/test_iec104.cpp`）。值得吗？

值得。理由在 `README.md` §5.2 写全了，这里只补一个决策角度：
**bool 的语义是"好/坏"，而现场需要的是"能用/别用来做决策/没有"三态。**
把三态压成两态，不是"信息少一点"，而是**必须选一个更差的表达**：

- 压向 IV：主站把 5 秒前的真实值显示成"没数据"（画面闪断）；
- 压向 GOOD：主站拿陈旧值当实时值（最危险）。

而且这条信息在根源就有（RT_DB 的 `QUALITY_UNCERTAIN`），
网关只是**不该把它丢掉**。所以这不是"多加一个状态"，
是"不要在一层转发里丢信息"。

## 4. RT_DB 点表缺口：BMS 限值没有真实来源

**现状**：IOA 4017 / 4018「BMS 充电限值 / 放电限值」映射到
`CFG.BMS_CHG_LIM` / `CFG.BMS_DIS_LIM`，但这两个点在
`07/src/rtdb/ems_point_table.h` 里**是仿真的注入点，不是真实采集点**。

**问题**：BMS 的充放电限功率**只能由 BMS 自己算出来**（电芯温度、
单体压差、SOH、SOC 区间都会收紧它），EMS 不可能推导。真实系统里
它必然来自 BMS 通信（CAN / Modbus / 厂内协议）。而现在：

```
仿真：CFG.BMS_CHG_LIM 由 DeviceSideSim 写死 → EMS 读 → 策略用
真机：？（没有人写这个点）
```

**若不补的后果**：EMS 会读到默认值（点表默认 200 kW），
于是"BMS 说要降到 50 kW"这件事**永远不会传进来**，
策略会持续按 200 kW 计划 —— 直到 BMS 直接切断。
这是安全等级最高的一类缺口。

**方案**（接真机前必须做）：

1. `07/` 的 BMS 适配器（真实通信驱动）把实测限值写进 `CFG.BMS_CHG_LIM` / `CFG.BMS_DIS_LIM`；
2. 增加 `STA.BMS_LIM_VALID` 状态位 —— **限值无效时必须能被识别**，
   否则"通信断了"会退化成"限值是默认值"，比读到 0 更危险；
3. `05/` 安全引擎把「BMS 限值无效」映射成 **DERATED**（可自恢复），
   而不是 EMERGENCY（需人工复位）—— 与「区间矛盾 ≠ 紧急」同一条原则。

在本轮里，这个缺口**只能靠文档暴露**，不能靠代码兜住。

## 5. 六个下行点的落点：EXT 点区（A3.1 已交付，2026-09-20）

**交付前的行为**：6 个点（6001~6004 遥调、5001~5002 遥控）在 `download_table()`
里 `src = ""` —— RT_DB 没有"外部设定"区。网关把命令交给 `ICommandSink`，
装配层**默认一律否定确认**。

**为什么默认拒绝而不是接受**：没有落点却回肯定确认 = 调度以为命令生效了。
**这比拒绝危险得多。**

### 5.1 让步的边界：写在类型里，不是写在注释里

网关原先的纪律是"第五个角色、全段只读"（`RtDbReadOnlySource` 没有 `write()`）。
A3.1 让步的方式是**另给一个类型**（`P3/src/ext_setpoint_sink.h`）：

```cpp
class IExtSetpointSink {          // ★ 只有六个具名 setter
    virtual bool set_p_setpoint(double kw,     std::string* err) = 0;
    virtual bool set_upper     (double kw,     std::string* err) = 0;
    virtual bool set_lower     (double kw,     std::string* err) = 0;
    virtual bool set_d_target  (double kw,     std::string* err) = 0;
    virtual bool set_pcs_onoff (bool   on,     std::string* err) = 0;
    virtual bool set_ems_enable(bool   enabled, std::string* err) = 0;
    virtual bool clear_all     (std::string* err) = 0;
};
```

接口里**不存在**"按索引写 / 按点名写 / 批量写"这类入口。所以
"网关写 `CMD.*`"不是"不允许"，而是**写不出来** —— 与 `RtDbReadOnlySource`
用"没有 write()"表意是同一手法。

为什么不做成"允许写 EXT 区"的白名单式 `write(point, value)`：
**白名单是运行期校验，具名方法是编译期约束**。本项目在 A1/A2 上反复吃过
"写在注释里的约束没人守"的亏。

三个写入者至此定型，点区互不重叠，由 `ems_point_zone_of()` +
各自 `self_check()` 守着（不靠注释）：

| 写入者 | 点区 |
| --- | --- |
| `RtDbPointWriter`（设备侧） | MEAS / STA / CFG |
| `RtDbDeviceIO`（EMS 侧） | CMD |
| `RtDbExtWriter`（网关） | **EXT** |

### 5.2 点表：8 个点，不是"6 + 12"

| 点名 | 默认值 | 用途 |
| --- | --- | --- |
| `EXT.P_SETPOINT` | 0.0 | 有功功率设定（IOA 6001） |
| `EXT.P_UPPER_SET` | +1e9 | 允许上界设定（IOA 6003） |
| `EXT.P_LOWER_SET` | −1e9 | 允许下界设定（IOA 6004） |
| `EXT.D_TARGET` | 0.0 | 契约需量设定（IOA 6002） |
| `EXT.PCS_ONOFF` | 1.0 | PCS 远程启停（IOA 5001） |
| `EXT.EMS_ENABLE` | 1.0 | EMS 投入退出（IOA 5002） |
| `EXT.SEQ` | 0.0 | **区级**写入序号（发布信号） |
| `EXT.TS` | 0.0 | 最后一次写入的墙钟秒（陈旧判定） |

**★ 为什么是"区级一个 SEQ/TS"而不是"每点一个"**：EXT 区保存的是
**当前外部设定的状态**（电平语义 —— 最新值持续生效），不是命令队列。
逐点 TS/SEQ 唯一多出来的能力是"分辨哪一条命令变新了"，那对应**事件语义**，
与设定语义不匹配，而且是 3 倍的点数与出错面。

**★ 默认值必须落在"不引入新约束"那一侧**（与 A1 把禁充放位默认成 0 同一条纪律）：
`EMS_ENABLE` 默认取 **1** —— 若取 0，"调度还没发过任何命令"就等于
"调度闭锁了 EMS"，冷启动只监视不调节。`P_UPPER_SET/P_LOWER_SET` 取 ±1e9
（与 `CFG.PCS_RAMP_KW_PER_S` 同款"极大数 = 不限制"约定）。
**注意 ±1e9 不是数学上的无界**：量级更大的区间会被它收窄（T69b 把这条前提
也断言了）。现场权限区间受 PCS 额定功率约束，在 1e2 量级，绰绰有余。

### 5.3 发布协议：区级 seqlock，**前后各递增一次**

`rt_db_set_value` 只保证**单点**不撕裂。而"上下界 + 设定 + 时标"是一组应当
同时生效的量：逐点读可能读到"新的上界 + 旧的下界" —— 对安全区间来说，
**中间态可能比两端都宽**。

```
写者：SEQ = ++n（开始，读者从此刻起拿不到一致快照）
      写载荷
      写 TS
      SEQ = ++n（提交）
读者：s0 = 读 SEQ → 读载荷 + TS → s1 = 读 SEQ
      s0 == s1 且 s0 为偶数  →  可用
```

**★★ `begin` 那一次递增不能省 —— 这是 A3.1 写测试时发现的真缺陷。**
只在末尾递增的话，下面这条时序会被误判成"一致"：

```
读者读 s0 = 7（写者还没开始）
写者开始写载荷（一次一个点，中间态是新旧混合）
读者在写者提交**之前**读 s1 = 7        ← 等于 s0
→ 判定"一致"，但载荷是混合的
```

也就是末次递增只挡住"读完之后才变"，挡不住"读的过程中在变"。
单点 setter 看不出问题，`clear_all()` 一次写 6 个点是真正的撕裂点。

**奇偶为什么也要看**：往返递增后稳定态恒为偶数、写入中为奇数。写者慢的时候，
读者的 s0 与 s1 可能都落在**同一个奇数窗口**里（相等但正在改），必须拒绝。
两条判据各挡一半：**相等**挡"快写者"，**偶数**挡"慢写者"。

**★ 重试耗尽 ≠ "数据不可信"**，而是"本拍没有一致快照" → 处置是**本拍不施加
外部设定**（退回哨兵），而不是沿用"一半新一半旧"的值（见
`07/src/rtdb/ext_setpoints.h`）。

### 5.4 失效兜底：不能只靠网关

网关在"主站断开 / 空闲超时"时会 `clear_all()`。但**网关进程被 kill 时
没有任何人会去清** —— 最后一个设定会留在段里**永远生效**，而调度已经连不上了。

所以兜底判据必须在**消费侧**：

```
now - EXT.TS > stale_s   →   整区视为无效（usable = false）
```

这条判据**不依赖任何进程活着**。两条判据正交：

| 判据 | 位置 | 覆盖 |
| --- | --- | --- |
| 主站断开 / 空闲超时 → `clear_all()` | 网关 | 快路径（让状态早点变对） |
| `now - EXT.TS > stale_s` | EMS 侧 | **兜底**（网关死了也成立） |

两个容易写反的边界（T71 有断言）：
- **时标来自未来**（`now < ts_s`）必须判不可用，否则一个未来时标会让
  "陈旧判定"**永远不成立**，等于把兜底关掉。
- **`stale_s <= 0` 的含义是"禁用外部设定"（视为总是陈旧）**，不是
  "禁用超时判定" —— 前者的失效方向是安全的。

### 5.5 `clear_all()` 的语义：写哨兵，**不是**把 SEQ 归零

SEQ 表示"本区被改写过多少次"。归零 = 让它在读者眼里**倒退**，而"倒退"与
"没变化"在"要不要重新处理"这个判据上不可区分。所以清空 = 把六个载荷写回
`EMS_POINT_DEFAULTS`（一处定义 + 两个消费者），SEQ 照常递增。

清空后读侧**仍然 usable** —— "无约束"是一个**有效**状态，不是失效。
失效必须是另一条独立判据（陈旧）；两者合并会让"清空"被误当成"坏了"。

### 5.6 6001 的语义：方向感知的单侧收紧（A3.2 接线，语义已钉住）

```
正设定 S  →  只收紧上界：p_upper = min(p_upper, S)
负设定 S  →  只收紧下界：p_lower = max(p_lower, S)
6003/6004 →  方向固定：上界设定只压上界，下界设定只抬下界
5001/5002 →  关 → 强制 [0, 0]
```

**为什么不是对称幅值带 `[-|S|, +|S|]`**（字面上更贴"我希望在 100 kW 以内"）：
对称带会把**反方向**也锁死。光伏大发 / 谷时充电时，调度一个 `+100` 会把
充电压到 `-100` → 可能制造 `interval_contradiction` → DERATED ——
那等于**用安全层造出一个假降额**（本项目已把"区间矛盾 ≠ 紧急"列为纪律）。
反方向该由 6004 显式表达，而不是被 6001 顺手带走。

**为什么不是"直接写 p_desired"**：`p_desired` 是**期望**，不构成安全约束。
写成 desired 等于调度的设定可以绕过 L0（SOC 上下限 / BMS 限值 / 变压器容量），
违反设计方案 §十一「安全优先级最高」。

★ 三个"只收紧"的来源合起来用 `min`/`max`，所以**结构上不可能放宽**。
`usable() == false` 时区间**逐位不动**（不是"收一半"—— 那在数据上与
"收到一个很窄的设定"不可区分）。

**A3.1 只交付通路，不接线**：`narrow_interval_by_ext()` 已实现且有测试（T72），
但**没有任何生产路径调用它**。接线（`05/` 加第 10 条约束 + 装配层调用）
是 A3.2 的内容。

### 5.7 ★ 已拍板（A3.2）：stale 时"停机 / 闭锁"**粘住**，功率设定**不生效**

2026-09-20 拍板：`usable() == false`（含 stale）时，**"停机 / 闭锁"（5001 / 5002）粘住**，
功率设定（6001~6004）**不生效**。

- 安全不对称：丢"停机"会丢安全（调度让停的理由往往本地看不到 —— 电网紧急 / 检修 /
  非 BMS 消防联动），粘"停机"只丢钱（`[0,0]` 对储能永远是安全的静止态）。
  失效方向该朝"少自由度"倒，与不变式"上层只收紧"同一条逻辑。
- 为什么不是"整体粘住"：功率设定是**瞬态经济约束**，粘住会把一条过时收紧永久卡住。
- 粘住守卫 = `present && consistent && finite`（**不含** stale / band_ok）：
  - 不含 stale —— "旧"不是"坏"，调度的最后一条命令仍然作数；
  - 不含 band_ok —— 那是设定带的倒挂，与停机这条**独立命令**无关；
  - **必须含 finite** —— 一个 NaN 的 raw 值经 `> 0.5` 会判成 false，被误当"停机"，
    必须挡住。
- 落点：`07/src/rtdb/ext_setpoints.h` 的 `narrow_interval_by_ext()`；断言在 T72 第 ⑧ 条
  （P3）与 05/ 的 T07。

## 6. 转发表外置：从"改代码"到"改数据"

**✅ 已交付（2026-09-20，见 `CHANGES.md` §33）**。下文是设计定稿，实现与之一致。

**升级前**：`iec104_point_map.h` 里的表是 `static const PointDef kTable[]`，
**换转发表要重编**（先跑通链路的临时决定）。

**为什么这必须升级**：IEC104 的 CA/IOA 表是**调度下发**的，每个现场不同。
让现场为了改一个 IOA 重编 C++ 是不可接受的 —— 现场没有编译环境，
而且改完还得过一遍测试。

**目标接口**：

```cpp
// 加载成功返回 true；失败时保留默认表并在 report 里写清楚哪一行错
bool load_point_map_csv(const char* path, std::string* report);
```

**CSV 格式**（与现有 `PointDef` 一一对应，方便双向导出）：

```csv
ioa,kind,group,name,src,scale,offset,unit,note
4001,MEAS_FLOAT,1,负荷有功,MEAS.P_LOAD,1.0,0.0,kW,
4005,MEAS_FLOAT,1,SOC,MEAS.SOC,100.0,0.0,%,
6001,SET_FLOAT,0,有功功率设定,,1.0,0.0,kW,映射到权限区间而非 p_desired
```

**加载时必须做的校验**（否则外置表会变成新的错误来源）：

1. **每一行都要过 `self_check()` 同一套规则** ——
   src 点名能在 `ems_point_table.h` 找到、IOA 唯一、区间正确、类型没搞反；
2. **失败时回退到内置默认表**，并把错误行号 + 原因输出到日志和退出码 ——
   绝不能"加载了一半"就开始跑；
3. `kind` 字符串大小写不敏感，未知值报错；
4. `scale = 0` 直接拒绝（`from_protocol()` 除零）。

**表数据的存放方式**：`load_point_map_csv()` 需要把 CSV 解析进一个
**可变的静态数组**，而不是现在返回 `static const PointDef*`。
所以 `upload_table()` 的签名要改成：

```cpp
const PointDef* upload_table(std::size_t* count);   // 返回当前生效的表（默认或已加载）
```

**实现要点（一个真实的坑）**：加载表的字符串不能直接存 `std::string` 进 `PointDef`
（`PointDef` 保持 `const char*`，改它牵连 5 个文件）。于是用 `PointMapStore{ vector<PointDef>
defs; deque<string> pool; }`，`defs` 里的 `const char*` 全部指向 `pool`。pool 用 `std::deque`
而不是 `std::vector`：**deque 在 push_back 时不移既有元素**（只失效迭代器），所以短串（SSO）
的 `c_str()` 不会因扩容而悬空 —— 若用 vector + push_back，SSO 短串指针会随扩容整体悬空。
最后 `std::move` 整个 store 换入，vector/deque 的移动构造保证元素地址不变，指针仍有效。

**影响面**：`iec104_point_map.h`、`rtdb_source.h::resolve()`、
`iec104_server.h` 的 `up_`/`up_n_` 初始化、`main_gateway.cpp` 加 `--point-map <file>`。
`self_check()` 不需要改（它本来就接 `report`）。

## 7. 累计量（电度）：为什么本轮不做

`Kind::kCounter` 在枚举里定义了，但 `emit()` 的 `add_point()` 里没有实现
（`default: break;`）。原因是累计量不是"再支持一种类型"那么简单，
它有三个额外要求：

1. **编码不是短浮点** —— `M_IT_NA_1(15)` 用 **BCR（二进制计数器读数）**：
   4 字节二进制计数 + 1 字节顺序号（SEQ） + 1 字节品质。
   值域和溢出语义与遥测完全不同（回绕时要靠 SEQ 判断"是溢出还是重启"）。
2. **语义是"累计"不是"瞬时"** —— 每次上送的是**累计值**，
   主站自己在两次之间做差算电量。所以不能套用变化死区
   （电量每拍都在涨，死区判定会失效），必须**周期性全量**上送。
3. **需要一个基准锚点** —— 电度表读数是设备侧累加的，
   EMS 和调度都不应该重新计算它。也就是说这需要一个**新的 RT_DB 点**
   （`MEAS.E_IMPORT` / `MEAS.E_EXPORT`），而 RT_DB 目前没有。
   和 §4 的 BMS 限值缺口是同一类问题：**没有源头**。

所以顺序是：**先在 RT_DB 侧把电度点建起来 → 再实现 BCR 编码与 SEQ 回绕处理**。
现在硬做只会做出一份没法验证的代码。

## 8. 分包与容量：算清楚，别写死

`max_ios_per_asdu()` 里把每个 IO 的字节数写成了一张表：

| Kind | 值字节 | 说明 |
| --- | --- | --- |
| `kMeasFloat` | 4 | 短浮点 |
| `kMeasScaled` / `kMeasNormalized` | 2 | int16 |
| `kSinglePoint` / `kDoublePoint` | 1 | 位串 |
| `kCounter` | 5 | 4 字节计数 + 1 字节 SEQ |

再统一加 `IOA(3) + 品质(1) + 时标(7，可选)`，帧头 `2 + COT + CA`。

**为什么现算而不是写死 16**：应用层参数（`sizeOfCA` / `maxSizeOfASDU`）
是**可以从配置改的**：CA 用 2 字节还是 1 字节、ASDU 上限是不是 249，
改了以后写死的 16 就会**静默越界**（`addInformationObject` 返回 false，
没有任何报错）。现算一次只花几个减法。

**踩过的具体例子**：18 个带时标遥测 = 276 字节 > 249，
不分包就会静默丢 2 个。现象是"总觉得有点没上去"，
最容易被当成数据源问题去查。

```
                05/ 安全约束引擎 ──► 04/ 仲裁器
                        ▲                  │
                        │            （未来）EXT 点区
                        │                  ▲
  ┌─────────────────────┴──────────┐       │
```

- **单向依赖**：`P3/` 依赖 `07/`（RT_DB 点表与品质枚举），

- **不产出被依赖的头文件**：`P3/` 与 `09/`~`12/` 同属"叶子层"，没有下游。
- **`11/` 是运行时的上游**：`rtdb_initializer.exe` / `device_side.exe`
  是网关的现场前置条件（段与数据来源）。

## 10. 一个待定的设计问题

**`--stale-ms` 该不该默认开？**

现在的默认是 `0`（关闭），理由是"阈值取错了会产生一堆假 NT，
而现场一旦学会忽略告警，告警就等于不存在"。

反对意见：设备通信断了以后**默认应该能被发现**，靠运维记得加参数是不可靠的。

**待定的折中**：默认开，但按**点名前缀分层**给阈值 ——

| 前缀 | 更新节奏 | 默认超龄阈值 |
| --- | --- | --- |
| `MEAS.` | 每拍 | 3 ~ 5 倍设备写周期 |
| `STA.` | 每拍 | 同上 |
| `CMD.` | 每拍（EMS 侧） | 同上 |
| `CFG.` | 上电 / 参数变更 | **不判**（静态参数） |

这样既默认有保护，又不会对静态配置量误报。
落地前需要先确认：现场的设备进程到底多久写一次 `CFG.*` ——
如果它也是每拍写，这一层分层就是多余的；如果只在启动时写，
那现在这个默认值就是**会产生假告警**的。

本轮不做，等现场确认写周期。
