# P3/ — 产品化 P3：IEC 60870-5-104 从站网关

> 依据：`docs/规划/模拟器与设备接入梳理.md` §「待办优先级」第 7 步 —— **对外协议：IEC 104（调度）**
> 第三方库：`vendor/lib60870`（lib60870-C v2.4.1，GPL-3.0，见 `vendor/lib60870/README.md`）
> 周期目标：**让电网调度 / 虚拟电厂平台能用标准远动协议读到这套 EMS 的可观可测数据。**

---

## 1. 这一层是什么

前面 12 个周期 + P1/P2 做的都是**站内**的事：把策略、安全、状态机、实时闭环、
优化调度装进一个能跑的 EMS。而站一旦并到用户的配电房里，**外面世界只认一种语言**：
电网调度主站发过来的 IEC 60870-5-104 报文。

```
              ┌──────────────────────┐
   调度主站 ──┤ TCP:2404  IEC 104    │
  (客户端)     │  CS104_Master        │
              └──────────┬───────────┘
                         │  ASDU（CA=1 + IOA）
              ┌──────────▼───────────┐
              │  P3 网关（本模块）    │   ← **只读**，站在系统最外围
              │  Iec104Server        │
              └──────────┬───────────┘
                         │  只读
              ┌──────────▼───────────┐
              │  RT_DB 共享内存段     │  ← 11/ 立起来的实时库
              └──────────────────────┘
```

**关键定位：EMS 是 IEC104 的从站（服务器），不是主站。** 调度是客户端，它来连我们。
这决定了三件事：

| | 后果 |
| --- | --- |
| 监听方是我们 | 端口、CA、IOA 表由**调度下发的转发表**定，不是我们说了算 |
| 数据方向是"我们报、它收" | 上送必须可信：**品质位比数值更重要** |
| 命令方向是"它发、我们执行" | 遥控/遥调是**外部写入通道**，必须过安全层，绝不能直连 PCS |

最后一条是本模块最硬的纪律。`RtDbReadOnlySource` **在类型上就没有 `write()` 方法** ——
不是"约定不要写"，是想写也写不出来。原因见 `src/rtdb_source.h` 顶部：
调度的遥控若直接落到 `CMD.*`，就等于绕过了 `05/` 安全约束引擎，
成了"远端能直接驱动 PCS"。

> **★ A3.1 让步了，但让步的边界同样写在类型里。**
> 网关原先对 6 个下行点**一律否定确认**（诚实，但调度真的控不了）。
> 现在另给一个类型 `IExtSetpointSink`（`src/ext_setpoint_sink.h`）：
> **只有六个具名 setter**，没有任何"按索引写 / 按点名写 / 批量写"入口 ——
> 所以"网关写 `CMD.*`"不是"不允许"，而是**写不出来**。
> 分区由 `ems_point_zone_of()` + `RtDbExtWriter::self_check()` 守着（不靠注释）。
> 完整取舍（发布协议 / 失效兜底 / 6001 语义）见 `docs/design.md` §5。所以命令只走 `ICommandSink` 交给装配层裁决。

## 2. 怎么跑

### 2.1 四种形态

| 形态 | 命令 | 用途 | 需要 RT_DB |
| --- | --- | --- | --- |
| 单元测试（协议） | `scripts\build_test.bat` | 自环（T61~T72，380 断言） | 否 |
| 单元测试（落点） | 同上（第 [3/3] 步） | T73~T76，121 断言，**会 reset 整个段** | 是 |
| 上电自检 | `build\iec104_gateway.exe --self-check-only` | 点表映射 + 段内点名可解析性 | 是 |
| 演示 | `scripts\run_gateway.bat` | 自检 + 监听 + 回环测试一条龙 | 是 |
| 生产（只读） | `build\iec104_gateway.exe --port 2404 --ca 1 --stale-ms 5000` | 对上开从站，**命令一律否定确认** | 是 |
| 生产（受理遥控） | 同上 `+ --ext-rt-db --ext-stale 300` | 受理遥控/遥调并落到 EXT 区（A3.1） | 是 |

> **落地模式的三档**（`main_gateway.cpp` 头部有完整说明）：
> 默认**一律否定确认** → `--accept-commands`（DRY-RUN，只记录）→
> `--ext-rt-db`（**真落到 EXT 区**，写成功才回肯定确认）。
> 两个开关同时给时取**更强**的那个 —— "以为在 dry-run 其实真落了"
> 是危险方向上的误解，反过来只是白跑。

> **`run_gateway.bat` 已实跑验证**（2026-09-19，首次执行）：一次跑通
> 「自检 → 监听 → 回环测试」，关键读数 = 上送 **24** 点 / 下行 **6** 点、
> 总召 `激活确认 2 / 激活终止 2` **成对**、命令 肯定 **2** / 否定 **0**、
> **坏点 0 点次**（无 `0x80`）、时标 `UTC+08:00`、分包 16+2。
> 顺带在这一跑里发现 §7.7 的心跳单位缺陷。

**RT_DB 段必须先存在，且初始化器必须常驻**：

```bat
11\build\rtdb_initializer.exe --seconds 600      REM 不能"跑完就退"！
```

Windows 上 RT_DB 段是页面文件映射对象，**最后一个句柄关闭即销毁**。
初始化器做成短命进程 → 它一退段就没了 → 网关连不上（Linux 无此约束，极易漏）。

### 2.2 参数

```
--port N          监听端口（默认 2404）
--ca N            公共地址 CA（默认 1，须与调度转发表一致）
--bind IP         绑定网卡（默认 0.0.0.0）
--seconds N       运行时长，0 = 一直跑（默认 60）
--periodic N      周期全量上报间隔秒（默认 5）
--deadband F      变化死区，相对量程比例（默认 0.002）
--utc-offset N    CP56Time2a 时区偏移小时（默认 8 = 北京时间）
--stale-ms N      数据超龄判据，超限置品质 NT；0 = 关闭
--accept-commands 受理遥控/遥调（DRY-RUN，只记录不落地）
--ext-rt-db       受理遥控/遥调并**落到 RT_DB 的 EXT 区**（A3.1 生产配置）
                  写成功才回肯定确认；失败回否定确认并带原因
--ext-stale N     外部设定空闲超时（秒，默认 300），超过则清空外部设定；
                  0 = 本进程不做，交给 EMS 侧按 EXT.TS 兜底
--dump-raw        打印原始报文帧（现场排障）
--point-map F     转发表 CSV（ioa,kind,group,name,src,scale,offset,unit,note）。
                  加载失败回退到内置默认表并报错
--self-check-only 只跑自检就退出
```

`--stale-ms` 的取值有讲究：**它要按"最慢的那个正常更新周期"来定**，
不是按最快的。实测踩过一次（见 §7.5）：`CMD.*` 三个点只有 EMS 进程写，
联调时没跑 `ems_side`，于是它们自初始化后就没更新过，3 s 一到全被判 NT。
这本身是**正确**的（"EMS 没在跑，别信权限区间"），但如果你不打算跑 EMS，
就应该把阈值调大或关掉。

## 3. 端到端实测基线

三进程 + 一个主站模拟器，验证"设备在跑"与"设备停了"两种工况
（日志：`P3/build/e2e/A.log`、`B.log`，可用 `scripts\run_gateway.bat` 复现）：

| 阶段 | 设备进程 | 品质位 | 值 | 含义 |
| --- | --- | --- | --- | --- |
| A | 运行中 | 全 `0x00` GOOD<br>（仅 `CMD.*` 三点 NT，因 EMS 未跑） | 实时变化 | 正常工况 |
| B | 已终止 + 等 5 s | 全 `0x40` NT | **冻结在最后一次好值** | `--stale-ms 3000` 生效 |

两阶段对比是**双侧证据**：只有 A 全绿不能说明 NT 通路活着，
只有 B 全 NT 不能说明 GOOD 通路没被误伤。两边都要有。

A 阶段同时验证：

```
[CONN] STARTDT 确认，数据传输已启动
-- 总召唤（站召唤 QOI=20）--
  <- 总召唤 激活确认
  <- ASDU type=13 COT=总召唤(20) CA=1 共 18 点      ← 遥测一次全上
  <- ASDU type=1  COT=总召唤(20) CA=1 共 6 点       ← 遥信
  <- 总召唤 激活终止（本次结束）                     ← 三段齐全（见 §4.1）
  <- ASDU type=36 COT=自发(3) CA=1 共 16 点
  <- ASDU type=36 COT=自发(3) CA=1 共 2 点          ← ★ 分包（18 点拆 16+2）
  <- ASDU type=30 COT=自发(3) CA=1 共 6 点
  <- 命令 肯定确认（已受理）                         × 2（遥调 6001 + 遥控 5001）

总召唤         : 确认 2 / 终止 2  (成对，正常)
命令确认       : 肯定 2 / 否定 0
```

时间戳是**北京时间**（`2026-09-19 18:12:43.558`），不是库默认的 UTC —— 见 §4.2。

## 4. 实测确认的库行为（四处与手册/常识不一致）

手册 `lib60870-IEC104-使用手册.md` 是本轮的主要参考，但实测发现四处偏差。
**都以实测为准**，因为它们都是"照着写就会错"的地方。

| 项 | 库实际行为 | 手册 / 常识 | 处理 |
| --- | --- | --- | --- |
| 从站 t0 超时 | **10 s** | 30 s | 文档更正，不影响代码 |
| CP56Time2a 口径 | **UTC（`gmtime`）** | 应北京时间 | `src/iec104_time.h` 扳回 |
| GI 的 ACT_TERM | **必须带一个信息对象** | §6.4/§6.9 漏写 | `serve_gi()` 修复，见 §4.1 |
| 带时标类型取值 | **无公开 getter** | — | 主站测试 include 内部头，见 §4.4 |

### 4.1 总召唤的 ACT_TERM 必须带信息对象

这是**唯一一个"完全照手册写就必然错"**的点。

总召唤的时序是异步的：回调里只登记 + 回 ACT_CON，数据在 `tick()` 里分批推，
最后发 ACT_TERM 收尾。问题出在最后那帧 —— 直觉上"终止帧没有数据"，
于是会去创建一个**空 ASDU**：

```c
CS101_ASDU a = CS101_ASDU_create(params, false, CS101_COT_ACTIVATION_TERMINATION, 0, ca, false, false);
IMasterConnection_sendACT_TERM(con, a);      /* ← 错的 */
```

空 ASDU 的 TypeID 是 **0**，而主站侧 `CS101_ASDU_createFromBufferEx` 会校验
TypeID 合法性 → **直接丢帧**。主站永远等不到终止，于是周期性重召 ——
从站侧看起来"总召唤一直有请求"，像主站有病，其实是自己发的帧不合法。

正确写法是给终止帧装一个总召唤命令信息对象（官方
`examples/cs104_server/simple_server.c` 就是这么写的）：

```cpp
if (InformationObject io = reinterpret_cast<InformationObject>(
        InterrogationCommand_create(nullptr, 0, gi_qoi_))) {
    CS101_ASDU_addInformationObject(a, io);
    InformationObject_destroy(io);      // addInformationObject 内部已复制
    ++st_.gi_act_term_sent;
}
IMasterConnection_sendACT_TERM(gi_conn_, a);
```

主站模拟器侧对应加了一条断言：**收到 ACT_CON 但没有 ACT_TERM 就报警** ——
这类"对端在等、我这边看着正常"的故障，不主动检查就发现不了。

### 4.2 CP56Time2a 是 UTC，要主动扳回北京时间

库的 `CP56Time2a_createFromMsTimestamp()` 内部走 `gmtime`，
**不做任何时区换算**。调度看到的时间会比实际早 8 小时。

`src/iec104_time.h` 的做法是在**入库/出库两端对称加减偏移**：

```cpp
make_local_cp56time2a(out, utc_ms)   { CP56Time2a_createFromMsTimestamp(out, utc_ms + off*1000); }
cp56time2a_local_to_utc_ms(t)        { return CP56Time2a_toMsTimestamp(t) - off*1000; }
```

**这个修法有个测量陷阱**：库的双向换算是**严格互逆**的，所以
"发出去再读回来，看是否相等"这种自环测试**永远恒等** —— 时标差 8 小时
也照样通过。T66 因此额外做了一次**外部真值对账**：
把 CP56Time2a 的字段拆出来，跟墙钟的 `gmtime(now + 8h)` 逐字段比。
写时区相关的断言，一定要有一个不经过被测代码的真值来源。

### 4.3 ASDU 249 字节装不下 18 个带时标遥测

ASDU 上限 **249 字节**。带 CP56Time2a 的短浮点每点占：

```
IOA(3) + 值(4) + 品质(1) + 时标(7) = 15 字节
帧头 2 + COT(2) + CA(2)           =  6 字节
```

→ `(249 - 6) / 15 = 16` 点/帧。本项目遥测有 **18** 个点，不分包就会
**静默丢 2 个**（`addInformationObject` 返回 false，但没人看返回值）。
现象是"总觉得有点没上去"，最容易被当成数据源问题去查。

`emit()` 里两道约束缺一不可：

1. **同一个 ASDU 只能装同一种 TypeID** —— 混装时库同样静默返回 false；
2. **按 `max_ios_per_asdu()` 分包** —— 这个值按当前应用层参数现算，不写死 16。

### 4.4 带时标类型没有公开取值接口

`M_ME_TF_1(36)` / `M_SP_TB_1(30)` 只有 `_create` / `_destroy` / `_getTimestamp`，
**没有 `_getValue` / `_getQuality`**。从站侧发得出去，主站侧要读值就只能
include 内部头 `information_objects_internal.h` 后按结构体读。

所以 `main_master.cpp`（对端工具）带 `-I .../src/inc/internal`，
**生产代码不需要**。这也是"对端工具"和"产品代码"的合理分界：
工具为了验证可以碰内部结构，产品不行。

## 5. 点表与品质

### 5.1 点表

**唯一真相源是 `src/iec104_point_map.h`**，上送 **24** 点 + 下行 **6** 点。
IOA 区间本项目自定（现场必须按调度转发表改）：

```
1001..1999  遥信      4001..4999  遥测
5001..5999  遥控      6001..6999  遥调      8001..8999  累计量
```

上送 24 点分四类：功率流（4001~4004）、电池状态（4005~4007）、
**EMS 决策含权限区间（4008~4010）**、设备与配置（4011~4018）、通信故障（1001~1006）。

其中 **4009/4010「允许功率上界/下界」是本项目的独有价值** ——
调度不只看到"现在发了多少功率"，还能看到"EMS 还允许调到哪个范围"。
一般厂家的 104 只上送功率值，调度要试探着下发才知道边界在哪。

**★ 下行的 6 个点从 A3.1 起有落点了**（`EXT` 点区）：

| IOA | 语义 | 落到哪个点 |
| --- | --- | --- |
| 6001 | 有功功率设定 | `EXT.P_SETPOINT` |
| 6002 | 契约需量设定 | `EXT.D_TARGET` |
| 6003 | 允许上界设定 | `EXT.P_UPPER_SET` |
| 6004 | 允许下界设定 | `EXT.P_LOWER_SET` |
| 5001 | PCS 远程启停 | `EXT.PCS_ONOFF` |
| 5002 | EMS 投入退出 | `EXT.EMS_ENABLE` |

**网关只能写 `EXT.*`，写不出 `CMD.*`** —— 这条边界写在类型里
（`IExtSetpointSink` 只有六个具名 setter），不是写在注释里。
为什么重要：调度遥控若直写 `CMD.*` 就绕过了 `05/` 安全引擎。
完整取舍见 `docs/design.md` §5。

换算系数（`scale`/`offset`）**必须写在表里**，不许散在代码中：
SOC/SOH 内部是 0..1，调度要百分数 → `scale = 100`。
散着写就一定会出现"有个地方乘了 100、有个地方没乘"的口径分裂。

`self_check()` 查 5 件事，都在 `--self-check-only` 里跑：
src 点名能否在 `ems_point_table.h` 找到、IOA 唯一、区间正确、group 合法、
上下行类型没搞反。

### 5.2 品质三态（本轮设计改动）

`IDataSource::read()` 的签名从 `bool* quality_ok` 改成 `Quality*`：

```cpp
enum class Quality { kGood, kNotTopical, kInvalid };
```

**为什么不用 bool**：IEC104 品质字节里 IV(0x80) 与 NT(0x40) 是两件不同的事。

| 源侧回答 | 上送品质 | 主站该怎么做 |
| --- | --- | --- |
| `Quality::kGood` | `0x00` | 正常使用 |
| `Quality::kNotTopical` | `0x40` NT | **照显示，但禁止据以决策** |
| `Quality::kInvalid` | `0x80` IV | 显示"未知"，告警 |

若退化成 bool，NT 只能二选一，两条路都错：

- 退化成 **IV** → 主站把"5 秒前的真实值"当成"没数据"，画面闪断；
- 退化成 **GOOD** → 主站拿陈旧值当实时值用，**这是现场最危险的一种错**。

而这条信息在源头本来就存在（RT_DB 的 `data_quality_t` 有 `QUALITY_UNCERTAIN`），
不该在网关这层被丢掉。另外 `--stale-ms` 走的是**同一个 NT 通路**：
设备通信断了以后点还在、值还是最后一次的好值，没有超龄判据的话调度看不出来。

### 5.3 品质跳变必须上报

`report_changes()` 不只在**值变化**时发，也在**品质跳变**时发（`prev_ok_[]`）。
原因：一个点从好变坏（比如 BMS 通信断了，`BMS_CHG_LIM` 读不出来）
本身就是最重要的信息。如果只在值变化时发，调度会一直拿着上一次的好值；
更糟的是读失败的点如果被 `continue` 跳过，连 INVALID 都收不到 ——
**这是最危险的失联方式：对端以为一切正常。**

## 6. 现场部署与多连接要点

### 6.1 绑定与白名单

默认 `--bind 0.0.0.0` 是为了联调方便。**生产必须收紧**：

```bat
build\iec104_gateway.exe --bind 192.168.10.20 --port 2404 --ca 1
```

`on_connect` 里有 `// TODO 现场：按调度主站 IP 白名单收紧` ——
目前任何能连到 2404 的客户端都会被接受。现场至少要:
① 绑到调度专用网段；② 防火墙只放行调度主站 IP；
③ 有条件时在 `on_connect` 里加 IP 白名单（`CS104_Slave_getConnectionParam` 可取对端地址）。

### 6.2 多连接

本项目用 **`CS104_MODE_SINGLE_REDUNDANCY_GROUP`**：只有一个活动连接，
所以 GI 会话状态（`gi_conn_` / `gi_state_`）用**单变量**存是安全的。

⚠️ **换成 `CS104_MODE_MULTIPLE_REDUNDANCY_GROUPS` 就必须按 connection 分桶**，
否则两个调度同时总召唤会互相踩。这是手册 §11 点名的坑，改模式前先改这里。

### 6.3 APCI 参数

库默认 `k=12 / w=8 / t0=10 / t1=15 / t2=10 / t3=20`。
`k=12` 表示"未被确认的 I 帧最多 12 个" —— 本项目周期上报 5 s 一次、
变化上报是事件驱动，12 足够。若现场把 `--periodic` 调到 1 s 且点数很多，
要留意 `k` 是否够用（不够会导致 TCP 层反复重传，表现为时标乱跳）。

### 6.4 GPL-3.0 授权（**必须走商务/法务**）

lib60870 是 **GPL-3.0**。静态链接的传染范围比动态链接大得多 ——
**本项目的做法是编成静态库 `lib60870.a` 直接链进 exe**，
这在 GPL 下通常意味着整个 EMS 二进制要按 GPL 发布。

三条可选路线，**本轮不做决定，交由商务/法务**：

1. 接受 GPL-3.0，整套 EMS 按 GPL 开源；
2. 向 mz-automation 购买商业授权；
3. 换实现（自研 104 从站，或换 BSD/MIT 许可的库）。

其余细节见 `vendor/lib60870/README.md`。

## 7. 本轮修掉的缺陷（都是"静默出错"型）

### 7.1 RT_DB 品质常量镜像写反 → 全部好点被判成坏点

**症状**：值全对（负荷 497.7、关口 294.6、SOC 50.0），品质位**全是 `0x80` IV**。
调度画面上 24 个点全灰，但这个系统的一切都"看着正常"。

**根因**：`rtdb_source.h` 里手抄了一份镜像常量 `kRtdbQualityGood = 0`，
而 `rt_db_structs.h` 的真值是 `QUALITY_GOOD = 1`。

**为什么难发现**：协议层忠实翻译源侧的话，看不出异常；
单元测试的 `MemorySource` 根本不走 RT_DB，全绿；自环测试也不碰品质真值。

**修法（三层）**：

1. 不再抄数字 —— 新建 `src/rtdb_quality.h` 直接引用 `QUALITY_GOOD`；
2. `static_assert` 对账：上游枚举一变，**编译期**就红；
3. 端到端加**外部真值对账**：主站日志里 `0x80` 必须为 0 条（§3 的双侧证据）。

### 7.2 `rt_db_structs.h` 的 C11 原子宏会破坏 libstdc++ 声明

引入 `QUALITY_GOOD` 时要 include `rt_db_structs.h`，结果撞出一堆怪错。
根因：该头为在 Windows 上模拟 C11 原子操作，定义了**函数式宏**：

```c
#define atomic_store_explicit(ptr, val, order) (*(ptr) = (val))
#define atomic_thread_fence(order) MemoryBarrier()
```

函数式宏的匹配**不看命名空间限定**，所以 libstdc++ 里
`std::atomic_thread_fence(...)` 这类**声明**会被就地展开，
编译器报的却是 `expected unqualified-id before 'sizeof'`，
错误全部指向 `rt_db_structs.h` 第 34 行 —— 跟真正出问题的地方隔着十万八千里。

**修法**：`rtdb_quality.h` 在 include 之后立刻 `#undef` 掉这些宏，
并加一道**前置检查**（`#error`）—— 谁把它 include 晚了（在 `<string>`/`<vector>`
等之后），就得到一个明确的错误，而不是一堆莫名其妙的报错。

### 7.3 计数自增早于载荷写入 → 观察者读到半成品

`on_clock_sync` 里 `++st_.clock_syncs` 排在 `last_clock_sync_text_ = buf` **之前**。
回调跑在库自己的线程上，观察者（测试、网管打印）跑在应用线程上，
惯用写法 `while (stats().clock_syncs < 1);` 再读文本 ——
计数先自增就让观察者有机会在载荷写入前通过检查。

**现象**：T66 偶发断言失败，看着像随机抖动，最难查的一类。

**修法**：把计数当"我前面写的东西都好了"的**发布信号**用 ——
先写载荷，`atomic_thread_fence(release)`，再自增。`on_asdu` 同样的两处也改了。

### 7.4 `char raw_dumped_` 溢出 → `--dump-raw` 反而刷满屏

```cpp
char raw_dumped_ = 0;
if (self->raw_dumped_++ > 200) return;   // 只想打前 200 帧
```

`char` 是有符号的，到 127 就回绕成负数，`> 200` **永远不再成立** ——
本想"只打前 200 帧"，结果把整场联调的所有帧全部刷出来，**正好和意图相反**。

**修法**：`int raw_dumped_` + 具名常量 `kRawDumpLimit`。
凡是用窄类型做计数器的都要查一遍。

### 7.5 `--stale-ms` 的语义边界（不是 bug，是使用纪律）

实测发现：`CMD.*` 三点在没有 EMS 进程时会全被判 NT。这是**正确行为**
（管理员该知道"权限区间没人发布"），但说明 `--stale-ms` **不能一刀切**：
它得按"最慢的正常更新周期"取，静态配置量若只在启动时写，要么调大阈值要么关掉。
后续若要精细化，可在 `PointDef` 上加一列 per-point 覆盖（本轮不做）。

### 7.6 `P3/scripts/build.bat` 里的 VT 控制字符

原有的 `-I ..vendor\...` 中，`v` 实际是一个 **VT 字符（0x0B）** ——
当年用 Python 批量改写脚本时 `"\v"` 被当转义序列解释了。这条 `-I` 与 `INC`
里已有的重复，所以 `gcc` 只发一条警告就继续，**错得毫无声响**。

**修法**：删掉冗余的 `-I`；并给 `scripts/fix_bat_encoding.py` 加了
**控制字符检测**（只报不改 —— 到底该是哪个字符只有人知道，
自动改只是把一种事故换成另一种事故）。

### 7.7 网关心跳 `T+` 恒为 0（单位换算）—— 首次实跑 `run_gateway.bat` 才发现

```cpp
const std::uint64_t t0 = now_utc_ms();               // 毫秒
std::printf("[T+%3llus]", (now - t0) / 1000000ull);  // 却按微秒除 → 头 1000 s 恒 0
```

网关跑 60 s，5 次心跳**全部**是 `[T+  0s]`。现场读起来只有一句结论："时钟卡住了"。
网关的设计工况是长期在线，所以这条心跳基本等于没有。

**修法不只是改除数** —— 把换算抽成**全工程唯一的 ms→s 换算口**
`iec104_time.h::ms_to_s()`，这样它就能被断言（T66 增 3 条：`60000→60` 正是这个 bug、
`999→0` 挡四舍五入、`3600000→3600` 挡量级）。修后实测 `[T+ 10s] [T+ 20s]`。

> **通用教训**：`/1000000`、`*1000`、ms/μs/ns 这类换算**不要散落在 `printf` 里**。
> 散落 → 无法断言 → 只能靠肉眼看日志 → 而"看日志"这件事在交付时一定被跳过。
> 抽成一个有名字的纯函数：代价 1 行，收益是它进了回归。

## 7.8~7.11  A3.1 新抓到的四个缺陷（都是"静默出错"型）

### 7.8 ★★ 发布协议少了"开始"那一次递增 → 半更新快照被当成一致的

**现象**：`clear_all()` 一次写 6 个点，读者可能读到"新的上界 + 旧的下界"，
而且**这个混合快照会被判定为"一致可用"**。

**根因**（时序）：

```
读者读 s0 = 7（写者还没开始）
写者开始写 6 个载荷（一次一个点，中间态是新旧混合）
读者在写者**提交之前**读 s1 = 7        ← 等于 s0
→ 判定"一致"，但载荷是混合的
```

原实现只在**末尾**递增 SEQ。末次递增只挡住"读完之后才变"，
**挡不住"读的过程中在变"**。单点 setter 看不出问题，多点写入才是撕裂点。

**修法**：`begin_publish()`（载荷写入前）+ `commit_publish()`（载荷写入后），
前后各递增一次 → 稳定态恒为**偶数**、写入中为**奇数**；
读者要求 `s0 == s1` **且** `s0` 为偶数（"相等"挡快写者，"偶数"挡慢写者，
两条各挡一半，缺一不可）。

**判据有效性反证**（`tests/test_ext_rtdb.cpp` T76c）：把 `begin_publish()`
挪到载荷写入**之后**（序号算术完全不变，只去掉保护）→
**2 次违规**，形态正是"新下界配旧序号"：

```
[违规] seq=66058 读到 (-16610.0, 49627.0)，该序号应为 (-16609.0, 49627.0)
[违规] seq=66602 读到 (-16746.0, 50035.0)，该序号应为 (-16745.0, 50035.0)
```

### 7.9 `.o` 缓存只判"存在"，不判"源文件有没有更新"

**现象**：点表从 32 点扩到 40 点后，`P3/build/ems_point_table.o` 仍是
**前一天**编出来的 32 点版本，而 `07/build/` 里的同名对象是当天新的 ——
**同名点表、两套内容**。编译期一个字都不说，运行期按名字找点直接失效。

**根因**：`P3/scripts/build.bat` 与 `13/scripts/build_test.bat` 里写的是
`if not exist build\ems_point_table.o (...)` —— 存在性判断只看文件在不在。
（`07/` `11/` `12/` 的脚本本来就是无条件重编，所以只有这两处中招。）

**修法**：去掉存在性判断，改成无条件重编（这几个 `.c` 很小，代价可忽略），
并在注释里写清"为什么不用缓存"。`P3/scripts/build.bat`、`P3/scripts/build_test.bat`、
`13/scripts/build_test.bat` 三处都改了。

**通用教训**：`if not exist x.o` 这种"手工 make"在**头文件驱动**的项目里
必然踩坑 —— 改的是 `.h`，编的是 `.c`，判断的却是 `.o` 在不在。

### 7.10 `present` 字段与它自己的注释不符

`ExtSetpoints::present` 的注释写的是"段里收到过任何一次外部设定（EXT.SEQ > 0）"，
但实现里在循环**之后无条件**写了 `out.present = true` —— 于是
"连 SEQ 这个点都读不到"（索引不存在 / 品质坏）也会报 `present = true`，
现场会显示"收到过设定、但快照不一致"，**指向完全错误的方向**。

**为什么难发现**：`usable()` 在两种情况下都是 `false`，所以**行为没变** ——
只有把它当诊断信息看的时候才是错的。（又是"注释声称的行为 ≠ 代码实际行为"。）

**修法**：加 `seq_readable`，只有真的读到过 `SEQ > 0` 才置 `present = true`；
T71 第 ⑩ 组有断言钉住。

### 7.11 测试自己出的两次"假绿"（判据有效性问题）

这两条不是产品缺陷，但都属于"**看着全绿、实际没验**"，所以一并记下：

| 假绿 | 表现 | 真相 |
| --- | --- | --- |
| **断言适用范围写错** | T69b 断言"±1e9 哨兵对任意区间都是恒等元"，用 ±1e30 当初始区间 → 2 条红 | 1e9 **确实会** clip 一个 ±1e30 的区间 —— 说明"无界"这个前提**不成立**。**不要为了消红去调大魔数**，改断言"对量级正常的区间是恒等元"+ 把前提本身也断言下来 |
| **并发用例空跑** | T76c 首版：可用 600 / 违规 0，看着全绿 | 600 次快照**一次都没被对账过**（记录表的写入总晚于读取）。改成"按公式预推期望值"+ 覆盖率守卫（`checked == usable_n`）才有意义。**"没报违规"与"查过之后没违规"是两件事** |

> **通用教训**：一条断言即使现在红着，也要问一句"**它红的是我以为的那个原因吗**"；
> 一条断言即使现在绿着，也要问一句"**它有没有可能什么都没检查**"。
> 覆盖率守卫（计数式断言）就是为后者准备的。
