# 21/ 设计推演 —— DL/T 645-2007 主站

> 本文只写**为什么这样切**，不重复"怎么跑"（见 `README.md`）。

---

## 1. 为什么切成三层：帧 / 数据项 / 传输

645 的错误分三类，**排查方向完全不同**：

| 层 | 出错表现 | 现场查什么 |
|---|---|---|
| 帧 | 对端不回、CS 错、半帧 | 线、波特率、校验位、网关分片 |
| 数据项 | 帧收到了、CS 也对，但数值离谱 | DI 表、字节数、小数位、符号位、变比 |
| 传输 | 连不上、端口占、串口打不开 | IP/端口、COM 号、驱动、权限 |

如果三层混在一个类里，一个"电压差 10 倍"的现象会同时触发"帧解析"和"数值换算"
两条怀疑路径，而日志里只有一句 `read failed`。**分层不是为了整齐，是为了让
失败能被归到唯一一类。**

切法：

```
dlt645_frame.h      地址 / DI / CS / +0x33      —— 只有字节
dlt645_codec.h      DI 表 / BCD / 符号位 / 变比  —— 才是"数"
dlt645_transport.h  怎么搬字节（内存 / TCP / 串口）
dlt645_master.h     事务：清缓冲 → 发 → 收 → 判
```

## 2. 显示序 vs 传输序：把反转关进两个函数

645 里"反不反"取决于字段，而**界面上写的一定是自然写法**：

| 字段 | 自然写法 | 线上顺序 |
|---|---|---|
| 6 字节地址 | `000000000001` | `01 00 00 00 00 00` |
| 4 字节 DI | `0x02010100` | `00 01 01 02` |
| 数据域 BCD | `220.5` | `05 22` |

规则只有一条：**反转只发生在 `Address::from_string` / `to_string` 与
`di_to_wire` / `wire_to_di` 里，各一处。上层永远不要再 reverse。**

为什么不"在结构体里就存线上顺序"：那样每个 `printf`、每次日志核对、
每个 DI 常量比较都要在脑子里做一次反转。**反两次等于没反**，而这种错
在数值上表现为"220.5 变成 5.22"，看起来像设备坏了（MeterSim645 作者
把这条列为头号坑，本模块把它变成了一条单元测试 T11）。

## 3. `Frame.data` 为什么存"已去 0x33"的形态

`+0x33` 是**传输层的伪装**，不是语义的一部分。三种存法：

| 存法 | 后果 |
|---|---|
| 存线上形态（带 0x33） | 每个下游都要记得减一次；漏一处就整体错位 |
| 存裸形态（本模块） | 编解码各做一次，中间层看不见它 |
| 存两种 | 一定会有地方用错那一个 |

代价：`parse()` 里那行 `- 0x33` 是唯一的减法，`encode()` 里的 `+ 0x33` 是唯一的加法。
**只要这两处对称，中间所有代码就不需要知道 0x33 存在。**

已知边界：原始字节上限是 `0xCC`（`0xCC + 0x33 = 0xFF`）。
超过会 uint8 回绕 —— 协议层**无法表达**这个值，所以 T10 把"回绕"本身写成了断言，
而不是假装它不会发生。DI 的四个字节都是 `0x00~0x02` 量级，实际触不到。

## 4. 为什么 `kIncomplete` 不是错误

645 是变长帧（`L` 字段决定长度），而 TCP 会分片、串口会按字节到达。
"收到 7 个字节"这件事**无法区分**以下两种情形：

- 一帧正在路上（还差 9 字节）；
- 对端发了一半就死了。

**区分它们需要时间，不需要更多字节。** 所以：

```
parse() 只回答"这堆字节里有没有完整的一帧"
超时判断交给 master（等不到就把 kIncomplete 报成 kTimeout）
```

若把"不完整"直接当错误，正常的分片会被报成坏帧，重试逻辑就会在
"帧其实还在路上"的时候重发 —— 把一次慢应答放大成三次。

对应的实测：T09 对 1..n-1 每一种截断都断言 `INCOMPLETE`；
T35 断言半帧最终报 `kTimeout` 而**不是** `kBadFrame`（两者现场处置不同）。

## 5. 重试粒度：整笔事务，不是补字节

645 **没有事务号**。一旦帧边界丢了（粘包、半帧、迟到帧），就无法知道
"现在这个 68 是上一帧的尾巴还是新帧的头"。

所以重试必须是：

```
清接收缓冲 → 重发整帧 → 重新收
```

而不是"继续读剩下的字节"。后者在粘包时会读进下一帧的开头，
然后 CS 校验失败、再重试 —— 一次超时变成一串超时，日志上表现为"设备时好时坏"。

**什么时候不该重试**（本次修的一个逻辑缺陷）：

| 失败类型 | 重试？ | 理由 |
|---|---|---|
| `kTimeout` / `kBadFrame` | ✅ | 线路 / 干扰 / 分片，可能一过性 |
| `kAbnormal`（表说没这个点） | ❌ | 这是**确定的回答**，重发三遍结论不变 |
| `kAddrMismatch` / `kDiMismatch` | ❌ | 配置错，不是瞬时故障 |
| `kLinkError` | ❌ | 线掉了，重试只是空转 |

原实现对异常应答也重试 2 次。后果不是"错的值"，而是**时间**：
一次失败被拖成三轮 timeout（1.5 s），现场感受是"程序卡住"，
而日志只写"重试 2 次"，很难把两件事对上。

## 6. 为什么只有两层测试（没有 13/ 那样的跨语言层）

`13/` 的三层结构里，第三层（C++ ↔ Python pymodbus）是**唯一**能证明
"我们的客户端符合协议"的证据 —— 因为前两层的假从站也是我们写的，
双方共同误解协议时谁都发现不了。

645 没有这个条件：**没有可 pip 安装的、独立的 645 实现**当对端。
所以本模块换了三种证据，各自覆盖不同的盲区：

| 证据 | 能证明 | 不能证明 |
|---|---|---|
| 手算黄金向量（T03/T04） | CS 公式本身对 | 与真表互通 |
| 假表回环（T31~T45） | 失败分类、重试、四条防线 | 真实字节流的分片 |
| **跨进程 TCP 实测** | 真实 `recv` 分片下能收敛 | 645 方言差异 |

第三条是本次特意做的：`sim_tcp_server.exe` 在**另一个进程**里，
主站通过 winsock 真收发。它替代不了"另一个团队写的实现"，但至少
把"自己调用自己"变成了"两个进程对着一个字节流"。

**别把它说成"跨实现互通"** —— 那是 13/ 第三层的性质，不是这里的。

## 7. 假表为什么必须"只应答发给自己的帧"

最初我让它无脑应答。后果：`ADDR_MISMATCH` 那条路径**永远测不出来** ——
因为假表总会回，主站只会走到"地址校验失败"以外的分支？不对，恰恰相反：
无脑应答时主站仍然会做地址校验，但**地址校验之外的场景**（多表共总线）
就无法被构造。

真实从站的行为是：地址不匹配 → 静默丢弃。这条不是"礼貌"，是**协议要求**。
把它写进假表之后，"主站地址配错"这个现场最常见的故障（表现为"表在线却一个字节不回"）
才有了可复现的夹具。对应 T43。

## 8. 为什么不接 RtDb（本次的范围边界）

接 RtDb 需要先回答三个问题，而它们都不是协议问题：

1. **电表的 35 个设备侧点怎么映射到 8 个 `MEAS.*` 抽象点？**
   （`17/src/point_mapping.h` 是代码化映射，新增一条通道要动它）
2. **645 是"一表一地址"的轮询制，多个表共 485 总线时怎么排时隙？**
   （Modbus 是 TCP 并发，645 是串行半双工，时序模型不同）
3. **品质位怎么合成？** 645 同样没有品质位，与 Modbus 是同一个问题
   （`13/` 的做法是"失败保留上次有效值 + 品质另行表达"，需要复用那套约定）

这三个问题如果在一个 PR 里一起解决，协议层的缺陷会被映射层的噪音盖住。
所以本次**刻意止步于协议 + CLI**，并在 README §7 把未做项列成表 ——
"没做"写清楚，比"看起来做了"安全。
