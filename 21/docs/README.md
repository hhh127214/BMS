# 21/ — DL/T 645-2007 主站（老式电能表接入）

> 一句话：把 645 电表的**协议**真正实现了 —— 组帧、校验、BCD 解码、超时重试，
> 三种链路（内存 / TCP 透传 / 串口）一套代码。
> **已接进 EMS**：`Meter645DeviceIO`（IDeviceIO 第五个实现）+ `main_field.exe
> --device dlt645`，数据从 DI 直达快照（见 §9）。

---

## 1. 它在整个工程里的位置

```
设备侧协议通道（三条，互相独立）
├── 13/  Modbus TCP      PCS / BMS / 电表（新表）      → ModbusDeviceIO
├── P3/  IEC60870-5-104  网关 / 调度（上行）           → Iec104Server
└── 21/  DL/T 645-2007   老式电能表（RS485 / 透传）    → **本模块**
```

三条通道**不共享代码**：645 的帧结构（68...68...16）、地址反序、`+0x33` 掩码、
BCD 编码、偶校验串口参数，与 Modbus 和 104 没有任何交集。共用一套解析反而会
把三种协议的边界揉在一起 —— 所以宁可重复"打开链路 / 超时重试"这层薄壳。

为什么现在做它：`链路协议清单.csv` 里"关口电表"那一行写的是
「现场多为 RTU/RS485，老表常为 DL/T 645」，而全仓此前**一行 645 代码都没有**。
这不是"锦上添花的协议"，而是老站改造时的硬门槛。

## 2. 怎么跑

### 2.1 零硬件（推荐先跑这个）

```bash
cd 21
scripts\build.bat
build\meter645.exe --sim --count 3 --interval 0
```

`--sim` = 内存回环 + 进程内假表，不占端口、不碰串口。实测输出：

```
--- 第 1 轮 ---
02010100 A 相电压         220.000    220.000 V        OK
02010200 B 相电压         222.700    222.700 V        OK
02010300 C 相电压         217.800    217.800 V        OK
02030000 瞬时总有功功率      0.000      0.000 kW       OK
--- 第 3 轮 ---
02010100 A 相电压         222.000    222.000 V        OK
...
=== 统计 ===
请求 12 / 成功 12 / 重试 0 / 重试后成功 0
超时 0 / 坏帧 0 / 异常 0 / 地址不符 0 / DI 不符 0
结论: 所有请求均已归类（已归类 12 / 请求 12）
```

### 2.2 TCP 透传（串口服务器）

```bash
# 终端 1：起一个"假串口服务器"
build\sim_tcp_server.exe --port 8899 --seconds 30

# 终端 2
build\meter645.exe --tcp 127.0.0.1:8899 --count 5
```

**这条是实测过的**（跨进程、真实 winsock 收发，8 请求 8 应答全对）。
它不是"自己和自己对答案"的替身：假表在另一个进程里，`recv` 返回半个帧是常态，
主站必须在真实字节流上把帧边界找回来。

### 2.3 真串口

```bash
build\meter645.exe --serial COM3 --baud 2400 --parity even --count 10
```

> ★★ **这条路未在真实 RS485 硬件上验证。**
> 本机没有 485 转换器也没有真表，`dlt645_serial_link.h` 只做到了
> "编译通过 + 参数设置符合 Windows API 语义"，**没有一次真实收发**。
> 上现场前的顺序：`--sim` → `--tcp`（接串口服务器）→ `--serial` 接真表，
> 且先用 `--di 02010100` 读一个已知点核对 BCD 小数位。

## 4. 四条静默失败防线（本模块的全部价值）

| # | 防线 | 不做的后果 |
|---|---|---|
| ① | 发请求前 **清接收缓冲** | 上一轮迟到的应答被当本轮 → 值全对，但全是旧的 |
| ② | 校验**应答地址** | 多表共总线时，隔壁表的电压被当自己的 |
| ③ | 校验**应答 DI** | 表回了目录帧/别的项，被按请求的格式解码 |
| ④ | **异常应答优先判**（`0xD1`） | 只有 1 字节数据域，会因长度不足误报"线路坏了" |

这四条**并列**，不是"锦上添花"。少任何一条，现场表现都是
"通信正常但数据不对" —— 而这类问题最难查，因为所有通信计数都是绿的。

## 5. DI 表边界（必读）

内置 11 项常用 DI，来自 DL/T 645-2007 附录 A.2。**但附录里"字节数 / 小数位 /
是否带符号"是三列独立信息，抄错一列不报错、只算出错数**，所以：

- 内置表只作默认值，现场必须按**表计说明书**逐条核对；
- 正式点位应改为外置 `di_table.csv`（**未做**，见 §7）；
- 每个内置项都带 `note` 字段写核对提示。

**两条已实测的边界**：

| 事实 | 数值 | 后果 |
|---|---|---|
| 功率 3 字节 + 带符号位 | 上限 **99999 → 9.9999 kW**（未乘变比） | 灌 10.29 kW 会编码溢出，表回 `0xD1 0x01` |
| 电压 2 字节 | 上限 999.9 V | 35 kV 侧必须靠 PT 变比 |

> 这不是"表的缺陷"，是**规约的表示范围**。工商业现场靠 `mul_coe`（PT/CT 变比）
> 把它放大 —— 所以 `Scale` 的默认值必须是 `1.0 / 0.0`（不改变读数），
> 配错时整体偏移是**全局性**的，界面上看不出异常。

## 6. 缺陷复盘（本次开发实际踩的）

### 6.1 地址 BCD 期望值算错（测试写错，不是代码错）

`"123456789012"` 我最初断言 `b[1] == 0x34`，实际应为 `0x90`。
两位一组从右往左是 `12|90|78|56|34|12`，`b[1]` 是**次低**两位。
**教训**：黄金向量必须手算，但手算也会错 —— 所以手算结果要用第二条路径复核
（此处是对 `to_string()` 的往返断言把它抓出来的）。

### 6.2 功率上限（代码错，被 CLI 实跑抓出）

`--sim` 第 2 轮功率灌 10.29 kW → 编码溢出 → 表回 `0xD1 0x01`。
根因：3 字节 BCD 带符号位只剩 5 个半字节。**单元测试全绿，只有端到端实跑才暴露**
—— 因为测试用的值（1.2345）恰好在上限内。这条说明：**测试数据的取值范围
本身也是一种覆盖度**，不是"有断言就行"。

### 6.3 异常应答不该重试（逻辑缺陷）

原实现对 `kAbnormal` 也重试 2 次。表已经明确回答"没这个点"，连发三遍
只是把一次失败拖成三轮超时的时长。已改为**只对 `kTimeout` / `kBadFrame` 重试**
（这两类是"可能一过性"的）。

## 8. 与两篇文章的关系（任务来源）

本模块的动机来自公众号「未来技术观察」的两篇工具介绍：

- **ems_simulate**（Apache-2.0，Python+Vue3，Modbus/IEC104/DLT645 多协议**从站**）
- **MeterSim645**（MIT，.NET8/WPF，645 **主站**，仿真从站走内存回环，139 测试）

**结论：两篇的代码都不能直接用**（技术栈与"零第三方依赖"相斥；
且 ems_simulate 与 `13/` 的能力高度重叠）。但 MeterSim645 暴露出的**三个坑**
被本模块照单全收，并且都变成了断言：

1. **字节序只转一次**（反两次等于没反）→ `dlt645_frame.h` 的显示序/传输序约定
2. **DI 表必须核对附录 A.2**（作者自己承认仓库里频率 DI 是占位值）→ §5
3. **`mul_coe` 配错差好几个数量级** → `Scale` 默认 1.0/0.0 + T21/T40

## 9. 接进 EMS：Meter645DeviceIO（2026-10-17，§71）

`meter645_device_io.h` 是 **IDeviceIO 的第五个实现**（前四个：Sim / Memory / RtDb /
Modbus），把 645 主站接进 07/ 现场进程：

```bash
07\build\main_field.exe --device dlt645 --host <网关IP> --port 4001 --addr 000000000001
```

结构：

```
main_field --device dlt645
  → TcpLink（串口服务器透传，真 Winsock）
    → Dlt645Master（四条静默失败防线）
      → meter645_point_map.h（EMS_P_GRID ← DI 0x02030000，编译期绑定表）
        → Meter645DeviceIO（契约①：失败保旧值；品质位合成）
          → RealtimeSnapshot → EMS 算法层
```

**三个结构性决定**（都写进了代码注释，且都有断言守着）：

1. **只读是语义，不是暂缺**。电表没有"接收功率指令"的概念，所以
   `--device dlt645 --control` 在**参数解析层**（field_args.h）就被拒 ——
   不让它活到适配器层才报"写失败"（那时像通信故障，其实是装错通道）。
2. **快照里 SOC/P_BAT 恒 0 = "没有值"，不是"读到 0"**。有效性由
   `meters_alive["METER"]` 与 `point_valid()` 表达；BMS/PCS 恒 false，
   安全层据此走 `bms_comm_lost → [0,0]` 兜底，方向安全。
3. **绑定表坏了就一帧不发**。`Meter645DeviceIO` 构造时先过
   `self_check_map()`（索引越界/点名不符/DI 未知/重复绑定四类），
   不过则 `map_ok_=false`、全部点不可信、线上零流量（T60 断言守着）。

**跨进程端到端冒烟**（真 Winsock，非内存回环）：`sim_tcp_server.exe` +
`main_field --device dlt645` → 5 拍采集 5/5 成功，P_grid 随仿真表的正弦
工况爬升（0.00 → 1.37 kW），`rx_frames=5 tx_frames=5 bad_frames=0`。

已知边界：`--record`（→14/ 平台库）只在 `--control` 下开放，而 645 恒只读，
所以 645 的巡检数据暂不入库（见 §7）。
