# 13/ — link_tap：链路中间人（报文监视 + 链路扰动 + 测点注入）

> 一句话：把"**链路不正常的时候两端各是什么行为**"从"现场偶发、实验室复现不出来"
> 变成一条命令。
> 它**不改被测代码**：主站与从站还是原来那两份交付物，tap 只是插在中间。

上游文档：`docs/README.md`（模块总览 / 点表 / 怎么跑）、`docs/design.md`（协议层设计推演）。
本文只讲**新增的这一件工具**：它为什么存在、怎么用、实测抓到了什么。

---

## 1. 它为什么存在 —— 现有资产覆盖不到的三件事

本项目已经有**两条**保证链，`link_tap.py` **不重复**它们：

| 资产 | 覆盖的问题 | 对端 |
|---|---|---|
| `13/src/fake_modbus_slave.h` | 我们的客户端**符不符合协议** | 进程内假从站（可注入故障） |
| `13/sim/modbus_slave.py` | 两个**独立实现**能不能互通 | 真 pymodbus 从站 |
| **`13/sim/link_tap.py`** | **链路不正常时两端各是什么行为** | 真主站 + 真从站，中间插一层 |

三条链回答的是三个**不同**的问题，缺一个就有一类边界测不到。

### ① 报文级可见性 —— 中间那一帧到底长什么样

从站日志只知道"被轮询了 N 次"，主站只知道自己报没报错。
**两端日志里都写着"成功"的那一次，帧本身可能是错的。**

字序 / 缩放这类问题恰恰**只能从帧上看出**：

- 主站解码失败 → 它自己知道；
- 主站**解码成功但值是错的**（比如把 `0x00007FC0` 这种组合解成一个合法的小数）→
  两端都不知道，日志全绿。

这正是微信文章里那个"ABCD / DCBA 搞反，读出来是天文数字"的坑的真实形态。

### ② 运行时改工况 —— "发生 → 持续 → 恢复"要在一次会话里跑完

`modbus_slave.py` 的 `--bms-dis-forbid` / `--pcs-fault` 是**整轮固定**的：
换工况必须重启进程。于是"t=2s 断链、持续 3s、t=6s 恢复"这种**时间窗内**的演进
在一次会话里**复现不出来**。

而 EMS 的故障模型恰好是时间窗表达的 —— `07/src` 的 `apply_fault` 就是
"发生→持续→恢复"。测试装置的表达能力**低于**被测模型，就有一类用例写不出来。

→ 本工具带**时间轴**（`timeline`），工况在跑动中切换。

### ③ 异常链路可复现 —— 把现场偶发变成一条命令

间歇性丢包、回包延迟忽高忽低、瞬断黑障：现场偶发，实验室复现不出来，
于是这类边界**永远测不到**。本工具给 9 个预设工况（`--ctl scenario <名字>`），
每一个都设计成**跑动中生效**。

## 2. 设计：透明中间人，两端零改动

```
   build\modbus_probe.exe          sim\link_tap.py           sim\modbus_slave.py
   （C++ 主站，交付物）      ──►   :15021  ══►  :15020   ──►  （pymodbus 从站，交付物）
        连的是 tap 的端口                链路中间人                还是原来那个从站
                                               │
                                     HTTP 控制口 :15022
                                     （浏览器监视台 + --ctl）
```

**两条铁律：**

1. **被测对象一行都不改。** 主站连的是 tap 的端口，从站还是原来那份。
   所以这里加的东西**不会污染被测代码** —— 测的仍然是 `13/src` 里那份真实实现。
2. **反向也成立。** tap 自己坏掉时，拔掉它（主站直接连从站）即可隔离问题。
   一个测试装置如果**不能一键摘除**，它自己就会变成新的故障源。

### 点表仍然只有两份 —— 不新增第三份

C++ 一份（`modbus_point_map.h`）、Python 从站一份（`modbus_slave.py`），
两份手写是**刻意的设计决策**（理由见 `modbus_slave.py` 顶部）。

本工具**不新增第三份**：它直接 `import modbus_slave`，用从站的 `point_table()`
当解码依据。于是**帧上显示的工程量恒与从站口径一致** —— 不会出现
"tap 显示 123、从站认为 123"这种第三份表带来的假一致。

> 为什么可以 import：`modbus_slave.py` 对 `pymodbus` 是**惰性导入**
> （缺库时 `HAVE_PYMODBUS=False` 但模块照常加载），而点表 / 编码工具不依赖 pymodbus。
> 这条边界很重要 —— 否则"没装 pymodbus"会被误读成"点表读不出来"。

## 3. 怎么用

### 3.1 三个窗口

```bat
:: 窗口 1 —— 设备替身
13\.venv\Scripts\python.exe 13\sim\modbus_slave.py --port 15020 --load 380 --pv 150

:: 窗口 2 —— 链路中间人（主站改连 15021）
13\.venv\Scripts\python.exe 13\sim\link_tap.py --listen 15021 --upstream 15020

:: 窗口 3 —— 被测主站，连的是中间人的端口
13\build\modbus_probe.exe --port 15021 --repeat 20 --verbose
```

监视台（浏览器）：`http://127.0.0.1:15022/` —— 帧表、时延分位、注水状态。

### 3.2 跑动中注入工况（不用重启任何东西）

```bat
:: 预设工况
13\.venv\Scripts\python.exe 13\sim\link_tap.py --ctl scenario blackout
13\.venv\Scripts\python.exe 13\sim\link_tap.py --ctl scenario wordflip

:: 手工调参
13\.venv\Scripts\python.exe 13\sim\link_tap.py --ctl perturb delay_ms=300
13\.venv\Scripts\python.exe 13\sim\link_tap.py --ctl perturb drop_every=3

:: 看状态 / 看帧 / 清空
13\.venv\Scripts\python.exe 13\sim\link_tap.py --ctl status
13\.venv\Scripts\python.exe 13\sim\link_tap.py --ctl frames 20
13\.venv\Scripts\python.exe 13\sim\link_tap.py --ctl clear
```

### 3.3 命令行参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--listen` | `15021` | 中间人监听端口。**主站连这个** |
| `--upstream` | `15020` | 真实从站端口（与 `run_sim.bat` 默认一致） |
| `--listen-host` / `--upstream-host` | `127.0.0.1` | |
| `--upstream-timeout` | `2.0` | 等上游回包的秒数。★ 见下 |
| `--ctl-port` | `15022` | HTTP 控制口 / 监视台 |
| `--record` | 空 | 把帧写成 JSONL（**帧级黄金向量**，含完整 hex） |
| `--verbose` / `-v` | 关 | 逐帧打印到控制台 |
| `--max-frames` | `2000` | 内存里保留的帧数（环形） |
| `--ctl CMD` | — | **客户端模式**：向已运行的 tap 发一条控制命令后退出 |

> ★ `--upstream-timeout` 默认 **2.0s**（不是 5s）：主站的超时比它短。
> 若设成 5s，延迟扰动会让**上游等待先超时**，测出来的方向就是反的 ——
> 明明是"主站超时"，会被记成"从站没答"。

### 3.4 预设工况（9 个）

| 名字 | 做了什么 | 设计意图 |
|---|---|---|
| `delay` | 响应固定延迟 300 ms | 主站超时边界 |
| `jitter` | 基准 50 ms + 抖动 0~250 ms | "忽高忽低"，考抖动吸收 |
| `drop` | 每 3 帧丢 1 帧 | 重发 / 事务编号错位 |
| `split` | 把响应拆成两次 TCP 写 | **真实半包**，考组帧器 |
| `blackout` | t=2s 断链、持续 3s、t=6s 恢复 | 完整"发生→持续→恢复" |
| `flap` | 反复断-通（1/3/5s 各断 0.9s） | 专治"现场偶发" |
| `wordflip` | 把 `MEAS.P_BAT` 按**相反字序**编码 | 打主站的**解码守卫** |
| `nan` | 直接塞 IEEE NaN 的两个字 | 打主站的 `kNonFinite` 守卫 |
| `reset` | 全部归零（含黑障与注入） | 一键回到干净链路 |

### 3.5 HTTP 接口（监视台用的就是这些）

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/` | 深色监视台 HTML |
| GET | `/api/status` | 计数、扰动参数、注水状态 |
| GET | `/api/frames?n=150` | 最近 n 帧（含解码后的工程量） |
| GET | `/api/points` | 点表镜像（32 点） |
| POST | `/api/perturb` | 改链路扰动参数 |
| POST | `/api/inject` | 测点注入 / 清空 |
| POST | `/api/scenario` | 应用预设工况 |
| POST | `/api/timeline` | 直接给时间轴步骤 |
| POST | `/api/clear` | 清空帧缓冲 |

> ★ `/api/clear` 是 **POST**。发 GET 会 404 —— 这一条是实测踩出来的。

## 4. ★ 测点注入的三种写法（运行时热生效）

```
MEAS.P_GRID=999                 按点表口径重新编码一个值（最常用）
MEAS.P_BAT=flip                 只把该点两个寄存器的字序**对调**，值不变
MEAS.P_BAT=nan                  注入 IEEE NaN（打主站的 kNonFinite 守卫）
MEAS.P_BAT=raw:0x0000,0x7FC0    直接给寄存器裸值
clear                           清空全部注入
```

### 为什么 `flip` 才是字序坑的真实形态

`MEAS.P_BAT=999` 是"**从站发了 999，主站读到 999**" —— 这是**正常链路**，
跟字序没关系。

`MEAS.P_BAT=flip` 是"**从站的值是对的，只是两端对"哪个字在前"的理解不一致**"。
这才是现场的真形态：设备厂家说"我发的是 123"，主站说"我读的是 0.0000"，
**两边都没说谎，帧上也能证明**。

### ★ `nan` 注入的字序陷阱（实测踩过）

`MEAS.P_BAT` 是**低字在前（BA）**，其余 f32 都是高字在前（AB）。

所以 `0x7FC00000`（NaN）在线上是 `[低字 0x0000, 高字 0x7FC0]`。
若按 AB 的顺序写成 `[0x7FC0, 0x0000]`，得到的是 `0x00007FC0`
—— 一个**合法的极小非规格化数（约 5e-41）**，不是 NaN。

于是"注入 NaN"变成了"注入一个正常的小数"，断言会莫名其妙地失败，
而且**看输出完全不像字序问题**。

> 这就是"注释声称的行为必须与代码实际行为一致"那条纪律的又一次实战：
> `raw_words` 必须**按该点自己的字序**给，低字在前的点要把高字写在第二个。

## 5. ★ 实测抓到的关键发现

端到端跑 `e2e_link_tap_live.py`（C++ 主站 → tap → pymodbus 从站，29 条断言全绿）
时，`wordflip` 工况暴露了一个**既有实现挡不住**的问题：

```
真值      123 kW
按错误字序发出后的线上值    0.0000
C++ 主站读到的值            0.0000，且【质量 ok】
```

**结论：真值 123 与主站读到的 0.0000（质量 ok）之间，没有任何告警。**

为什么危险：

- `kNonFinite` 守卫只挡 **NaN / Inf**；
- 字序交换后的值可能落在**任何**地方：天文数字、NaN、
  或者像这次一样 —— **0.0000 / 或一个合法的极小非规格化数**；
- 而 `0.0000` 是一个**看起来完全正常的数值**。BMS 报 SOC=0、
  电表报 P=0，算法会照常跑，只是跑在一个假世界上。

这正是 `docs/README.md` §2.1 那条纪律在**另一个入口**的复现：
**"把读失败当读到 0"是最典型的静默失败** —— 而字序错会**自动**产生这个结果，
不需要任何一处代码写错。

→ 因此本工具的价值不只是"能注入故障"，而是**把这类故障变成可复现的证据**：
帧上有 hex、主站侧有读数、断言里有"主站侧没告警"这一条。

### 6.1 自包含断言（L01~L12）

| 用例 | 考什么 |

| L02 | 解码正确性：量测 **+ 配置区** 都读（★ 见下） |
| L03 | 位解码：FC02 离散输入 |
| L04 | 延迟：中间人记录值 == 主站实际经历值 |

### 6.2 三条"判据本身写错过"的记录

> 这一节的价值不在"测试过了"，而在**测试的判据一开始是错的**。

**(1) `rc == 0` 当判据 —— 错。**

第一版把"主站退出码 0"当成"数据可用"。实测发现：延迟超过主站超时时，
探针**退出码仍然是 0**，只在**输出**里标"不可信"。

> 退出码 0 就等于数据可用，是很容易犯且后果很重的误判 ——
> 因为它把"**读到了但不可信**"混进了"**一切正常**"。

修法：改用 `probe_untrusted(out) or probe_bad_items(out)`
（正则抠"不可信"与行尾 `--`）判断。

**(2) 断言太窄 —— 错。**

第一版断言"字序错 → 值非有限或过大"。实测发现字序错也可能产生
**合法的极小非规格化数**（-50 交换后约 7e-41），既不非有限也不大。

修法：加"**量程合理性**"断言（`|错值 + 50| > 1.0` 且
`|错值| < 1e-3 或 > 1e3 或非有限`）—— 用**物理量程**当判据，
而不是用"看起来是否异常"当判据。

**(3) `dropped` 双重计数（工具真 bug）**

`drop_every=3` 时实测 `dropped=4 / rsp=6`（比例 2/3 而非 1/3）。

根因：`gate()` 里改了 `stats["dropped"]`，`record_event()` 里又加了一次。
修法：**`gate()` 无副作用**（只判定、不动计数），计数唯一归属 `record_event`。

> 这条也顺带修掉了一个更隐蔽的东西见 (4)。

**(4) `Recorder` 用轮询帧缓冲 —— 被 `/api/clear` 一清就永久静默失效**

第一版 `Recorder` 靠"帧缓冲长度是否变长"来取新帧。于是 `/api/clear`
把缓冲清空后，**水位永远回不到**，录制**停止**而且**不报错**。

修法：改成**推送式**（`Ctl.sink` 回调），并加一条断言
"录制覆盖到清空**之后**的注入帧"。

> 这是"工具自己有 bug 却能让被测对象背锅"的典型 ——
> 一个静默失效的录制器，会让人得出"扰动没生效"的错误结论。

## 8. 已知限制

| 限制 | 说明 |
|---|---|
| 只做 **MBAP/TCP** | 不含 RTU。但组帧器已把"帧同步"与"字节流"分开，加 RTU 主要是补 CRC16 + 静默间隔 |
| 单连接 | 每来一条连接起一个 `Link` 泵，不做连接池；EMS 现场够用 |
| 注入只改**响应方向** | 请求方向目前只支持延迟（`req_delay_ms`），不支持改写主站发出的指令 |
| 时间轴分辨率 | 由链路线程的调度粒度决定（毫秒级），不适合验证微秒级时序 |
| `--record` 无上限 | 长跑会持续增长；长跑请配合 `--max-frames` 或定期轮转 |
