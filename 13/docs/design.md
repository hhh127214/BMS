# 13/ 设计推演 — Modbus TCP 设备接入

> 本文只写**为什么这样设计**，以及**备选方案的代价**。
> "是什么 / 怎么跑"在 `README.md`；具体踩坑在源文件头部。

---

## 1. 为什么不能复用 `RtDbDeviceIO` 的假设

`RtDbDeviceIO`（07/src/rtdb）已经把"从外部拿数据"这件事做完了。
但它建立在一组**RT_DB 特有**的假设上，换到 Modbus 全部不成立：

| 假设（RT_DB 成立） | Modbus 上的现实 | 后果 |
|---|---|---|
| 每点自带 `data_quality_t` | **协议里没有品质位** | 可信性必须主站合成 |
| 一次 `read_snapshot` 是一个原子读（seqlock 保） | 一次事务只能读一段**连续地址** | 32 点 = 3 次请求 → **部分成功是常态** |
| 点名 ↔ 索引就够（值域 double） | 寄存器是 16 位、有量纲、要拆字 | 多出**字序 / 缩放 / 分表**三个出错维度 |
| `write_*` 只是写共享内存 | 写下去要等设备响应，**响应 ≠ 生效** | 需要"发布 / 驱动"分离 |
| 进程内 → 失败就是失败 | 跨网络 → **超时 / 半包 / 串包 / 异常码** | 错误必须分类，不能一个 bool |

结论：**不能把 Modbus 塞进 RT_DB 的形状里**。但可以复用它的两条纪律：
`write_command()` 是发布、`execute()` 是驱动；以及"点名只出现在适配器内部"。

## 2. 品质合成：三级结构的设计

RT_DB 有品质位，我们有"三级派生"：

```
① block_ok_[k]     本拍第 k 个分块读成功了吗          （通信层）
② point_ok_[i]     本拍第 i 个点解码成功了吗          （编码层）
③ point_valid(i)   = block_ok_[block_of(i)] && point_ok_[i]
   data_valid()    = value(STA.DATA_VALID) > 0.5 && 所有 block_ok_
```

**为什么必须分开 ① 和 ②**（这是最容易做错的地方）：

- 只留 ①：字序配错时块读成功、值是 NaN 或天文数字，仍被判"可信" →
  算法拿 `4.7e38` 当功率用。
- 只留 ②：通信断了但旧缓冲还在，解码"成功"地解出一批**过期值**。

**为什么 `point_valid` 而不是给每个点一个 `quality` 字段**：
Modbus 的品质是**分块**属性的函数（通信）+ **逐点**属性的函数（编码），
存成 32 个枚举反而要在每次扫描后逐个重算，且容易忘了更新。
存成 2 个位数组 + 一个纯函数查询，**不可能出现"忘了更新"**。

**`stale_points()` 的语义**：不是"出错了多少次"，而是"**现在有多少个值不能用**"。
完全未连接时它等于 32 —— 那是**一个**事实的完整表达，
比"逐点记 32 条 stale 日志"清楚得多（日志会淹没真正的原因）。

## 3. 分块规划：为什么是 IR 40 / HR 6 / DI 8

约束：
- FC03/04 单次上限 **125 寄存器** → 32 点远未触顶，不是瓶颈；
- 一次事务只能**一段连续地址**；
- 地址段之间不能重叠（`blocks_disjoint()` 守卫）。

所以目标不是"不超限"，而是**把点数压到 3**。做法是把段内用空位对齐：

```
IR: [0..10] 量测 7 点（f32 占 2 寄存器 → 0,2,4,6 + u16/i16 各 1 → 8,9,10）
    [11]    空 1 个（让配置段从偶数起 —— 14 个 f32 = 28 寄存器，12..39）
    [12..39] 配置 14 点
```

**备选方案的代价**：

| 方案 | 请求数 | 代价 |
|---|---|---|
| 一点一次 | 32 | 每帧 32 个 RTT；现场 100 ms RTT 下采一帧 3.2 s |
| 按"逻辑组"分（量测/配置/指令/状态按需） | 3~5 | 组会随需求变，**点数一变请求数就变**，无法作为契约断言 |
| **按表分三段 + 段内连续（本方案）** | **3** | 需要一个空位（IR[11]）+ 新增点必须落在段尾 |

选本方案的核心理由：**"3" 可以写进断言**。T09/T22/`--plan` 都钉死这个数字，
任何"顺手改成一点一次"的退化会立刻变红。这是把一个性能属性变成**契约**的典型手法。

代价也是真实的：**新增点必须落在段尾**。IR[11] 那个空位就是为此留的
（"空位"而不是"把配置段左移" —— 左移会让已有设备/已有配置整体错位）。

## 4. 指令原子性：为什么一次 FC16

`write_command()` 要下发 `(p_bat, p_upper, p_lower)`。三种写法：

| 写法 | 中间态风险 |
|---|---|
| 3 次 FC06 | 设备可能执行到 "新功率 + **旧权限区间**" —— 若新功率越过了旧区间，那一瞬间越界 |
| 1 次 FC16（本方案） | 无。三个值在同一 PDU 里，从站要么全收要么全不收 |
| 先写区间再写功率 | 略好，但仍有"新区间 + 旧功率"的窗口（方向上更安全，但不可证明） |

**为什么这件事必须由编译期保证**：如果哪天有人往指令段中间插一个点，
地址就不连续了，`write_multiple_regs(base, regs, 6)` 会静默地**把中间那个点的值也覆盖掉**
（FC16 只认地址和长度）。`cmd_points_contiguous()` 的 `static_assert` 让这种改动**编不过**。

这是本项目的一条通则：**能编译期拦截的结构约束，不要留给运行期断言**。

## 5. 连接管理

### 5.1 非阻塞 connect（现场最容易踩的坑）

阻塞 `connect()` 在目标不可达时要等 OS 的 SYN 重传超时 ——
**Windows 实测约 20 秒**，而控制周期只有 200 ms。

现场表现是"程序偶尔卡死"，最难归因：日志上看不出，CPU 也不高，
只是因为某一拍恰好去连了一台正在重启的设备。

做法：非阻塞 connect + `select` 等可写 + `getsockopt(SO_ERROR)` 拿真实结论。
T47 断言"连不上必须 **< 3000 ms** 返回"。

### 5.2 超时 ≠ "暂时无数据"

底层 socket 在超时和"缓冲区空"上给出的错误码**在不同平台上语义不同**：

- Windows：超时给 `WSAETIMEDOUT`，"暂时无数据"给 `WSAEWOULDBLOCK` —— 两者可分
- Linux：非阻塞 recv 在无数据时给 `EAGAIN/EWOULDBLOCK`，超时由 `SO_RCVTIMEO` 决定

把它们合成一个 `would_block()` 的后果是**致命的**：
`recv_exact()` 在设备静默时会 `continue` 重试 —— **永远不返回**。

★ 这个缺陷是 `fake_modbus_slave` 的 `silent` 注入把测试**卡死**之后才暴露的，
不是读代码看出来的。**这就是"故障注入"存在的意义。**

### 5.3 重连策略

| 参数 | 默认 | 理由 |
|---|---|---|
| `auto_reconnect` | true | 现场链路抖动是常态 |
| `reconnect_interval_ms` | 1000 | 防"离线设备拖垮控制周期"：每拍都去 connect 会因 5.1 之外的原因吃掉时间预算 |
| 连接成功**不清缓存** | — | 上次会话的值比"没有值"安全；立刻清空会让"重连后第一拍"读到一个假零点 |

保留旧值的安全边界在哪里？在 `05/` —— BMS 通信丢失由 `bms_comm_lost → [0,0]`
**独立**兜底（判据是 `meters_alive["BMS"]`，而它经 `point_valid()` 已含"本拍真的采到了"）。
适配器只负责"如实表达可信性"，不负责替安全层做决定。

## 6. 串包自愈：为什么不是"事务号不符就失败"

上一次请求超时后，它的响应可能在几毫秒后才回到 socket 上。
此时下一次请求读到的第一个包是**上一次的**。

若判"事务号不符 → 失败"，一次网络抖动会**连锁成两拍数据缺失**
（第一拍超时、第二拍被上一拍的回包顶掉）。

做法：`round_trip()` 是**宽容循环** —— 不是我的包就 `drain()` 后 `continue`，
最多容忍 4 个迟到包。并单独计 `stale_responses()`。

★ 关键：`stale_responses()` **不是错误计数**。它增长说明链路在抖，
但本轮数据是对的。把它算进错误会让"抖动"和"故障"混为一谈。

## 7. 测试分层的推演

一句话：**每一层都在缩小"结论的适用范围"**。

| 层 | 手段 | 结论的适用范围 |
|---|---|---|
| 协议层 | 纯函数 `pdu::` + fake 从站 | "编解码按协议来"（字节级可复现） |
| 契约层 | fake 从站 + 故障注入 | "适配器在异常路径下的行为符合 `IDeviceIO` 契约" |
| 跨语言层 | **pymodbus**（第三方实现） | "两个独立实现能互通" |

**为什么故障注入必须在第二层而不是第三层**：
Python 从站是别人的实现，**不会配合你演半包/串包/静默**。
这些场景只能在进程内造（`fake_modbus_slave.h::Options`），
而它们恰恰是最需要验证的路径。所以两层分工是：

> fake（进程内）→ 异常路径正确性
> Python（跨进程）→ 互操作性

**为什么两层都要有**：反过来也不行 ——
只做故障注入，两个实现共同误解协议时全绿（`--bias 40` 那条断言就是这么被逼出来的：
只有它才能区分"读电表"与"本地重算"）。

### 7.1 ★ 第三层"允许不跑"带来的新问题：谁来保证 SKIP 被看见

第三层依赖**外部环境**（Python + pymodbus），所以必须是 **SKIP 而非 FAIL**
—— 环境问题不是代码缺陷，否则在没装 pymodbus 的机器上会**永久假红**。

但做完这一步才发现，**"允许不跑"只解决了一半**：

| 只做一半 | 做全 |
|---|---|
| 测试层打 `SKIPPED=7`、退出码 0 | 上层 `build_test.bat` 的**结论行**也据实改成 `[SKIP]` |
| 只有 skip 时才打印 `SKIPPED` | **总是**打印（哪怕是 0）→ "跑了"有**正面证据** |

为什么第二列是必需的：

- **结论行才是人读的那一行。** 测试层再诚实，只要上层印 `[OK] 三层测试全部通过`，
  读日志的人就只会记住这一行 —— 而它**是假的**。这是「静默降级」的教科书形态。
- **"没有反面证据"不等于"正面证据"。** 若"跑了"只能靠"日志里没有 `SKIPPED` 那一行"来推断，
  那么"没跑 / grep 写错 / 日志被截断"三者**完全不可区分**。所以要让"跑了"有正面输出。

落地形状（判据的传递链，任一段断掉都会退化成静默）：

```
桥接测试 --(1) 总是打印 SKIPPED=n
         --(2) 另落 build/bridge_status.txt（纯 ASCII 键值行）
build_test.bat --(3) findstr /C:"SKIPPED=0" 取判定
               --(4) 收尾行据实印 [OK] 或 [SKIP]
全量日志       --(5) grep "SKIPPED=0" 判定 8906 / 8984 口径
```

★ 第 (2) 步用**文件**而不是 grep 中文输出：`build_all.log` 是**混合编码**的
（`.bat` 的 `echo` 走 CP936、C++ 的 `printf` 走 UTF-8），对中文 grep 不稳。
让被测程序自己落一行纯 ASCII，是唯一稳的做法。

★ 同批修掉的第三个问题：`bridge_slave.log` 原先按相对路径落在 **`13\` 模块根**
（源码目录）。相对路径按 **CWD** 落盘，而 `build_test.bat` 的 CWD 是模块根 ——
**运行期产物不该进源码目录**。现默认落 `build\`，可用 `EMS_BRIDGE_LOG` / `EMS_BRIDGE_STATUS` 覆盖。

## 8. 一个反面的教学案例：注释与代码脱节

本模块初版的 `DeviceModel.step()`：

```python
# ⑥ 关口电表 = 负荷 + 站用电 - 光伏 - 电池 + 电表系统偏差
p_grid = (self.p_load + self.standby_kw) - self.p_pv - self.p_bat
```

注释写了 `+ 电表系统偏差`，**代码里没有**。

- 默认 `--bias 0` 时，"加了"与"忘了加"**逐位相等** → 默认值证明不了这一行存在。
- 更糟的是：bias 恰恰是**唯一**能把"读电表"与"本地重算"区分开的观测量。
  这个 bug 一旦存在，T42 那条最关键的断言在默认参数下**永远是绿的**。

修法两步（缺一不可）：
1. 补上 `+ self.meter_bias`；
2. **把默认值之外的区分度做进夹具** —— 联调固定用 `--bias 40`，
   并加反向守卫 `|p_grid - 本地重算| > 30`。

教训：**"注释声称的行为"必须与代码实际行为一致**；
且**默认值不能作为"这一行存在"的证据**。

这条纪律在本项目已经栽过四次（`read_limits()` 的"每拍刷新"、
`execute()` 的"发布权限区间"、网关心跳的 `T+0s`、这次的 `meter_bias`）。

## 9. 遗留的设计问题（诚实清单）

1. **RTU 未支持**。协议层把"帧同步"（MBAP 解析）与"字节流读取"耦合在
   `round_trip()` 里了。加 RTU 需要把帧边界抽出来（CRC16 + 3.5 字符静默间隔），
   当前结构**不阻碍**但也不支持。
2. **单连接顺序请求**。高点数时吞吐受限。真并发需要连接池 + 事务号分配器，
   而现在事务号是单调递增的单客户端状态。
3. **`read_limits()` 与 `read_snapshot()` 各扫一次**。
   `limits_scope_only=true` 时 `read_limits` 只扫 2 个分块，
   但两者在同拍先后调用时会**重复读 IR**。正确做法是"同拍内共享一次扫描结果"
   （用一个扫描序列号）。当前没做，因为控制回路的调用顺序是
   `read_limits` 每拍一次、`read_snapshot` 每拍一次，重复读的代价（1 个 RTT）
   可接受 —— 但这是**已知的浪费**，不是设计意图。
