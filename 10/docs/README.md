## 1. 这一层在做什么

`10/` 是**装配层**，不是新的控制逻辑层。它把 04~09 的全栈装进一个可配置的 24h
场景里跑一遍，并把结果落成**可交付的产物**：

```
04/ 策略层  ─┐
05/ 安全层  ─┤
06/ 状态机  ─┼─► 07/ 实时闭环 (EmsRuntime) ─► 10/ 24h 场景装配 ─► 报告产物
08/ 优化协同 ─┤
09/ 场景库  ─┘
```

控制逻辑的**正确性验收**在 05~09 已完成（6673 条断言）。`10/` 回答的是另外三个
工程问题：

1. **长时稳定性**：连续 86400 拍（24h）后，不变量还成立吗？
2. **经济性**：在两部制电价下，这套策略一天到底省多少钱、多久回本？
3. **全场景覆盖**：设备故障、通信中断、故障恢复——闭环能不能正确地"停下来、
   并且恢复"？

**本周期实测找到了 2 个真实缺陷**（见 §5.1 / §5.2，均为跨周期隐患），
并得到一个有价值的**场景结论**（§5.3：故障日能量预算耗尽导致傍晚无容量削峰）。

## 4. 经济性核算口径

工商业**两部制**电价（与现场结算单一致）：

```
总电费 = 电度电费 + 需量电费 − 上网收益
  电度电费 = Σ 购电功率 × 分时电价 × Δt
  需量电费 = 计量窗口内**最大平均购电功率** × 需量单价
  上网收益 = Σ 上网电量 × 上网电价
```

两个容易做错的地方，本模块都按现场口径处理：

1. **需量按窗口平均，不按瞬时峰值。**
   国内需量电费按 15 min 计量窗口的**平均功率**最大值计费。用瞬时峰值会把一个
   尖刺当成整月需量，严重高估收益。实现见 `peak_demand_kw()` 的滑动窗口。

2. **储能收益必须扣电池衰减。**
   只报"省了多少"而不算衰减会高估收益。度电衰减成本按
   `单位投资 / (循环寿命 × 往返效率)` 摊销，`net_benefit = saving − degradation`。

### 实测结果（典型日，1000 kWh / 250 kW）

| 指标 | 值 |
| --- | --- |
| 日用电量 | 7618 kWh |
| 日发电量（光伏） | 2291 kWh |
| 购电量 | 5181 kWh |
| 储能充电 / 放电 | 535 / 730 kWh |
| 等效循环 | 0.73 次/日 |
| 最大需量（含储能 / 无储能） | 400 / 450 kW |
| 电度电费（含 / 无储能） | 3142 / 3816 元 |
| 需量电费（含 / 无储能） | 480 / 540 元 |
| 总电费（含 / 无储能） | 3622 / 4356 元 |
| **节省（未扣衰减）** | **734 元/日** |
| 电池衰减成本 | 162 元/日 |
| **净收益** | **572 元/日** |
| 节省比例 | 16.9 % |
| 静态回收期（线性外推） | 5.75 年 |

节省拆分：电度电费 674 元（峰谷套利）+ 需量电费 60 元（削峰）。

## 5. 本周期发现并修复的缺陷

### 5.1 【已修复】15 min 阶梯预报跳变导致关口瞬时倒送

**现象**：以单拍粒度（`log_every=1`）检查时，10:45:00 出现 1 拍倒送，
`P_grid = −7.918 kW`（配置只允许 −5 kW 的滤波暂态）。10 拍粒度下被掩盖。

**根因链**：

1. 预报是 **15 min 阶梯**。阶梯边界上 `base = P_load − P_pv` 会在一拍内突降
   十几 kW（10:45 实测突降 12.5 kW）。
2. 安全层的并网上界是 `p_upper = base − grid_p_min`。上一拍按**旧（更松）**的
   base 下发了 `p_cmd = 120.2 kW`（恰好顶在当时的边界上）。
3. PCS 有 0.10 s 死区 + 0.30 s 一阶惯性，新一拍边界收紧到 107.7 kW 时，
   在途指令仍在执行（实测 `p_actual = 115.7 kW`）。
4. 结果：`P_grid = 107.7 − 115.7 = −8.0 kW` → 瞬时倒送。

**这不是噪声问题，是"预报粒度 vs 控制带宽"的结构性问题。** 安全层用当拍量测
算边界，而执行机构带记忆 —— 边界收紧的那一拍，上一拍的指令还没执行完。

**修复**（`05/src/safety_engine.h` + `07/src/realtime_loop.h` + `04/src/data_models.h`）：

给 `RealtimeSnapshot` 增加**下一控制拍的预测量**，安全层的并网上界取
`min(base_now, base_next)`（更紧的上界）：

```cpp
// 04/src/data_models.h
bool   has_lookahead  = false;   // 无前瞻时行为与历史完全一致
double p_load_next_kw = 0.0;
double p_pv_next_kw   = 0.0;

// 05/src/safety_engine.h — check_grid_connect()
const double base_safe =
    rt.has_lookahead ? std::min(base, rt.p_load_next_kw - rt.p_pv_next_kw)
                     : base;
double upper_by_grid = base_safe - p_.grid_p_min_kw;

// 07/src/realtime_loop.h — fill_context()
if (fc_.loaded && fc_.size() > 0) {
    double ln = 0.0, pn = 0.0;
    if (fc_.sample(t_ + dt_s, &ln, &pn, nullptr)) {
        rt.p_load_next_kw = ln;  rt.p_pv_next_kw = pn;  rt.has_lookahead = true;
    }
}
```

这与周期 9 给变压器约束加的"量测 + 预测取较劣者"是**同一思路**：约束必须在
指令**下发之前**就预见它的后果。

**效果**：单拍粒度下 `P_grid` 最小值从 −7.918 kW 提升到 **+2.0 kW**，倒送拍数
**0**，全部不变量在**逐拍**粒度下通过。

**向后兼容**：`has_lookahead` 默认 `false`。所有手工构造 `RealtimeSnapshot` 的
单测（04/05/06）行为不变；只有设置了预报的运行时（07/08/09/10）才启用前瞻。

### 5.2 【已修复】稳态判定窗口的日志粒度不一致

周期 9 的"稳态窗口"用于把 PCS 起动暂态排除在安全不变量之外，判据是
"连续 N 拍未门控"。但 N 是拿**日志行数**比较的，而日志按 `log_every` 降采样 ——
同一物理过程在 `log_every=1` 与 `log_every=10` 下，稳态起点相差 10 倍，
不变量结论会不一致。

**修复**：`Sim24hConfig::settle_ticks` 明确定义为**控制拍**（`dt_s`），
`run_sim_24h()` 内部按 `settle_ticks × dt_s / rec_dt_s` 换算成日志行数。
`T109` 断言两种粒度下不变量结论一致。

### 5.3 【场景结论，非缺陷】故障日傍晚关口越限 —— 能量预算耗尽

**现象**：故障注入日（08:00–08:30 PCS 故障 + 14:00–14:10 BMS 通信中断 +
20:00–20:05 电表中断）在 19:45–20:30 关口冲到 **443.8 kW**，超过配置要求 408 kW
（`grid_breach = 220` 拍）。

**这是缺陷吗？不是。** 同一时段实测：

```
19:45  DERATED  grid=443.84  cmd=0.000  act=0.000  SOC=0.100  reason=interval_contradiction
19:55  DERATED  grid=434.10  cmd=0.000  act=0.000  SOC=0.100  reason=interval_contradiction
20:15  DERATED  grid=421.30  cmd=0.000  act=0.000  SOC=0.100  reason=interval_contradiction
```

SOC 已经触底 0.100 → 安全引擎锁存"禁放"（`p_upper = 0`），而需量约束要求
`p_lower = base − 400 = 34.1 > 0` → **区间矛盾** → 指令 0。
**储能不是不动作，是没容量可动。**

原因链：设备故障使当日能量轨迹改变（少充少放 + 恢复后追赶），储能提前触底，
到傍晚峰段已无容量削峰。这是**有效场景结论** —— 它回答的是"该配多大容量 /
该怎么分配能量"，而不是"代码有没有 bug"。

**处理方式**（不隐藏、可归因）：

1. 不变量明确分成**硬 / 安全**两类，只有硬不变量决定"通过/失败"（见 §7）。
2. `Sim24hResult::grid_breach_soc_limited` 单独统计"发生在 SOC 触底/触顶"的越限拍数。
   本场景 **220 / 220 全部可归因**。
3. `T111` 断言：硬不变量必须全过，且关口越限必须 100% 可归因 ——
   一旦出现"控制失效型"越限，测试立刻失败。
4. 报告里单独列出该归因行，避免被误读。

## 6. 故障注入语义（重要）

故障用**时间窗**表达（`FaultWindow`），可以在一条 24h 曲线里编排
"发生 → 持续 → 恢复"的完整过程。支持 6 种故障源：
`BMS 通信中断 / 关口电表通信中断 / PCS 通信中断 / PCS 故障 / 设备离线 / 数据无效`。

### 6.1 故障恢复后**不会自动带载**（这是设计意图，不是缺陷）

`06/` 状态机的 `transit()` 明确规定：进入 `FAULT` / `EMERGENCY` 时**撤销运行许可**，
故障恢复后落到 `READY` 待机，必须由上层**显式重新下发启动命令**才回到 `NORMAL` ——
避免故障未彻底排查就自动带载。

因此 `Sim24hConfig` 提供 `auto_restart_after_fault`：

| 取值 | 语义 | 用途 |
| --- | --- | --- |
| `false`（默认） | 严格按安全规程：恢复后停在 READY，指令恒 0 | 验证"不自动带载"这条安全要求 |
| `true` | 模拟"上层运行许可保持"：恢复后重新带载 | 验证恢复路径可用 |

`T107` 对两种模式都做了断言：

```
默认模式：故障窗采样=174 非零=0 恢复后非零=0/540（应全 0）
保持许可：故障窗非零=0 恢复后非零=540/540
```

## 7. 不变量（与 09/ 同口径，但明确分成两类）

### 7.1 硬不变量 —— **逐拍**判定

| 不变量 | 判据 | 违反的后果 |
| --- | --- | --- |
| 指令逃逸 | `p_cmd ∈ [p_lower, p_upper]` | 架构级问题（EMS 预期 ≠ 设备执行） |
| 功率超限 | `\|p_cmd\| ≤ min(PCS, BMS)` | 架构级问题 |
| 门控不变量 | 非运行态 `p_cmd ≡ 0` | 架构级问题 |

**任何场景（含故障日）都必须全过。** 演示程序据此决定退出码：
硬不变量违规 → 退出码 2。

### 7.2 安全不变量 —— **稳态窗口**判定

| 不变量 | 判据 |
| --- | --- |
| 关口越界 | `P_grid ∈ [grid_min_required, grid_max_required]` |
| 变压器越限 | `\|P_grid\| + 0.1·P_load ≤ th·cap·tol` |
| SOC 越界 | `SOC ∈ [soc_min ± tol, soc_max ± tol]` |

**这两类的性质不同，报告必须分开呈现：**

- **硬不变量**是 EMS 自己声明的权限区间与设备能力，与执行机构动态无关。
- **安全不变量是物理量，受能量预算约束。** SOC 用尽 → 储能没有削峰能力 →
  关口必然越限。这是**有效场景结论**（该配多大容量 / 该怎么分配能量），
  不是控制失效。报告里用 `grid_breach_soc_limited` 把可归因部分单独统计出来。

**为什么要分两类**：硬不变量是契约，安全不变量是结果。把两者混在一起判"通过/不通过"，
会让"设备故障一天导致傍晚无容量削峰"这种**有价值的结论**被误读成代码缺陷。

### 7.3 两个必要的容差

1. **稳态窗口必须按时间定义。** `settle_ticks` 单位是**控制拍**（`dt_s`），
   `run_sim_24h()` 按 `settle_ticks × dt_s / rec_dt_s` 换算成日志行数。
   按日志行数比较会让结论依赖 `log_every`（见 §5.2）。

2. **SOC 越界容差不能取 0。** EMS 的 `soc_min` 是**控制限值**，被控对象的物理下限是
   `plant.soc_phys_min`（默认 0.05）。PCS 带死区 + 惯性，指令停止时 SOC 会再滑过限值
   一点点（实测 ~1.5e-5），用 `1e-9` 判据会把这种数值滑移记成"越界"。
   默认 `soc_tol = 0.002`（0.2%），足以覆盖执行机构动态，又远小于真实越限。

（本次的倒送缺陷在 `log_every=10` 下显示为 0 次违规）。
