> 一句话：给上游模块**只读地装一把尺子**，并把「性能达标」从"报告里的一句话"
> 变成**可复现、可证伪、能进 CI 门禁**的断言。
>
> 声明口径：本项目尚未全部完成，本模块是**阶段成果**。

文档地图：
- 本文 = 是什么 / 为什么这么设计 / 怎么跑 / 数字能信到什么程度 / 已知边界

## 2. 设计决策与"为什么"

### D1 尺子先于数字：单测与基准分成两个 exe

`test_perf_stats.exe`（T01~T11）测**统计基础设施本身对不对**，
`test_perf_bench.exe`（B1~B6）在**现场环境**上跑基准。

**为什么必须分**：单测不依赖 RT_DB 共享内存，能在任何机器上先绿。
混在一起的话，一次「共享内存没起来」会被误读成「分位数算错了」——
把「环境问题」和「实现缺陷」两类失败搅在一起，是调试成本最高的一种结构。

**不这样会怎样**：分位数定义写错（例如把 nearest-rank 当插值）时，
所有基准数字会整体偏移几个百分点，而**没人能从基准报告里看出来**。

### D2 分位数定义必须显式，默认 nearest-rank

`perf_stats.h` 提供两套：
- `kNearestRank`：`ceil(q·n)` 取**实际观测值**（门禁默认）
- `kLinearInterp`：R-7 线性插值（numpy / Excel 默认）

**为什么**：两类定义在 n=20000 时差异在 0.1% 量级，但在 n<100 时能差一个采样间隔。
更关键的是：插值法会产出**从未观测到过的值**，用来做「p99 < 10 ms」这类门禁时，
无法回答「到底是哪一次采样越线了」。门禁要可追溯到具体样本，故选 nearest-rank。

**不这样会怎样**：报告写「p99 = 9.97 µs」，但按另一种定义是 10.03 µs，
两边都能自证正确 —— 判据不可复核。

### D3 离群值**只标记不剔除**（默认 `drop_outliers = false`）

用 `median + k·1.4826·MAD`（稳健 z）标记，但**不**参与计算。

**为什么**：本项目最怕的事故是「10 Hz 闭环错过一拍」——
而错拍恰恰会表现为一个尖峰。若把尖峰当离群点剔掉，
**事故会从统计里消失**，报告反而更漂亮。

**不这样会怎样**：调大 `outlier_k` 就能让 p99 变好看，等于把判据调软，
这正是用户明令禁止的「调大到刚好能过」。

### D4 预热必须显式写出丢弃条数

每条基准都声明 `warmup`（B1 丢 1000 / B2 丢 200 / B3 丢 500 / B5-S2 丢 20），
报告表格里有独立的「预热丢弃」列。

**为什么**：首拍含惰性分配、页错误、分支预测器冷启动，量级可达稳态的**百倍**。
不丢弃则 mean 无意义；丢弃而不**写出来**则数字不可复核。

**例外**：SLA-C5 是**故意**要求含冷启动 max（`cold_max`）——因为它要回答的是
「首拍会不会吃掉半个周期」，这正是别人想丢掉的那一拍。

### D5 SLA 取「多次重复的**最差**」，不取平均

`RepeatResult` + `worst_of()`：B1 重复 3 次、B3 重复 5 次，取最差的那个 p99。

**为什么**：性能测试本身不稳定。取平均会把一次「机器被抢了一下」平滑掉，
于是门禁在**最需要它红的时刻**变绿。取最差是保守方向 ——
它只会让门禁更容易红，不会更容易绿。

### D6 优先用**相对判据**，绝对判据只在有推导时用

| 判据类型 | 例子 | 为什么 |
|---|---|---|
| 相对（同机同进程同刻前后对比） | SLA-P4（优化/基线 p50 比）、SLA-L2（末段/头段 p99 比） | 把「这台机器多快」约掉，跨机器仍成立 |
| 相对（比值） | SLA-A2（stale/collisions）、SLA-M3（编解码/单拍） | 同样约掉机器差异，且量纲无关 |
| 绝对 | SLA-C1（p99 ≤ 10 ms） | 有设计推导（周期 100 ms 的 10%），必须能落地 |

### D7 每条 SLA 必须标注**来源**，三类缺一不可

```cpp
enum class SlaSource {
    kDesignDerived,     // 从设计预算推导（如"周期 100 ms 的 10%"）
    kMeasuredMargin,    // 实测 + 明确裕度（如"基线 70 us，取 5% 改善"）
    kInheritedFrom12,   // 沿用 12/ A4 的既有口径（便于与该验收报告逐项对照）
};
```

**为什么**：不标来源的阈值无法审计。本模块在修订过程中就发生过
「阈值按机制预期设 2×，实测只到 1.33×」——**标了来源才敢把差距写进报告**（见 K5）。

### D8 反向验证是判据的**一部分**，不是可选附录

18 条反向验证：故意注入延迟或换成退化实现，**门禁必须变红**。
`test_perf_bench.cpp` 用 `EXPECT(rc.gate_red)` 把它们变成硬断言 ——
反向验证不红，测试本身就失败。

另配 1 条**负对照**：平坦样本必须**绿**（防止"任何输入都判红"的假门禁）。

**为什么**（约定 §3.1）：本项目已有先例 —— 某次修复在所有既有夹具下逐位恒等，
编译/单测/验收全绿，但把代码退回去**一条断言也不会红**。
所以每条关键断言都要能回答：「把实现故意改错，这条会红吗？」

### D9 反向守卫：先证明「条件真的被触发」

硬判据（`== 0` 这类）前面常配一条守卫：
- SLA-A3：先要求 `collisions > 0`，才谈 `stale / collisions ≤ 1%`
- SLA-P5：先要求「基线发布步 ≥ 5 µs」，才谈「优化后比它快 5%」
- SLA-P2：`suppress_rate ≥ 0.20`，先证明死区**真的在工作**

**为什么**：没有守卫的 `stale == 0` 可能只是「条件没被触发」而不是「实现正确」。
B2 的**无竞争**组 `collisions == 0`、`stale == 0` ——
单看后者会得出「重试逻辑正确」的结论，而实际上那条路径**一次都没跑过**。

### D10 长跑用**头尾自比**，而不是「跑 24 小时看数」

B6 跑 86400 拍，比较**预热后首段**与**末段**的 p99（SLA-L2 比值 ≤ 2）。

**口径必须是稳健统计量**：把 post-warmup 样本切 16 个等长子窗，逐窗取 p99，再比较
「末 1/4 子窗 p99 的**中位数**」与「首 1/4 子窗 p99 的**中位数**」。
不用单个 1000 样本窗的 p99 —— 那是第 10 差的样本，一次 OS 调度抖动落进窗口就能
把它抬 3~5 倍。**实测代价**：同一二进制连跑 5 次，单窗 head p99 在 5.5~39 µs、
tail p99 在 7.8~35 µs 之间跳，比值在 **0.20~3.42** 之间翻，2.0 的门禁时红时绿 ——
那测的是「抖动恰好落在头窗还是尾窗」，与「性能有没有随时长退化」无关（本机 32 逻辑核，
但后台进程多，抖动不可避免）。取中位数后单窗抖动被压掉。

**为什么**：加速比（本机 ~2.4 万倍）只说明「跑得快」，不说明「跑久了会怎样」。
真正要抓的性能泄漏（容器膨胀、日志线性增长未摊平、句柄泄漏）**只有头尾对比能抓到**。
另外 86400 拍 @ dt=0.1 是 **8640 s 仿真**，不是 24 h —— 报告里显式提醒，
避免与 12/ A4-05 的 24 h 口径混用。

> **★ 稳健口径的代价与收益都要写清**（否则会被误读成「把门禁调松了」）：
> 换成子窗中位后，**正向**比值从 0.20~3.42 收敛到 0.50~1.75（连续 10+ 次全绿）；
> **反向**验证（注入随时长线性增长的延迟）反而从「1.90x 无区分度」变成
> **3.88x 稳定变红**。所以它是**又稳又灵**，不是靠放水通过。

## 3. 踩坑记录

> 每个坑写四件事：**现象 / 根因 / 修法 / 判据有效性**（这个坑是怎么被发现的）。

### K1 `steady_clock` 在 MinGW 上是**假精度**

- **现象**：`std::chrono::steady_clock::period` 自称 `1 ns`，
  但所有测量值都是 `0.1 µs` 的整数倍（B3 的 p50/p95/p99 全是 0.0/0.1/0.1，
  B2 全是 0.2）。`p50 = 0.000 µs` 时 `CV` 还会炸到 100%+（本机 184.9% / 348.3%）。
- **根因**：MinGW-w64 的 `steady_clock` 走 `QueryPerformanceCounter`，
  QPC 频率 10 MHz → **真实粒度 100 ns**。`period` 是编译期写死的声明值，
  与实际后端无关，属**假精度**。
- **修法**：`perf_clock.h` 的 `probe_steady_clock()` **实测最小正增量**，
  写进报告 §0（本机 `1.000 ns 声称 / 100.000 ns 实测`），
  并在报告里声明「所有 µs 级数字的量化误差上限 0.1000 µs」。
- **判据有效性**：任何小于 0.1 µs 的差异在本机**不可分辨**；
  SLA-C4 的阈值设计正是被这个坑逼出来的（见 K3）。

### K2 延迟注入写在**计时区间外**，反向验证不会红

- **现象**：给 B4 加「注入 30 µs/次」的反向验证后，断言**仍然绿**。
- **根因**：注入写在
  `t0 = now(); f(); t1 = now();` 的**外面**。测到的是「调用方变慢」，
  不是「被测函数变慢」—— 计时区间没变，当然不会红。
- **修法**：把注入**移进** `f()` 与两次取时之间：
  `t0 = now(); busy_wait_us(d); f(); t1 = now();`。
  B1/B3/B4/B5/B6 五处全部照此修改。
- **判据有效性**：这是「反向验证不红」的一个**假原因** ——
  如果当时接受「绿」的结论，就会误以为「判据没区分度」，从而去**调松**阈值，
  方向完全错了。**反向验证不红时，先怀疑注入位置，再怀疑阈值。**

### K3 SLA-C4 用比值 `p99/p50` 会被**量化噪声**主导

- **现象**：SLA-C4 原定 `p99/p50 ≤ 3`。B1 实测 p50 ≈ 3.4 µs 时该比值轻易越过 3，
  理由却只是「计时粒度 100 ns 正好是 p50 的 3%」+「噪声地板 max 达 0.1~8.2 µs」。
- **根因**：**分母太小**。p50 在 3~4 µs 量级时，任何微架构抖动（缓存未命中、
  频率切换）都能把比值推上去 —— 阈值测的是「抖动」，不是「设计缺陷」。
- **修法**：改成对量级不敏感的**绝对尾散** `p99 - p50 ≤ 1 ms`
  （= 单拍预算 10 ms 的 10%），并把 `p99/p50` **降级为报告值**（不再是判据）。
  关键是**说清为什么**：这不是「因为超标了才放宽」，而是「原判据的物理含义错了」。
- **判据有效性**：新判据的反向验证是「每 50 拍注入 +2 ms」→ 尾散 2 ms > 1 ms → **红**（已验证）。
  而旧比值判据在**没有任何注入**时就会红 —— 那种「红」是噪声，没有信息量。

### K4 SLA-P1 / P2 照抄 `17/` 的判据**立不住**

- **现象**：原按 `17/docs` §4 的口径设「点值写入降低 ≥4×、数据点写入降低 ≥10×」。
  实测只得 **2.80×**（61200 → 21835）与 **4.38×**（51000 → 11635），两条**都没达标**。
- **根因**（两层，都是"把别人的结论当成自己的判据"）：
  1. **总写入比有理论上界**。17 个安全点必须永远发布且全在快档，
     `17 × 600 = 10200` 是不可压缩的地板 —— `61200 ÷ 10200 ≈ 6.0×` 就是**上限**。
     我却把判据设成 `≥4×`，已经贴到上界（`17/docs`「坑 6」原话：
     「原来那个"5 倍"既接近上界又没把这层结构说出来」）。
  2. **数据点写入比强依赖值变化模型**。它 = 死区抑制率的函数：
     `17/` 的 `test_scale_rtdb` 动态夹具抑制率 **0.5946**，而 18/ 的夹具只有 **0.394**
     （值的变化幅度/频率不同）→ 于是 17.1× 对 4.38×。
     跨模块拿它当判据，等于**把「我的夹具」当成了「设计要求」**。
- **修法**：改成**与点数、与值变化模型都无关的机制判据**：
  - SLA-P1 = **API 调用**降低倍数 ≥ 50×（机制：批量写把每拍 N 次调用压成 **1** 次，
    与点数、值模型完全无关；本机实测 102.0× 恰等于 102 点，正是理论值）
  - SLA-P2 = **安全点地板精确成立**（`opt_writes ≥ n_safety × ticks`，
    地板 `10200` 是**算出来的**，不是写死的常量）+ **死区抑制率 ≥ 0.20**
  - 写入次数比、数据点写入比**降级为报告值**，不再设判据
- **判据有效性**：新判据的反向验证是「把优化路径改成逐点单点写」→ 倍数 → 1× → **红**（已验证）。

### K5 优化后 CPU 只快了 1.33~1.39×，**没有**达到原预期的 2×

- **现象**：B5-S2 基线发布步 p50 = 80.6 µs，优化后 = 58.1 µs，比值 **0.721**
  （SLA-P4，阈值 0.95；三次运行 0.744 / 0.750 / 0.721，即 1.33~1.39× 改善）。
  而模块内部原按机制推演预期「≤0.50（2× 改善）」。
- **根因**：优化路径对每个**到期**点要做**两次字符串键 map 查找**
  （死区表 + 取值表）。到期点数 ≈ 快档占比 × N，**与死区是否抑制无关** ——
  死区只减少「写入」，不减少「判断」。这是 CPU 的**地板**，
  与 `17/docs`「坑 6」说的「写入次数地板」**不是同一件事**。
- **修法**：**没有**把阈值从 2× 悄悄改成 0.95 了事。做法是：
  1. 阈值下调到「**可测改善**」0.95（依据：基线 ~80 µs/拍，5% = 4 µs
     ≫ 计时器噪声 p99 0.1 µs，即改善**可分辨**）；
  2. 把差距、根因、原预期**如实写进报告**（`SLA-P4` 的 derivation 里，
     以「★ 未达成的预期（诚实记录）」开头）。
- **判据有效性**：反向验证「在优化路径计时区间内 +100 µs/拍」→ 比值 2.15 > 0.95 → **红**（已验证）。
  该判据测的是「优化有没有换来可测改善」，不是「有没有达到 2×」——
  后者是**设计指标**，不属于本模块的门禁范围，记录下来交回 `17/`。

### K6 `.bat` 里中文紧邻 `!VAR!` 会**静默吃掉变量**

- **现象**：`echo 结果 !NAME!: PASS=!P!` 这类行，变量展开后数字消失，
  而**退出码仍是 0**。
- **根因**：`.bat` 是 UTF-8 但 `cmd.exe` 按 CP936 读。中文（双字节）行尾若落在
  前导字节（0x81–0xFE）上，会与行尾 `\r` 配对被吃掉；
  同类的字节对齐问题也会让紧邻的 `!VAR!` 展开结果丢失。
- **修法**：三条同时做 ——
  1. **CRLF** 行尾（写完跑 `python scripts/fix_bat_encoding.py`）；
  2. 块内一律 `!VAR!`（先 `setlocal enabledelayedexpansion`），路径类变量**禁用** `%VAR%`；
  3. 所有**汇总数字行用纯 ASCII 且单独成行**，不让中文与变量贴在一起。
  另外：**不从 Git Bash 直接跑 `.bat`**（本机路径含 `(cn)`，MSYS 不加引号会被当分组括号），
  一律用 `subprocess.run(['cmd','/c','build_test.bat'], cwd=...)`。
- **判据有效性**：这三条由 `scripts/fix_bat_encoding.py --check` 兜住；
  新写的 `.bat` **必须先过 `--check`**（本模块的两个脚本已过）。
  另外：`fix_bat_encoding.py` 会跳过 `build/` 等目录（那是产物区），
  所以**别把要用的 `.bat` 放在 `18/build/` 里** —— 它永远不会被修复器检查到。
- **★ 现场复现（不是推断）**：做「门禁脚本失败路径」自测时我先写了一个探针 `.bat`，
  忘了转 CRLF。结果是：**整个脚本一行都没正确执行**（`!NAME!` 不展开、中文 `REM` 行
  被当命令执行、报「不是内部或外部命令」），而**退出码仍是 0**。
  转成 CRLF 后立刻正常（`PASS=124 FAIL=2`、`probe_bat_fail_flag=1`）。
  这正是本项目最忌讳的一类失败：**错的毫无声响**。

### K7 让 `.bat` 去 grep 测试输出计数，是**不可靠**的

- **现象**：本模块输出中英混排。`cmd` 在 CP936 下抓 `PASS=` 那行时，
  管道里的 UTF-8 会乱码/截断；一旦没抓到，脚本把断言数当 **0** 上报，
  仍然打印「通过」并以 0 退出。
- **根因**：**编码不确定的通道不能承载判据**。
  这和 `13/` 当年「静默跳过 vs 真的跑过不可区分」是同一类失败。
- **修法**：exe 落一份**纯 ASCII 状态文件** `build/status_*.txt`（每行一个 `key=value`），
  `.bat` 只读它；并且**先删旧状态文件**（否则上一轮的 `PASS=63`
  会让本轮「exe 崩了没落盘」被误判成跑过）。
- **判据有效性**：本次实测 —— 控制台捕获确实是乱码（`SLA-P1  API 璋冪敤...`），
  但 `PASS=91 FAIL=0` 依然被正确读出（因为走的是状态文件）。
  **这个坑是"设计时就防住"的，不是事后发现的。**

### K8 档位口径自己写错：`15/38/32` ≠ 102

- **现象**：报告 B5 的负载口径行显示「快中慢档位 15/38/32」，三档相加 = 85，
  而点表是 102 点。
- **根因**：`17/docs` §4 的「快 32」**含** 17 个安全点（安全点本身也是快档，
  只是死区为 0）。我在结构体里存了 `n_fast - n_safety`，于是少算 17。
- **修法**：`n_fast` 改存**快档总数**（与 `17/` 同口径），并在报告里加
  「（三档之和 == 点数，可自校验）」和「其中 17 个安全点**计入快档**」两处说明。
- **判据有效性**：自校验（三档之和是否等于点数）本身就是最简单的反向守卫 ——
  **如果当时加了这条自校验，第一次就发现了。**

## 5. 已知边界（**诚实列出，不做的就不写"已完成"**）

1. **多机并联 / 多 PCS 功率分配未测** —— `07/` 目前是单 PCS 模型。加分配层后单拍耗时会变，
   本模块的数字不再适用。
2. **真实网络 IO 未测** —— 只测到 PDU 编解码（纯 CPU）。Modbus TCP 的 socket 往返、
   超时重传、分块读次数**未纳入**。
3. **跨进程共享内存的极端竞争未测** —— B2 只用**同进程**一个写者线程模拟设备进程。
   真实三进程在更高写频下的重试吸收率需复测。
4. **真实预测（含误差）未测** —— `08/` 目前是完美预测。接入真实预测后，
   96 点重优化与滚动重优化的 CPU 代价未测。
5. **内存分配器的长期碎片未测** —— 长跑看的是**工作集**，不是虚拟内存碎片。
6. **不同 CPU 频率 / 电源策略未测** —— 本机结果受 turbo / 节能影响。
   绝对 µs **不可移植**（但相对判据仍成立）。
7. **未做多核扩展性** —— 全部基准**单线程**。现场若把采集/告警拆到独立线程，
   需重测竞争与缓存一致性代价。
8. **B6 的 8640 s 仿真 ≠ 24 h** —— 不要把它与 `12/` A4-05 的加速比直接比（步长不同）。
9. **未接入 `scripts/build_all.bat`** —— 按约定 §6，新模块挂进构建树**由集成方统一执行**
   （避免多个工作流并发改同一文件互相覆盖）。因此 `18/` 目前**不在**全量基线的分母里。

## 6. 数字可信边界（**这些数字是怎么测的、什么时候可信、什么时候不可信**）

> 这一节是本模块存在的前提。**性能数字没有可信边界等于没有。**

### 6.1 怎么测的（可复核的步骤）

```bat
REM 1) 编译（不改任何上游模块）
18\scripts\build.bat
REM 2) 编译 + 跑全部测试 + 落盘报告
18\scripts\build_test.bat      :: 退出码 0 / PASS=91 FAIL=0 SKIPPED=0
REM 从 Git Bash 里要用（不要直接跑 .bat）：
python -c "import subprocess;subprocess.run(['cmd','/c','build_test.bat'],cwd=r'D:\wb(cn)\BMS\18\scripts')"
```

产出 `18/build/BENCH-REPORT.md`，含：日期 / 机器 / 编译器 / 时钟实测粒度 /
**测量前空载窗口的系统 CPU 忙率** / 计时器噪声地板 / 每类统计量 /
23 条 SLA 与实测对照 / 18 条反向验证 / 未覆盖风险。

**测量约定**（写进报告 §0，不符合则数字不可用）：
- 本进程**独占运行**：no 并发编译、no 并发压测；
- 测量**前**先跑 1 s 空载窗口记录系统 CPU 忙率（本次三次运行实测 5.6% / 7.7% / 10.0%），
  作为「背景足够干净」的证据；
- `dt=0.1 s`、`log_every=1`、9 策略全启用；
- 闭环与长跑单线程；B2 的 contended 组另起 1 个写者线程
  —— **那是被测负载本身，不是并发干扰**。

### 6.2 什么条件下**可信**

| 用法 | 为什么可信 |
|---|---|
| 同机、同进程、同刻的**相对比较**（B5 优化前后、B6 头尾对比） | 机器特性被约掉；这是 SLA-P4 / SLA-L2 的用法 |
| 空载条件下的**量级判断**（「单拍在 µs 量级，远低于 10 ms 预算」） | 与阈值差 **2~3 个数量级**，噪声不可能翻盘 |
| **比值型**判据（A2、M3、P1） | 量纲无关、与机器绝对速度无关 |
| 「**反向验证会红**」这个结论 | 注入的是 ms 级延迟，比噪声地板大 4 个数量级 |

### 6.3 什么条件下**不可信**（谨慎使用 / 必须重测）

| 用法 | 为什么不可信 |
|---|---|
| **跨机器直接比绝对 µs** | CPU 型号/频率/电源策略不同。迁移时**改用相对判据** |
| 小于**计时器噪声地板**（报告 §0 的 `timer_floor_p99`）的差异 | 不可分辨。本机地板 p99 = 0.1 µs，且粒度 100 ns |
| **有并发负载时**的绝对数 | 尾部对干扰极敏感：一次编译/杀毒/系统更新就能把 p99 抬一个量级 |
| **首拍 / max** | 含惰性分配与页错误，run-to-run 方差极大：B1 max 三次为 551 / 577 / 1168 µs；B2 有竞争 max 三次为 5.8 / 160.0 / 244.1 µs（**40 倍**差）。只能当**量级**参考 |
| **`B5-S1` 的点写入次数比**（0.357 / 0.228） | **强依赖值变化模型**，只对本模块的夹具成立；故只报告、不设判据（见 K4） |
| **`timer_noise.cv_pct`** | 当噪声 p50 被量化到 0.000 µs 时，CV 会炸到 100%+（本机观测 184.9% / 348.3%），**无意义**，只看 p99/max |
| **B6 的加速比与 12/ A4-05 的加速比放在一起比** | 步长不同（dt=0.1 vs dt=1），口径不同 |
| **从 Git Bash 跑 `.bat`** | 路径含 `(cn)`，MSYS 拆错命令行 → 整脚本不执行。必须走 `cmd /c` |

### 6.4 「不稳定」是怎么被处理的（**不允许调大到刚好能过**）

| 手法 | 具体做法 |
|---|---|
| **相对判据** | 能比就比，不和"绝对值"较劲（P4、L2、A2、M3） |
| **多次重复 + 取最差** | B1 ×3、B3 ×5，`worst_of()` 取最保守值 |
| **显式写出成立条件** | 每条 SLA 在报告里带「成立条件」一行（单线程 / 独占 / dt / 策略数） |
| **反向守卫** | 硬判据前先证明「条件真的被触发」（A3、P2、P5） |
| **反向验证** | 18 条注入后**必须红**，不红则测试本身失败 |
| **门禁脚本自己也验一遍** | 用假状态文件测三种情形：`FAIL=0` → 汇总通过；`FAIL=2` → 置 `FAIL=1`；状态文件**缺失** → 也置 `FAIL=1`（防"exe 崩了没落盘"被当成通过）。实测汇总 `PASS=124 FAIL=2`、`probe_bat_fail_flag=1` |
| **负对照** | 平坦样本必须**绿**（防"任何输入都判红"的假门禁） |
| **阈值来源可审计** | 每条标 `design-derived` / `measured-margin` / `inherited(12/A4)`，不写"经验值" |
| **未达成的预期如实记录** | SLA-P4 原预期 2×、实测 1.33~1.39× —— 差距与根因写进规则 derivation（K5） |

> **反面做法（本模块明确禁止）**：先跑一遍，看实测多少，再把阈值设到刚好比它大一点。
> 这样得到的门禁**只能证明"今天没退化"**，无法证明"设计达标"，
> 而且反向验证一定不会红（因为没人为它设过能红的条件）。

- `-O2` **必须**：基准测的就是优化后代码（与全量构建同口径）。

- `-lpsapi`：`GetProcessMemoryInfo` 采样工作集 / 句柄（`psapi.h`）。
- 避开 `<filesystem>` 与 `<charconv>`（g++ 8.1.0 上不完整，见约定 §1）。
- 跨模块 `#include` 是**扁平**的（`#include "xxx.h"` 不带路径），靠 `-I` 解析。
