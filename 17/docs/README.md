## 2. 设计决策与"为什么"

### 2.1 为什么做两层点表，而不是把 40 点表"扩点"

1. **40 点表是算法契约**。它的点数是 `05/06/08/09/P1/P2/P3` 共同依赖的常量。
   往里塞簇电压、三相电流，等于让算法层直接看见厂家点表 —— 换一个 BMS 厂家就要动算法。
2. **现场点表是最容易变的那一样**（C5 原话）。它必须能配置化加载，而算法契约不能跟着站变。
3. **40 点表有硬约束**：`07/` 的索引是**运行时坐标**（追加只能在末尾）。
   第 1 层没这个包袱 —— 它由加载器在运行期构建。

### 2.2 为什么映射表必须是**代码**，不能是文档里的一张表

文档不会在"有人改了 40 点表的枚举顺序"时变红。映射表是代码，
`self_check()` 就能把"抽象表第 i 个点在设备侧找不到来源"变成一条**会红的断言**。

本项目已经吃过三次"写了、但某条路径上不生效"的亏（§10.4 D4），
而"映射表只存在于文档里"正是这一类缺口的温床。

### 2.3 为什么是四种映射关系，而不是"一对一"就够

| kind | 条数 | 语义 | 不单列会怎样 |
| --- | --- | --- | --- |
| `DIRECT` | 27 | 抽象点 = 某个设备点的原值 | — |
| `COMPOSED` | 2 | 抽象点由多个设备点**合成** | "某个单体过温"永远进不到 EMS（§5.3 的原话） |
| `SINK` | 3 | 抽象点是 **EMS → 设备** 的**下行落点** | 方向相反，会被 `self_check` 误判成"找不到来源" |
| `EXTERNAL` | 8 | 来自调度（IEC104），**不在设备侧任何点表里** | 藏进 `DIRECT` 或不登记，"抽象表 40 点是否都有交代"这条判据就失去意义 |

两条 `COMPOSED` 的实际口径：

- `EMS_T_C = mean(MEAS.BMS.T_MAX, MEAS.BMS.T_MIN)` —— 抽象侧只要一个温度，
  设备侧的权威量是最高/最低温度对。
- `EMS_STA_OFFLINE = any(comm_ok == 0)` —— 抽象侧是"三路通信位"的逻辑或非。

### 2.4 为什么新增点**只能追加在末尾**

索引是**运行时坐标**，段里的下标由登记顺序决定。中间插入一个点，
其后所有点的索引整体偏移 1 —— 编译期不报错，运行期按索引取到隔壁点。
所以 `DP_APPEND_BEGIN` 之后才是可追加区，**既有枚举一个都不能动**。
加载器的追加点用例（`test_point_config` T11）就是钉这条的。

### 2.5 为什么选 JSON 而不是 CSV / INI

| 理由 | 说明 |
| --- | --- |
| **有嵌套** | 一个点是八元组，而"量程"本身是一对 `(min,max)`。CSV 在 `MEAS.BMS.CELL_V_MAX` 这种含点的名字上，分隔符选什么都别扭 |
| **类型可信** | JSON 里 `"default": 0` 与 `"default": "0"` 是两种东西，能把"字段类型写错"与"字段缺失"**分开报错**；INI 里全是字符串 |
| **已有先例** | `P1/src/json_lite.h` 已建立团队对 JSON 配置的心智模型，不再引第二种格式 |

代价：JSON 比 CSV 啰嗦（107 点 ≈ 1200 行），手写容易漏逗号。
补偿：`json_min.h` 有意放宽 **注释 + 尾逗号 + 裸键** —— 现场想临时注释掉一行点位定义，
不该导致整张点表加载失败。

数字输出用"最短可往返"策略（15/16/17 位有效数字逐级回退），
使 `dump → parse` 的**双精度逐位相等**成立 —— C5 的往返幂等判据靠它。

### 2.6 为什么"禁充放位"必须与"允许充放功率"**同源**

A1 的教训是这两个位是 L0 最底层那道锁（`05/` 折进 `p_lower/p_upper`）。

如果模拟器把它们做成两个独立布尔开关，那么"T=50 °C 时功率限值掉到 0"
与"T=50 °C 时禁位还是 0"可以**同时成立** —— 于是 `05/` 的保护逻辑
**永远不会在温度维度上被触发**，测试全绿而现场会出事。
同源以后，"温度越限 → 限值降到 0 → 禁位置 1"是一条因果链，可以被单条断言钉住
（`test_sim_bms` T05）。

### 2.7 为什么死区必须给安全点开例外（死区 0 = 永远发布）

禁充放 / 故障 / 通信 / 数据有效性位被死区抑制，**不是"少发了一帧"，是安全链断了**。
这些点必须"永远发布"。

在动态工况下这条要求代价很实在：`test_scale_rtdb` 里 17 个安全点全部落在快档，
`17 × 600 = 10200` 次写入**无法压缩** —— 它是点值写入次数的**地板**，
见 §4 的量化对比。

### 2.8 为什么冷启动必须**全部档都先跑一次**

慢档点（单体电压）若"等到第一个周期才发"，那么从上电到第一个慢档周期之间，
EMS 看到的这些点是**从未收到过**（值 = RT_DB 默认值）。
而点表语义里"没被写过"与"写过 0"**不可区分** ——
于是上电头几秒所有单体电压都是 0 V，越限判据会集体误报。

### 2.9 为什么批量写要"整批成功或整批拒绝"

半批写入会让"这一拍的点集"处于一个**既不是旧值也不是新值**的中间态，
而下游无法察觉。所以先把所有点名解析成索引、再发一次调用；解析到一半失败就**一个都不写**。
`test_scale_rtdb` T08（`CountingWriter`）与 T10 ④（真 RT_DB）各钉了一遍。

### 2.10 为什么 PCS 的一阶惯性 τ 要跟 `11/` 同口径

两处模拟器若各写一式，跟踪曲线形状不同，"哪一条才是被测系统的真实行为"就说不清了。
这里用与 `MemoryDeviceIO::execute()` 同一式：`p ← p + (ref − p)·min(1, dt/τ)`，
再串 `ramp_kw_per_s` 变化率限幅（先惯性后限幅）。

### 2.11 为什么单位要区分 `"-"`（比例）与 `"%"`（百分数）

`CFG.BMS.SOC_MIN/MAX` 用**比例**（单位 `"-"`，量程 `[0,1]`），
`MEAS.BMS.SOC/SOH` 用**百分数**（单位 `"%"`）。这是刻意的 ——
它与 40 点表抽象契约逐字对齐（`CFG.SOC_PHYS_MIN` 单位是 `"-"`），
`self_check` 的"单位一致"判据正是靠这条抓"比例 / 百分数混填"。

## 3. 踩坑记录

> 本项目最看重的一节。每条写清：**现象 / 根因 / 修法 / 判据有效性**。

### 坑 1 — 分相有功之和 ≠ 总有功（浮点归一化）

- **现象**：`test_sim_meter` 里 `P_A + P_B + P_C` 与 `P_TOTAL` 差 1e-13 量级，
  `EXPECT_NEAR` 收紧到 1e-9 时红。
- **根因**：分相出力是 `p_total / 3 × 调制系数`，浮点除法引入的
  余项在三相里不闭合。
- **修法**：先按不平衡度**归一化**三相调制（让系数之和恰好等于 3），
  再让**末相取补** `p_C = p_total − p_A − p_B`（`src/meter_sim.h:143-153`）。
- **判据有效性**：把"末相取补"去掉，这条断言立刻红 —— 它不是恒真的。
  电流侧同理。

### 坑 2 — BMS 构造时限值为 0 ⇒ 冷启动锁死（**就是 A1 那个坑的翻版**）

- **现象**：`test_sim_bms` 一个用例里 `bh.soc() > 0.94` 始终不成立，SOC 纹丝不动。
- **根因**：`chg_limit_` / `dis_limit_` 成员默认初始化成 `0.0`，而推进循环的
  条件是 `while (chg_limit_kw() > 1e-9)` —— **一次都不进**。
  限值 0 在语义上等于"禁充禁放"，于是 A1 的锁在模拟器自己的构造函数里又被扣上了一次。
- **修法**：构造函数里显式 `chg_limit_ = dis_limit_ = cfg_.p_rated_kw;`
  （`src/bms_sim.h:132-133`），并留注释点名这是 A1 同一个坑。
- **判据有效性**：修好前该用例红、修好后绿；且 `test_sim_bms` T05
  另外钉住了"限值降到 0 时禁位必须变 1"这条**反向**因果。

### 坑 3 — `EXPECT_GT0` 把 double 截成 `long long`，正确的实现被判红

- **现象**：`EXPECT_GT0(lost - gained)` 报 `0`，而打印出来实际差值是 `0.00136`。
- **根因**：宏体写成 `(long long)(v) > 0` 之类，`0.00136` 被截断成 `0`。
  **这是测试框架自己的 bug，却表现为"被测实现不对"**。
- **修法**：`EXPECT_GT0` 改为 double 直接比较（`tests/expect.h:83`）。
- **判据有效性**：这类"框架把对的判成错的"最危险 —— 它会诱导人**去改正确的实现**。
  教训：断言红了先确认**断言本身**的语义。

### 坑 4 — PCS 待机态仍然跟踪指令

- **现象**：`test_sim_pcs` 里待机态 `fabs(p_actual()) < 1e-6` 失败。
- **根因**：状态机分支只处理了"运行时怎么跟指令"，
  `kStandby` / `kOffGrid` 沿用了上一拍的 `ref_p/ref_q`，于是一阶惯性继续往指令爬。
- **修法**：`kStandby` / `kOffGrid` 分支显式 `ref_p = ref_q = 0.0`（`src/pcs_sim.h:111`）。
- **判据有效性**：待机断言与"并网态必须跟上指令"的断言同时存在 ——
  只留后者的话，一个"永远待机、永远输出 0"的实现会全绿。

### 坑 5 — 分级节拍的"触发次数比"**不是**固定的 1/10

- **现象**：`test_scale_rtdb` T09 里断言 `fires[中]/fires[快] == 0.1`，
  实得 `0.5`。
- **根因**：比值 = `dt / 中档周期`。T04 里 `dt=0.1` 且快档周期也是 `0.1`，
  于是比值恰好是 `0.1`；到 T09 里 `dt` 变成 `0.5`，快档仍是"每拍到"，
  中档（1 s）变成"每 2 拍到"，比值就成了 `0.5`。
  **把 T04 的数字抄到 T09，是两个不同 `dt` 下的错误类比。**
- **修法**：改为按**周期**算绝对值
  （`EXPECT_EQ(fires[快], ticks)` + `EXPECT_NEAR(fires[中], ticks·dt/中档周期, 1)`），
  并加一条反向守卫：把中档周期拉到比慢档还长，触发次数必须跟着倒过来。
- **判据有效性**：反向守卫把"实现固定按 0.1 输出"也能通过的可能性排掉了。

### 坑 6 — "点值写入降 5 倍"这个判据本身就立不住

- **现象**：T09 断言 `point_writes < base/5`，实得 `13184` vs 门槛 `12240`，红。
- **根因**（**这条最重要的不是修法，是认知**）：17 个安全点必须"永远发布"，
  且它们全在快档 —— `17 × 600 = 10200` 次写入是**不可压缩的地板**。
  全量重发 61200 次 ÷ 10200 ≈ **6.0×** 才是点值写入降低倍数的**理论上界**。
  原来那个"5 倍"既接近上界又没把这层结构说出来。
- **修法**：把量化结论**拆成两段**报告，而不是一个笼统的倍数：
  - 总写入 61200 → 13184（4.6×，地板 10200 已含在内）
  - **扣除地板后**：数据点 51000 → 2984（**17.1×**）
  断言相应地改为 `point_writes × 4 < base` + `data_writes × 10 < data_baseline`。
- **判据有效性**：如果只留一个"4 倍"，那就成了"凑一个能过的数"。
  拆开之后，"地板"和"真实压缩力度"**分别**有断言，
  而且地板那条是**算出来的**（求和安全点各自档位的触发次数），不是写死的常量。

### 坑 7 — 两层点表**故意**同名不同写法

- **现象**：`test_point_table` 断言
  `EMS_POINT_NAMES[EMS_STA_BMS_DIS_FORBID] == "STA.BMS_DIS_FORBID"` 失败，
  实得 `"STA.BMS.DIS_FORBID"`。
- **根因**：抽象表用 `STA.BMS_DIS_FORBID`（下划线），
  全点表用 `STA.BMS.DIS_FORBID`（点分隔）—— 这是**有意**的：
  两层命名体系不同，映射表的两端各写各的，恰恰证明映射表在起作用。
- **修法**：改断言为"**两层写法不同**且都非空"，并加注释说明这不是笔误。
- **判据有效性**：如果两层名字逐字相同，映射表就成了"复制粘贴"，
  它是否真的在转译就测不出来。

### 坑 8 — 只调 `publish_static()` 不调 `step()` ⇒ 动态点一个没发

- **现象**：`test_sim_pcs` 断言"本拍发布了 39 点"，实得 6。
- **根因**：`publish_static()` 只写配置点（PCS 6 个），
  动态量在 `step()` 里才发。断言写在了 `step()` 之前。
- **修法**：断言挪到循环之后，改成 29（静态 6 + 动态 23；CMD 区 5 点是 EMS 下行，不由设备侧发布）。
- **判据有效性**：这条本身也是"点计数 vs 点表总点数"的对账 ——
  `34 = 6 静态 + 23 动态 + 5 指令`，三个数必须配平。

### 坑 9 — 中文 `.bat` 在 CP936 控制台显示为乱码；`echo` 行还会**吞掉后面的 ASCII 字符**

- **现象**：`17/scripts/build_test.bat` 的中文在 `chcp 936` 的 cmd 里显示成
  `璁惧叏鐐硅〃` 之类的乱码；更要紧的是
  `echo [OK] 17\ 设备全点表与高保真模拟器：6 个测试全部通过`
  显示成 `…模拟器[?] 个测试全部通过` —— **数字 6 消失了**。
- **根因**：本仓库的 `.bat` 统一是 UTF-8（`13/` 同样是），
  而 cmd 读 `.bat` 时按**当前代码页（936）解码**、回显时再按 936 编码。
  `：` 的 UTF-8 是 `EF BC 9A`，被 936 解码时 `EF BC` 合成一个字，
  剩下的 `9A` 是**前导字节**，会与后面的 `6`（0x36）配成一个 GBK 字 ——
  于是 `：6` 两个字符变成**一个**乱码字，`6` 被吃掉。
  `）`（`EF BC 89`）后跟空格同理。
- **修法**：
  - **`echo` 行一律改成纯 ASCII**（本模块 18 条 echo 全改），
    这样与控制台代码页、终端编码都无关，输出**逐字节稳定**；
  - `REM` 行保留中文 —— `@echo off` 下 REM 从不回显，乱码不可见，
    而中文注释的说明价值远大于"整份文件 ASCII 化"。
- **★ 真正致命的是"吞 CR"**（不是乱码）：某行末尾落在双字节字符的前导字节
  （0x81–0xFE）上时，该字节与行尾 `\r` 配成一对被吃掉 → 下一行的 `REM` 前缀被吞 →
  整行中文被当命令执行，而**退出码仍是 0**。
- **判据有效性**：新写的两个 `.bat` 都过了
  `python scripts/fix_bat_encoding.py --check`（输出"全部合规"，退出码 0）；
  并在批量替换脚本末尾断言"所有 echo 行均为纯 ASCII、旧串剩余数为 0"。
  `13/` 的 echo 行尚未这样做（**不在本模块权限内**），故 `13/` 的输出仍有同类乱码。


### 坑 10 — 批量写降的是**API 调用次数**，不是 seqlock 往返

- **现象**：把"批量写"接上真 RT_DB 后，段内 `header.write_count` 照样 `+N`。
- **根因**：vendor 的 `rt_db_set_multiple_values()` 内部是
  `for(i) rt_db_set_value(...)`。
- **修法**：**不掩盖**。在 `test_scale_rtdb` T10 ⑥ 用公开 API
  `rt_db_get_write_count()` 的前后差值把这件事留成**正面证据**，
  并断言 `delta == N`；同时在 `src/rtdb_batch_writer.h` 文件头写明。
- **判据有效性**：没有这条，"批量写省了 2000 次内存往返"就是一句没被检验的宣传。
  要真正降往返得改 `07/vendor/`（**不在 17/ 的权限内**）。

### 坑 11 — 把"有副作用的调用"塞进断言条件 ⇒ 实现真坏掉时**整个 exe 崩掉**，看不到 FAIL

- **现象**：做失败注入（把 `EXPECT` 条件临时改成恒假）验证构建脚本的失败路径时，
  `test_scale_rtdb` **没打印 `PASS=/FAIL=` 收尾行**就退出了，
  构建脚本因此只报 5 个 exe 失败而不是 6 个。
- **根因**：`EXPECT(batch.write_batch(...))` 把**有副作用的调用**放进了断言条件。
  正常跑没问题（条件总会被求值），但一旦 `EXPECT` 改为不求值（或有人做失败注入），
  这次写入就静默不发生 → `calls == 0` → 随后的
  `single.stats().calls / batch.stats().calls` 是**整数除零**（崩溃，不是 FAIL）。
  换句话说：**一个真实的实现回归会让测试崩掉而不是报红**，而崩掉的现场没有任何 FAIL 清单。
- **修法**：调用单独一行、结果进断言；
  并在除之前加 `EXPECT_GT0(...)` + 非零保护（`test_scale_rtdb.cpp` T07）。
  其余文件里仍保留 `EXPECT(有副作用的调用(...))` 的写法（本仓库既有风格）——
  它们后面没有除法与下标，实测失败注入下 6 个 exe 都干净报红，故未强行统一。
- **判据有效性**：**这条判据本身就是判据**：做完修改后重跑失败注入，
  6 个 exe 全部干净地报 `[FAIL] ← has failing assertions`，退出码 1，
  汇总行 `assertions total: PASS=442 FAIL=279 SKIPPED=0`。
  再恢复 `expect.h`、复跑确认 721/0/0 —— **一个不会红的构建脚本等于没有构建脚本**。

## 4. C1 / C2 / C3 的量化结果

场景：三台模拟器 → 全点表 102 点（107 减去 5 个 CMD）→ `分级节拍 → 死区 → 批量写`。
`dt = 0.5 s`，600 拍 = 300 s；工况是正弦驱动的**动态**工况（功率/无功/负荷/光伏都在变）。

档位：快 0.1 s / 中 1.0 s / 慢 5.0 s。
档位点数：快 32 / 中 38 / 慢 32；触发次数：快 600 / 中 300 / 慢 60。

| 口径 | 全量重发（= 修复前的 `publish_all()`） | 优化后 | 降低 |
| --- | --- | --- | --- |
| **API 调用次数** | 61200 | **600** | **102.0×** |
| 点值写入次数 | 61200 | 13184 | 4.6× |
| ├ 其中：安全点永久发布（**不可压缩的地板**） | 10200 | 10200 | 1.0× |
| └ 其中：数据点（扣除 17 个安全点） | 51000 | **2984** | **17.1×** |

- 分级到期 32520 次，死区抑制 19336 次（抑制率 **0.5946**）。
- **死区抑制率的分场景口径**：`test_scale_rtdb` T01 的**静止**工况抑制率 **> 99%**；
  上面的 59.5% 是**动态**工况 —— 值本身在连续变化，死区自然压不下去。
  两个数字都真实，别互相替代着用。
- **逐点值等价**：安全点 17 个逐位核对，不一致 **0**；
  非安全点 85 个，不一致 64（死区允许的滞后，**必须有**，否则说明死区没生效）。

批量写本身（`test_scale_rtdb` T07 / T10）：

| 场景 | 单点写 | 批量写 |
| --- | --- | --- |
| N=40 点（内存 CountingWriter） | calls=40 | **calls=1** |
| 8 点（真 RT_DB 段） | calls=8 | **calls=1**（段内 write_count 仍 +8，见坑 10） |

## 6. 已知边界

**诚实优先 —— 下面这些是"没有做"，不是"已完成"。**

1. **没有接 `13/` 的 Modbus。** 全点表的落点是 RT_DB，17/ **不产生 Modbus 报文**。
   `13/` 是第一个真实消费者（§10.5），但"点表 → Modbus 寄存器映射 → 真机"这条链
   本模块没有走。B3 的原始描述是"Python 模拟器不存在"，
   17/ 给的是 **C++ 侧设备物理模型**（`meter/bms/pcs_sim.h`），
   Python 侧仍是 `13/sim/modbus_slave.py`，两者没有接起来。
2. **没有挂进 `scripts/build_all.bat`。** 按约定 §6，这一步**由集成方统一执行**
   （避免多个工作流并发改同一个文件互相覆盖）；且本次施工的硬性边界是
   **不改 `scripts/build_all.bat`**。所以 `17/` 目前只在自身 `scripts/build_test.bat` 下跑。
3. **107 点是"常用全点表"，不是某个厂家的完整点表。**
   单体不做**逐点登记**：单体是 224 串的数组，只有在模拟器内部；
   点表里登记的是极值 + 编号（`CELL_V_MAX/MIN` + `_IDX`、`T_MAX` + `_IDX`）。
   真实厂家点表动辄几千点（含每个单体的电压/温度），那部分需要由厂家点表自动生成（§5.3 的"协议层生成"）。
4. **死区只做"与最后发布值比较"，没有"最长静默强制上报"。**
   一个点若长期不变就长期不发，下游无法区分"没变"与"断线"。
   现在靠安全点死区 0 + `STA.COMM_OK` / `HEARTBEAT` 兜；**没有**做"每 N 秒保底重发一次"。
   这是 C2 的已知缺口（也是 §3.4 里没被列出的第四条）。
5. **`TieredScheduler` 只给机制，档位分配由调用方给。**
   17/ 里有一个示例分配（保护/状态 → 快，功率/三相 → 中，单体/电量/需量 → 慢），
   但它**不是配置项**，也没有做成可加载的规则。
6. **点表加载器只做结构校验**（八元组齐备 / 单位非空 / 量程自洽 / 重名），
   **不校验"量程是否与现场设备匹配"** —— 那需要设备手册或实机标定，不在本模块能力内。
   也没有 schema 版本号与向后兼容处理。
7. **三个模拟器都不是电磁暂态模型。** 保真度级别是
   "表计口径完整 + 一阶惯性 + 能量积分 + 热积分"，采样步长由调用方给。
   **没有实时调度**（不起线程 / 不 sleep），时间只是仿真时间轴。
8. **`EXTERNAL` 8 点是"标注了来源类别"，不是"接上了 IEC104"。**
   `reason` 写清了来自调度，但调度那一侧的写入在本模块之外。
9. **批量写降低的是 API 调用次数，不是 seqlock 往返**（见坑 10）。
   要真正降往返必须改 `07/vendor/`，不在 17/ 的权限内。
10. **没有 Python 依赖，因此本模块的断言总数是单一口径**（721），
    不存在 `13/` 那种"有 / 无 pymodbus → 两个合法基线"的问题。
    唯一的条件是 T10 需要能建 Windows 页文件映射段；建不出来时它打印
    `SKIPPED=1` 并以 0 退出（**不是 FAIL**，但也**必须打印**）。
